## 组成及作用

| 部分 | 作用 | 对我们的意义 |
| --- | --- | --- |
| agents | 9份专长代理：规划、架构、TDD、代码审查、安全审查、构建排障、E2E、清理、文档 | 参考专业职责，不逐文件变成常驻岗位 |
| rules | 8份共享约束：代理调度、风格、Git、hooks、模式、性能、安全、测试 | 约束独立于岗位；我们按场景加载，不全部常驻 |
| skills | 工作方法与领域知识 | 复用现有Skill，避免角色手册复制教程 |
| commands | 用户触发入口及流程组合 | 对应轻入口，不应再复制岗位职责 |
| contexts | dev/review/research工作模式 | 模式切换不等于独立审查者 |
| hooks | 工具前后和会话事件自动动作 | 宿主相关机制，须单独验证，不当作文字规则已强制执行 |
| scripts | hooks与包管理器检测的Node实现 | 对应工具实现，不属于岗位定义 |
| tests | 工具脚本与hooks测试 | 证明工具行为，不证明所有岗位专业能力 |
| mcp-configs | 外部工具连接配置示例 | 候选连接方式，不是已部署能力 |
| .claude-plugin / plugins | 插件清单与生态说明 | Claude宿主打包，不直接适配Pi/Herdr |
| examples | 项目/用户配置、会话等示例 | 参考形状，不继承私人业务假设 |

注意：setup-pm在该项目指package manager，不是项目经理。orchestrate的bugfix示例引用explorer，但agents目录没有同名定义；文档流程不等于完整可执行系统。

## 从开发交付倒推最小结构（待讨论）

目标→形成方案→判断方案是否可执行→实现→判断代码是否符合方案→验证实际结果→PM汇总。

岗位只承载一项清楚的责任与交付；同一个角色可以多实例，专业方法按需引用Skill。不是每次任务走满全部角色。

- PM：目标、范围、依赖、委派、证据汇总和待决策项，不替代所有专业判断。
- 方案设计：整合planner的可执行分解与architect的取舍分析；优先扩展现有架构岗位，不再加一个与PM重叠的规划层。
- 方案审核（新增候选）：读取方案与需求基线，找缺失前提、契约冲突和不可执行步骤；输出带依据的阻断/建议/通过，不自己改方案。参考planner/architect的专业检查维度；参考仓库没有独立的同名plan-reviewer。
- 开发：沿用前端与通用开发，按实际技术栈加载方法；排障、TDD、清理和文档通常是开发任务的方法，不先建立四个常驻岗位。
- 代码审查（新增候选）：基于确定diff和需求，检查正确性及直接影响；输出位置、证据、后果和最小修正建议，不顺手修改实现。
- 测试：沿用现有岗位，负责需求到可观察结果；验证方式由任务决定，不统一绑Playwright或覆盖率。
- UI、调研、安全专长：存在真实缺口时加入。安全可先作为审查专长，是否独立岗位留待实际任务决定。

方案作者与审核者、代码作者与审查者要有独立判断时不能复用同一实现上下文。专业岗位把结果交PM，由PM决定返工与交接，不嵌套创建代理。

## 借鉴和调整

1. 借鉴planner具体到改动位置、依赖、边界和可验证步骤；不要求小任务输出完整长方案。
2. 借鉴architect对方案的收益、代价、替代项与理由；不继承Next.js/Supabase/交易项目示例或无依据的扩容路线。
3. 借鉴code-reviewer的问题分级和file:line、Issue、Fix；替换为我们的阻断项/相关建议/需求外观察，限制本次diff和直接依赖。
4. 借鉴e2e-runner的场景与证据对应；测试工具和范围服从项目，不把浏览器测试升级为全工作台唯一验收方法。
5. 不继承所有改动强制启动代理、永远并行、固定Opus或其他模型、全项目80%覆盖率和所有测试类型必跑。
6. 不继承security-reviewer既审查又直接修复的默认混合职责，不把隐藏工具当权限隔离。
7. 不全盘安装hooks：其开发服务强制tmux、限制Markdown新建等规则与当前工作台不同。

建议先讨论并批准“方案设计→方案审核→开发→代码审查→测试”的输入输出与触发条件，再编写最短岗位手册和引用已有Skill。保留当前运行底座；专业内容可以重写，没必要从零重建调度器或增加目录层级。
