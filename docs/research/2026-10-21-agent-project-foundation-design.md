# AI Agent 项目底座：统一结构与初始化 Skill 设计

日期：2026-10-21。状态：设计待确认；不是已创建、启用或验收通过的 Skill。

## 1. 最终交付应是什么

提供一个面向用户的“初始化项目开发底座”操作，内部复用现有新项目、老项目与增量同步三个 Harness 能力。它在项目中建立一套有固定职责的最小入口，让后续Agent知道规则、架构、需求、用例、环境和账号引用在哪里；不统一业务源码目录，不安装第二套交付框架。

当前仓库已有相关Skill和模板，缺的是轻量默认结构、长期测试资源入口及一致的正文归宿。推荐调整现有Harness Pack，不默认再建一个名称不同但职责重叠的Skill。若以后确需独立用户入口，仅做薄路由，名称和安装另经确认。

官方方案依据见[第一方调研](2026-10-21-agent-project-bootstrap-primary-sources.md)；本设计从中选择方法，不宣称下列目录为业界强制标准。已有测试准备设计见[复用账号与默认库](2026-10-21-reusable-project-test-preparation.md)。

## 2. 新项目默认结构

只创建已有内容和当前需求真正需要的文件；下图中按需项在首次产生内容时创建。

```text
项目根/
├── README.md                       给人：用途、启动入口
├── AGENTS.md                       给Agent：任务路由、必要命令入口、操作底线
├── ARCHITECTURE.md                 组件职责、主链、改动落点；空项目标目标设计
├── CONTEXT.md                      按需：有歧义的项目术语
├── docs/
│   ├── harness/
│   │   ├── README.md               仅导航：何时读哪份现有正文
│   │   ├── rules.md                项目特有工程约束；引用formatter/schema，不抄配置
│   │   ├── development.md          需求如何编号、批准、迭代、交付及更新当前事实
│   │   └── testing.md              最小验证方式、长期环境/角色/账号获取入口
│   ├── requirements/
│   │   └── 0001-需求名/            按需：首次需求产生时创建
│   │       ├── requirement.wl-req-confirm.md
│   │       ├── requirement.wl-req-confirm.html       从md生成
│   │       ├── design.wl-design-doc.html             唯一设计正文
│   │       ├── test-cases.wl-qa-test-planner.md
│   │       ├── test-cases.wl-qa-test-planner.html     按需从md生成
│   │       └── progress.md                           按需：只记执行状态与证据引用
│   └── decisions/                  按需：非显然取舍，不复制需求/当前事实
└── .gitignore                      本机秘密/状态/构建产物不提交，不能替代秘密保护
```

README/架构/rules/development/testing各拥有不同事实；harness README只有导航，不把所有正文合并，也不另维护机器manifest。小项目已有清晰AGENTS路由时可以省略重复导航；只要能找到相同职责，不为凑目录强建空文件。

初始化状态复用现有Harness的STATE/changes，仅草案未完成或底座真实变更时产生；不成为长期需求状态中心，不为模板升级自动commit。

### 老项目保持路径，统一读取职责

初始化先建立“已存在/缺失/冲突”的Owner映射，再补一跳，不能搬业务仓库或重写已有文档。固定的是读取方法和事实归属，不是强迫所有老项目重命名。

例如Yuxi继续使用根ARCHITECTURE、docs/develop-guides/spec-loop和testing-guidelines；AGENTS指到这些Owner。测试资源刚补在testing-guidelines中，就不再新建一个竞争的docs/harness/testing。具体需求目录继续原来的docs/requirements，不并建openspec和specs作为第二份正文。

## 3. Agent怎样统一加载

根AGENTS用如下语义路由，具体路径在初始化时从真实Owner生成：

```text
收到任务
  ├─ 了解/改源码 → 读架构相关部分 + 命中子树规范
  ├─ 新增/变更需求 → 读development → 进入当前阶段及该需求目录
  ├─ 生成用例/准备测试 → 先读testing长期资源 → 检查本需求覆盖
  ├─ 执行登录/数据库/发布 → 动作前加载相应安全规则与授权条件
  └─ 只查文件或Git状态 → 不加载完整开发流程
```

AGENTS保留秘密保护、外部副作用、删除和发布授权等始终适用底线；专项正文按动作触发，不能为了省上下文漏读。子树AGENTS仅在真正存在局部差异时生成。

支持AGENTS的宿主直接读取；Claude或其他宿主只加最薄入口适配，规范正文不复制。未测试的宿主支持标未验证，不能把文档链接当强制执行Hook。

## 4. 后续需求怎样迭代

```text
原始诉求
  ↓
同一需求目录：确认目标和差异 → 用例定义数据/预期 → 设计
  ↓
取得对应批准，才实施并验证
  ↓
结果进入既有执行记录，progress只引用证据
  ↓
变化成为当前行为：更新源码对应架构/契约/测试说明
  ↓
保留需求和决策历史，不让历史草稿覆盖当前事实
```

需求批准、方案批准、实现完成、测试通过和开放使用分别表达。需求变更修订同一需求正文及受影响用例，记录版本与新确认，不复制“第二版分析报告”争夺Owner；已冻结历史/已发布证据按项目规则保留，新需求不改写旧通过记录。HTML派生与单一设计正文沿现有wl-*契约。

初始化只说明何时进入这些环节，不把简单改字强制升级成完整流水线；需要使用共享Skill时按真实登记路径加载，没有该Skill则明确缺少能力而非伪称可用。

## 5. 环境、账号、密码的固定读取方式

统一的是“公开导航 → 受控获取”，不把所有秘密放一个可被模型全文读取的仓库文件。

### testing正文的最小长期索引

| 内容 | 示例（合成） | 边界 |
|---|---|---|
| 默认环境 | local-dev，已核验入口/Compose定位 | 数据库由项目确定，不默认生产或每需求隔离 |
| 库标识与核验方法 | 服务别名/数据库名/schema，实际连接只输出必要标识 | 不存DSN/密码，登记不代表当前连接正确 |
| 角色别名与作用域 | operator、viewer、product-a；企业A/B | 按权限差异最少账号，过期只补登 |
| 受控获取引用 | 既有密码管理器条目/钥匙串名/获准本机登录入口 | 只引用，不复制密码/token/cookie |
| 维护与失效处理 | 负责人、最后核验、缺口及补齐条件 | 存在/映射/登录有效分别记录 |

本需求输入、测试数据关系和预期归用例；实际运行ID/结果归既有result.json。账号新增、数据写入与清理分别检查授权，长期账号不随每轮清理。

### 秘密实际存在哪里

优先复用项目已经批准的密码管理器、系统钥匙串或CI秘密存储，由工具按需消费；仓库只保存secret reference和必要字段名。没有现成秘密存储时，初始化提出最小本机方案并请求授权，不自动安装Vault或把密码写进AGENTS。被忽略的`.local`文件可以容纳非秘密本机映射；若将来需要存秘密，必须另行授权访问控制与生命周期，`.gitignore`本身不提供加密和保密保证。

模型默认加载账号别名/角色/入口，不全文读取凭据正文；能由受控工具直接使用的凭证不回显到聊天、命令日志、截图和产物。固定结构不构成对所有后续项目密码的读取授权。

## 6. Skill应怎样工作

### 初始化：盘点、映射、补缺、验证

1. 识别新/老项目，读取根指令、已有入口、构建配置及任务必要材料；不先扫描全库或秘密。
2. 列上述事实职责的Owner映射，已有则复用；冲突先指出，不按最新文件名直接覆盖。
3. 提出最小目录/入口补丁、缺失事实、验收方式。新项目无源码则只写已确认目标，不编造接口、测试账号或通过状态。
4. 获准后只创建缺失正文和短指针，保留原文；记录托管块/基线，文件已变化则停止重叠补丁，不覆盖用户工作。
5. 校验链接、状态、秘密边界和代表任务；重跑无增量不写文件、不提交、不启动服务。

### 日常维护：不重复初始化

单需求变更在原Owner处修改；稳定结构变化才进入现有harness-sync。模板升级只提候选diff，不自动给所有项目铺新文件。初始化不默认全量提取API、创建多角色、生成空Wiki或复制编码规范。

### 对现有能力的最小调整

- greenfield/legacy共享协议改为以上轻量默认；完整工程手册仍可按明确需求使用，不能默默删除已有消费者的路径。
- 新增AGENTS中立模板和testing长期资源模板，不再默认只生成CLAUDE入口。
- harness-sync复用已有增量/不覆盖规则，取消自动commit和无增量写记录；委派按负责人选择，不因monorepo强制组队。
- wl-req-confirm/wl-design-doc只核对项目已确认Owner/归档路径，不建立冲突的术语、架构或设计正文。
- wl-qa-test-planner增加生成前资源覆盖检查，执行约定增加实际身份/库核验；不另加测试账号管理Skill。

以上均为待实施改动。现有能力的“已验证”只代表原功能，不覆盖本版新增默认和跨宿主行为。

## 7. 怎样判定真的交付了底座

| 验收任务 | 必须能完成 | 失败信号 |
|---|---|---|
| 找到改动点 | 从入口定位架构、相关源码/契约与最小验证 | 通读全库或生成API副本才能理解 |
| 开始新需求 | 找到固定归宿和正文Owner，不复制第二套分析/设计 | 状态混同、要求重复提供已有资料 |
| 准备权限测试 | 找到最少账号/默认库/受控入口，指出真实缺口 | 泄露秘密、猜库、每需求建号 |
| 新项目初始化 | 只生成有依据的最少结构，未知明确 | 空模板充数、编造运行事实 |
| 老项目/第二次运行 | 保留原路径和本地修改，无增量不变化 | 覆写AGENTS、迁移文档、重复副本 |
| 宿主加载 | 在实际目标宿主证明命中规则与无关任务不加载 | 文件存在即宣称生效 |

初次只在临时夹具验证新项目和有本地改动的老项目，不对Yuxi或其他项目批量改造。夹具成功和用户确认后，才选择一个真实项目试用；安装/启用和真实外部操作另核授权。本轮只完成研究与本设计，没有创建、安装或实施Skill。
