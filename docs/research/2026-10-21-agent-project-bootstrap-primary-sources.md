## 一、结论先行

**建议做一个轻量、可重复运行的“盘点—映射—补缺—核验”Skill，而不是默认安装整套框架。** 用 AGENTS.md 做共同入口，借鉴 BMAD 的存量接纳与小块更新，借鉴 OpenSpec 的“当前行为与变更历史分开”，在复杂需求中选用 Spec Kit 的规格、计划、任务与一致性检查。四者都不能自动补齐真实测试环境、账号权限和秘密管理。

最小场景：老项目已经有 `CLAUDE.md`、架构说明和测试账号登记。用户要求“统一底座”时，不应再生成三份同义规范，也不能把账号密码搬进新目录。

> Skill 盘点已有入口和事实来源 → 维护者确认每类事实的唯一 Owner → Skill 提议最小增补及宿主指针 → 维护者批准后更新 → 用入口命中、链接及秘密检查验收。

这是拟议流程，本次未执行项目初始化。

### 不能混用的三个概念

1. **初始化目录 ≠ 项目知识已经准确。** Spec Kit 明确不替现有代码反推完整规格；OpenSpec init 的空目录不代表业务规格已建立；BMAD context 工作流也需核验、提问和批准。[S1][O1][B2]
2. **文档校验／任务勾选 ≠ 环境可用／用例通过。** OpenSpec 的结构检查、Spec Kit 的一致性与收敛检查、BMAD 的测试生成分别解决不同问题，不能替代真实运行证据。[O1][S3][B3]
3. **宿主入口存在 ≠ 强制执行。** AGENTS.md、命令、Skill、导入语法是不同递送方式；工具权限、安全隔离和 CI 门禁仍需独立配置与验证。[A1][S2][O1][B2]

## 四、拟议可复用 Skill 的最小设计（非现成框架能力）

以下均为本次建议，不冒充官方标准，不构成 Skill 已创建或已验证。

### 4.1 结构先定义职责，不强迫目录搬家

每类事实只选**一个负责维护的正文与维护责任人／团队（Owner）**。老项目保留现有路径，索引只记录引用。新项目尚无对应资料时才建议如下位置，不预先生成空壳全家桶。

| 事实类别 | 建议默认归宿 | 单一 Owner 及边界 |
| --- | --- | --- |
| Agent 接单入口 | 根 `AGENTS.md` | 只放任务路由、基础安全边界和必要指针；不能变成资料仓库。 |
| harness 适配及条件规则 | `docs/agent/` 中的规则正文；宿主原生文件只做薄适配 | 同一条规则正文只维护一次。记录宿主、触发条件、递送位置和验证状态；不支持条件加载时明确降级方式，不伪装已强制执行。 |
| 架构与决策 | 复用已有架构／ADR；没有时建议 `docs/architecture/` | 维护组件边界、跨组件约束及决策依据；能从代码或构建配置直接确认的信息优先引用，不维护第二份依赖清单。 |
| 当前业务行为 | 既有规格入口；无则建议 `docs/specs/` | 若已采用 OpenSpec，以其 `openspec/specs/` 为正文；不要另抄一份。代码是实现证据，未验证的描述标“待核验”。 |
| 需求迭代与历史 | 既有需求目录；无则建议 `docs/changes/<需求编号>/` | 需求、方案、用例正文分别唯一；状态与证据互相链接。采用 Spec Kit 等体系时沿其路径，不平行建同义需求包。 |
| 测试方法与环境 | 已有测试指南；无则建议 `docs/testing/` | 维护用例入口、环境 ID、依赖、数据边界、允许操作和证据要求；实际测试代码留原测试目录。 |
| 测试角色与账号索引 | 测试指南中唯一的一张角色／环境映射表 | 保存角色别名、租户范围、权限预期、账号领取或秘密引用方式、失效处理和 Owner；**不保存凭据值**。账号标识本身敏感时也只放别名。 |

例如现有 `docs/requirements/` 已维护需求确认和用例，就把它登记为该类事实 Owner，而不是再造 `docs/changes/`。索引是导航，不是正文副本；长期架构决策与单次需求设计也不互相全文复制。

### 4.2 同一个老项目的增量融合

1. **只读盘点**：识别已有入口、构建配置、架构、需求、测试文档及宿主配置；不扫描凭据文件，不启动服务，不读取真实秘密。
2. **给映射和缺口**：每类资料标记“复用／仅补指针／缺失／冲突／待核验”，说明 Owner 和证据。冲突不能靠“新文件优先”自行裁决。
3. **提出最小变更**：默认不搬目录、不重命名、不改用户正文；确需修改时给局部 diff。批准范围外的历史材料不顺手清理。
4. **后续经授权才执行**：第二次运行不重复创建、不扩写相同内容；更新模板前比较上游基线、本地改动与目标版本，无法安全合并就停。
5. **最小验收**：入口可发现、引用有效、不同宿主能读取对应规则、相关动作前加载而无关任务不加载、秘密不落盘。没有环境时只报告静态核验，不写“初始化可用”。

新项目可从最小入口及确有内容的文档开始；架构未知、测试环境未提供时留明确缺口，不为了目录完整而编造事实。

### 4.3 测试环境与秘密的硬边界

**测试角色**是“要验证哪种权限”，**测试账号**是“谁在该环境执行”，**秘密引用**是“经授权后从哪里取得凭据”；三者必须分开。

建议每条测试准备记录包含：环境 ID、入口及依赖、角色别名、租户／数据范围、允许读写操作、账号 Owner、秘密引用标识、登录／刷新方式、最后核验日期、阻塞原因。这里只给字段，不填写任何真实账号或环境事实。

- **普通 tracked 文档不得出现密码、Token、Cookie、私钥、完整敏感连接串或含会话内容的 storage state**；截图和日志也需要脱敏。
- **gitignore 不等于秘密管理**：它不负责加密、访问授权、轮换、审计、撤销，也不自动清除已经进入 Git 历史的秘密。被忽略的本地文件仍可能被读取或复制。
- 优先复用项目获准的秘密管理服务、系统钥匙串或 CI 秘密注入。仓库只存变量名／秘密引用及领取步骤；本地必须落地时另行授权并限制权限和生命周期，不通过聊天回显凭据。
- 不把“可通过环境变量提供 Token”宣传为完整秘密管理。Spec Kit 的 `token_env` 是工具资源访问的认证选项，不解决业务测试账号分配、租户权限与会话恢复。[S4]
- 初始化只建立索引和授权边界，不默认创建账号、提升权限、写数据库、调用生产或启动共享服务。这些动作必须另有明确授权。
