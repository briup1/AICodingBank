# 需求 0001：个人 AI 工作台最小骨架

## 需求重定义

**原始诉求**：参考 Brayness 中有启发的能力，将当前项目发展为个人 AI 工作台。

**最终目标**：让现有的能力仓库、项目、个人偏好、知识和任务机制不再彼此孤立；用户与 Agent 每次开始工作时，都能明确工作台是什么、当前处于哪个阶段、目标项目在哪里，以及下一步应调用哪类现有能力。

**异议**：不应复制 Brayness 的目录和完整运行时。当前系统已经具备更成熟的 Skill 治理、知识库和任务可观测性，真正缺少的是统一入口和清晰路由。首期应先建立最小骨架，验证它能否降低选择和衔接成本，再决定是否增加自动化。

**约束**：

- 在当前仓库基础上升级，不另建一套平行工作台。
- 首期采用文档驱动，不引入新程序、数据库、服务或依赖。
- 个人路径、偏好和其他私有信息不得进入共享版本库。
- 现有 Skill 安装、登记、验证及按需加载行为保持不变。
- 不覆盖或夹带工作区已有的其他未提交改动。

**重定义后的需求**：为现有个人 AI 系统建立一个最小且可读的控制骨架，统一说明系统边界、工作阶段、项目入口和个人上下文，使现有组件能够按同一条工作路径协作，同时保持隐私与既有能力治理不变。

## 用户故事

1. As a **工作台使用者**, I want 从一个统一入口看懂工作台的定位、组成和边界, so that 我不必分别猜测每个仓库、工具和知识源的职责。
2. As a **任务发起者**, I want 根据任务现状判断当前工作阶段及下一步, so that 我不会在需求未确认时设计、在方案未批准时实施，或在未验证时宣称完成。
3. As an **Agent**, I want 获得明确且不重叠的阶段路由, so that 我能优先复用现有能力，而不是临时发明新的流程。
4. As a **跨项目开发者**, I want 通过项目索引找到项目位置、用途、知识入口和常用工作入口, so that 我能快速进入正确上下文，同时以项目真实文件为准。
5. As a **个人用户**, I want 将稳定偏好与私人项目资料保留在本地上下文中, so that Agent 可以持续理解我，而共享仓库不会暴露隐私。
6. As a **Skill 维护者**, I want 保留当前能力控制面的规则和边界, so that 工作台升级不会破坏已经可靠运行的 Skill 供应链。

## 不做什么（Out of Scope）

- 不复制 Brayness 的目录结构、命名、脚本或完整 Harness。
- 不把现有项目迁入当前仓库，也不改变各项目的 Git 边界。
- 不统一或迁移 Pi 会话、模型配置、凭证及其他运行状态。
- 不开发 Web UI、任务看板后端、数据库或项目扫描服务。
- 不新增阶段 Skill；首期只组织和路由已有能力。
- 不重构 Skill 安装器、登记格式、验证门禁或第三方依赖管理。
- 不自动执行完整开发流程；人仍负责需求、方案和高风险操作的批准。
- 不在本需求中处理当前工作区已有的其他未提交内容。

## 验证方案

| 维度 | 可观察的验收结果 |
| --- | --- |
| 统一入口 | 新用户从仓库主入口出发，可在两次跳转内找到工作台定位、系统组成、阶段路由、项目索引和个人上下文说明。 |
| 阶段路由 | 对“了解现状”“确认需求”“设计方案”“开始实现”“检查结果”“记录经验”六类典型请求，文档均能给出唯一的当前阶段和明确下一步。 |
| 项目索引 | 使用者能通过索引找到已登记项目的本地位置、用途、知识入口和常用入口；索引同时声明实际项目文件是事实来源。 |
| 个人上下文 | 私人路径和偏好可供本地 Agent 使用，但不会出现在 Git 待提交内容中；共享版本仅提供字段与使用说明。 |
| 兼容性 | 现有 Skill 登记、安装、验证门禁和按需加载规则不发生行为变化，原有自动化检查继续通过。 |
| 可读性 | 工作台核心说明保持单一入口、无重复定义；详细能力继续按需读取，而非全部塞入常驻规则。 |
| 工作区保护 | 验收差异中不包含本需求范围外的既有未提交修改。 |
