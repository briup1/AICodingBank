# wl-herdrs

本 Skill 定义个人编排策略；最常用命令直接维护在[PM手册的委派场景命令](../../../../roles/project-manager/ROLE.md#委派场景命令)，不另建速查文件。其他操作查当前可用清单中 `herdr` Skill 的原始文件；生命周期和 CLI 语法以上游Skill及当前CLI为准。

## 进入条件

### 统一委派约定（2026-10-19 用户确认）

调用资格：仅项目经理。当前负责人可承担项目经理职责；已接到执行任务的岗位不得通过自称项目经理继续委派。一层链路为“项目经理 → 执行岗位 → 项目经理回收”，不允许嵌套子代理。工具是否可见不改变职责边界；目前尚未验证工具级禁用。

无论负责人使用哪个 Code Agent，只要确需把明确子任务交给另一个 Agent，就进入本 Skill。负责人宿主可以变化，委派方式不跟着变化。

- 本 Skill 是个人委派策略的唯一正文；岗位与宿主入口引用这里，不各自选择执行工具。
- 固定执行选择见 [统一子代理执行配置](../../../execution-profiles/delegation.md)。不使用宿主内置子代理，不自动改用其他 CLI；下方兼容性表仅用于历史参考，不作为工具选择菜单。
- 有可拆分任务不等于必须委派；自己执行与委派的选择遵循[项目经理手册](../../../../roles/project-manager/ROLE.md#角色定位)。用户明确要求PM自己完成或不要委派时，不启动子 Agent；无法直接完成则报告缺口，不擅自委派。
- Herdr 不可用、启动失败或不能确认思考级别时，不切换备选通道。能自行完成则说明后自己完成；确实要求独立执行或验证则报告阻塞。
- 派单模板只维护在[PM手册的三段式派单](../../../../roles/project-manager/ROLE.md#三段式派单)，本Skill不另存副本；不要求JSON、固定字段或完整会话。
- 子 Agent 的完成声明不是验收证据；负责人负责回收、核对和最终交付。

```text
收到任务
  -> 是否确需委派且有边界清楚、可验收的子任务？
       ├─ 否：负责人直接完成
       └─ 是：读取固定执行配置，检查 HERDR_ENV=1 与启动前提
                ├─ 满足：使用上游 herdr Skill 委派
                └─ 不满足：负责人可完成则自己做；必须独立执行则报告阻塞
```

- 用户明确提到 Herdr 时总是检查本策略。
- 用户未提 Herdr，只要确需委派仍先应用本策略，不因负责人宿主变化而换通道。
- `HERDR_ENV` 不是 `1` 时不控制 Herdr；按上述阻塞处理，不以本地完成冒充独立验证。
- 不为很小的任务、当前步骤的即时阻塞项或写集合重叠的任务创建子 Agent。

## 拆分规则

子任务必须同时满足：

1. 有一个清晰目标和可量化完成标准。
2. 明确允许读取和修改的路径。
3. 能独立运行聚焦验证。
4. 与并行任务不存在共享写集合。
5. 并行委派时主 Agent 有独立工作可继续；用户明确要求独立分析或验证时，允许等待其结果，不为并行而另造任务。

优先按垂直结果拆分，例如“实现并验证一个完整行为”；不要按模型、控制器、测试等水平层拆分。主 Agent 始终负责上下文、排序、冲突处理、集成和最终验证。

## 子 Agent 默认 YOLO

通过 Herdr 新启动的编码子 Agent 使用固定执行配置指定的工具，在获准范围内使用当前 CLI 支持的无人工权限确认模式；启动参数按[PM手册的委派场景命令](../../../../roles/project-manager/ROLE.md#委派场景命令)中的加载规则核验；已有上下文中的有效 CLI 契约可沿用，不从兼容性表选择其他工具。

当前已验证映射见 `references/compatibility.md`。原生参数必须放在 `herdr agent start ... --` 之后。

YOLO 只用于用户已经批准的目标项目或隔离 worktree 内的开发任务。子 Agent 提示必须限制写入范围，并排除：

- 生产环境、发布和外部系统写操作
- Token、密码、Cookie、私钥和客户敏感数据
- 未经授权的 Git push、破坏性 Git 操作和目录删除
- 超出任务边界的配置、依赖或权限修改

命中这些范围时不以 YOLO 委派；由主 Agent 停下并取得明确授权。

## 委派与回收

### 默认：直接交代工作

一次分析、一次实现或一次验证，默认直接使用 Herdr 的 start → prompt → wait/read，不先创建项目组、不写 group.json/task.json、不要求执行者 checkpoint。已有台账管理的任务仍按原记录继续，不绕过台账重复派发。

1. 用几句话交代任务；只有一个工作包就直说整项由谁负责，不强凑拆分。必要资料的实际路径只给一次。
2. 只核对当前项目相关实例。新建执行者使用独立 Tab，不用 pane split；在调用者工作区创建，创建时按岗位命名，保持目标项目 cwd 且不抢焦点，使用返回的 root pane ID 启动 Pi，显式 high 并核验实际生效。项目经理不修改自己所在Tab的名称，不提前或批量重命名其他工位。已有上下文里的 CLI 契约有效时不重复查询整套帮助。
3. 第一条工作消息按三段式一并交代身份、具体任务和成功标准：有岗位手册就给实际绝对路径并要求先读；没有匹配岗位则按[临时职责约定](../../../../roles/README.md#临时职责与交付)直接写职责，不虚构路径。不增加“初始化 → 等待派单 → 再发送同一背景”的空转回合。
4. 发送一次后等待、回收完整结果。结果不明时检查该实例，不自动重发或重新启动。完成后保留工位，只有用户明确要求才关闭。
5. 负责人按约定核对交付。用户要求原样展示时，不修改代理结果，负责人判断单独说明；不能因终端截断而把部分输出当完整结果。

### 需要持久协作时才使用台账

用户要求长期项目组、跨会话恢复、成员复用与任务历史，或正在继续已有台账任务时，进入[岗位运行与恢复入口](../../../execution-profiles/role-runtime.md)。它是可选的持久协作流程，不是普通委派的前置条件；不要仅因选了岗位就建立项目组。当前台账 CLI 仍使用结构化输入，不宣称已自动从自然语言生成记录。

### 输出只展示工作状态

正常进展用一句话说明谁负责什么、是否完成、是否阻塞。实例名、会话路径、pane/Tab ID、启动尝试等用于内部定位，不在正文复制完整 JSON；只在排障或用户索要时展开。工具返回 JSON 时仅提取下一步必要的字段，不再查询 members/group-show 重复打印成功回执已有的信息。材料路径与交付物链接仍保留真实位置。

`blocked` 不视为完成。出现 blocked、unknown、超时或启动失败时，读取该实例状态和最近输出；只有确需用户决策或高风险授权时才打断用户。子 Agent 的完成声明不是证据；涉及代码集成时，主 Agent 运行直接受影响的最小验证。

## 完成标准

- 每个委派任务都有独立产物或结论及验证输出。
- 并行任务没有未处理的写冲突。
- 主 Agent 已核对约定的结果和证据；有代码变更时检查本次 diff 并完成相关最小验证，只读分析核对内容完整性与材料依据。
- 没有因 YOLO 绕过生产、凭证、发布或破坏性操作的授权边界。
