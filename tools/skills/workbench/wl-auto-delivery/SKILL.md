# 自动交付（wl-auto-delivery）

以本次目标和已有证据选择**唯一当前阶段**，完成后再判断下一阶段；不把阶段名当完成证据。各环节均可独立使用，不依赖总流程私有文件或新流程引擎。

| 阶段 | 进入条件 → 完成证据 | 最小能力 |
| --- | --- | --- |
| Observe / 观察 | 只想了解事实 → 可追溯事实与局限，可在此结束 | 项目阅读、诊断、调研 |
| Confirm / 确认 | 目标/边界/预期未稳定 → 人确认需求+用例及执行约定 | wl-req-confirm、wl-qa-test-planner |
| Design / 设计 | 需求稳定但做法未定 → 本版方案可执行决策及证据 | wl-design-doc |
| Execute / 执行 | 目标、做法与授权明确 → 实际diff、行为测试与版本 | wl-ticket-run、项目开发能力 |
| Verify / 验证 | 已有实现 → 聚焦Review后目标环境逐条用例结果 | wl-requesting-code-review、wl-web-auto、项目测试能力 |
| Learn / 沉淀 | 已验证且值得长期复用 → 按工作台归宿保存 | EXTENDING.md |

阶段冲突时：用户指定 → 已确认文档/任务状态 → 本次目标 → 只问一个会改变阶段的问题。简单明确任务可直接执行，Bug 内部先复现再修复；提交/发布另需授权，不因为到达 Execute 自动获准。

## 主链与唯一正文

```text
需求：目标/范围/规则/新旧差异
  → 按业务分组的测试用例（唯一具体数据/操作/预期正文）
  → 正式用例基线一次独立审查 → 人确认需求+用例+执行约定
  → 明确推荐方案及理由 → 本版决策生效
  → 按行为TDD开发 → 聚焦Review → 约定环境逐条验收
  → 失败/阻塞回修 → 新运行复测 → 留存摘要与外部证据
```

- 最小产物交接：用例正文默认 `test-cases.wl-qa-test-planner.md`，调用方负责生成同源 `test-cases.wl-qa-test-planner.html` 阅读页，按 A/B 业务分组、同步版本。需求 HTML 的整体相对链接指向实际存在的用例 HTML，不强迫逐条双向链接；用例 Trace 仍需有依据。历史名称沿实际文件，旧 AC 原位兼容，不迁移、不复制双正文。单独调用 QA 仍只产出 Markdown 与缺口，不以 HTML 生成为前置；完整规则见 [产物交接](references/execution-and-evidence.md)。
- 正式用例按 [独立用例审查](references/test-case-review.md) 执行。先审查再人确认；审查不可用时记阻塞，不拿自检冒充独立结论。
- Grill 或讨论确定的业务结论回写需求规则，再检查受影响用例；未知预期保留 Q，禁止 Agent 代定。用例变化返回受影响范围审查和确认，不重审无关用例。
- 范围/规则变更回到需求；实现路径变更回到方案；环境阻断留在执行约定，不静默换环境或降低通过标准。版本变动需检查审查/批准是否仍覆盖本版。

## 两种方案决策方式

默认 **manual**：Agent 给出一个有依据的明确推荐、理由与代价，用户确认本版方案及范围后才可实施，不为形式制造多方案。

只有用户**明确委托采用推荐方案**才用 **delegated**：记录委托原话/位置、适用的需求和方案版本、范围、数据、成本及操作授权边界，再核对关键假设证据。合法委托允许在边界内自动采用推荐并继续；沉默、需求批准、旧版批准均不等于委托。采用结果用 `status: adopted` 和独立 `delegation_evidence`，不得伪造人工 `approved` / `approval_evidence`。元信息细则与工单入口由 wl-design-doc / wl-ticket-run 共同约束。

重大不可逆变化、范围/数据/成本/授权越界或关键假设无证据时停止，返回确认；方案决策不授予提交、发布、生产或真实写入权限。

## 能力选择与恢复交接

- 写业务文档/代码前核对目标目录和分支、实际 Worktree 及已有改动；不因当前 cwd 正好可写就选它。
- `wl-git-flow` 只在创建/复用需求 Worktree、集成、记录环境结果或回收时按需加载；纯读取/写文档不因此强制走 Git Flow。只导航，不复制其分支/授权专业规则。
- compass 本地验收调用 `wl-compass-local-test`；其他项目读取自身 README/构建配置的启动方式，不套 compass，也不默认启动服务。
- API/数据库核验只按用例需要选择现有能力：非生产查项目约定与海管家 `fuxi.md` 入口，生产数据库走 `wl-prod-db`，生产 API 走项目已授权生产入口；先核对目标环境，不混用入口。默认只读，不默许写；写操作另需具体环境/数据/动作授权，专业细则按对应入口执行，不在此复制。
- 用项目已有 `progress.md` 作为轻量恢复记录：实际产物路径/版本、确认范围及证据、当前阶段、未决项/下一步、run 链接。切换会话时先核对文件/分支/版本与记录一致，缺项就补证或停在对应阶段，不据旧摘要自动认定批准或通过；不造流程 DB。最小格式见 [环境与证据](references/execution-and-evidence.md)。

## 执行和验收约定

- 人确认需求+用例时一并确认环境、URL、角色、前后端版本/分支和可写数据/操作。无设置时公司业务推荐 Dev，私人项目推荐本地，均随本次确认确定；生产永不默认。
- 执行前重新核对基线和授权。版本不符、入口不可用或未授权写入则阻塞；本地自测不能冒充 Dev/Beta 验收。
- 默认一个持续负责人，不强制多 Agent、/goal 或 /list。正式用例独立审查以外，只有实际验证/专业缺口才增加角色；只通过 Herdr 启动 Pi，thinking=high。不可用或不能确认 high 时说明阻塞，不降级、不冒充独立完成。
- 开发后显式调用 wl-requesting-code-review 的 **focused-delivery** 模式，只报本版 diff 及必要直接依赖上的设计偏离和具体交付阻断问题；建议可省略，不做泛化改进审查。Review 在业务验收之前，不全库回归、不无限扩审。
- 实际测试的目录、进度、问题与中断恢复统一遵守 [测试执行记录约定](../../../execution-profiles/test-execution.md)；[环境与证据](references/execution-and-evidence.md)仅补充交付及保留边界。结果按轮次追加，progress只链接结果，缺陷和原失败不覆盖，不改预期凑通过。
- **done 门槛**：约定目标环境中所有适用用例必须通过；不适用须依据并由已确认范围/规则支撑，不能临时改为不适用来绕过失败。失败/阻塞/未执行不算完成，也不能由 Agent 自己接受；有缺口保持未完成，交人明确处理范围变化并更新需求/用例基线后重新判断。目标环境通过不等于发布，发布成功、需求关闭及清理资格分别核对。

## 交付与停止

交付实际修改、版本、命令/操作与结果、用例运行链接、未覆盖项和残余风险；静态检查不能冒充真实项目或网页 E2E。需求实现、所有适用用例通过且有依据的不适用已记录、直接链最小验证完成、无阻断后才可 done 并停止，不为流程形式增加检查；有失败/阻塞/未执行时只交付真实进度与缺口，不声称完成。新总流程未完成真实项目验证前 `verified` 留空。

修改本流程后按 [回归场景](references/regression-scenarios.md) 推演；文案断言只保护结构，不代表语义或端到端验收。
