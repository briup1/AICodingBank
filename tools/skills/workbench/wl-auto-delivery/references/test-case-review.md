# 正式用例基线的独立审查

本标准也可用于单独请求用例审查，不要求使用总流程。生成器自检不等于独立审查；正式基线由不同会话审阅真实需求和用例，留下范围、版本及结论。

输入：需求正文及确认状态/版本、原始材料索引、按业务分组的用例及版本、直接回归依据、未决 Q、目标环境与授权限制。只审本需求及直接影响链，不补全全系统测试。

```text
需求 → 用例：目标/规则/差异是否漏测？
用例 → 依据：Trace 能否定位已确认规则或必要直接回归？是否越界？
适用条件 → 操作/数据/逐步预期：能否在约定环境执行并判定？
相同触发+动作+预期 → 合并或参数化，保留有意义的角色/状态差异
```

- 按业务 A/B 等部分检查正常、异常、边界、权限和状态变化；每类先判断适用性，不适用说明原因，不按清单强凑场景。
- 每条核对前置状态、角色、具体数据、步骤、可观察预期和必要禁止副作用；环境/数据不可得时标阻塞或未执行，不能猜期望。
- 核对范围双向成立即可，不要求需求 HTML 对每条 TC 建反向链接。旧 AC 可以是现有依据，不要求再抄一遍。
- 输出分为：阻断项（遗漏/越界/未知预期/不可执行）、相关建议、需求外观察。每项指向需求/用例 ID、版本、证据、影响及最小修订；证据不足写“待补证，不能判定通过”。
- 审查不替人批准业务规则、不实际操作业务系统、不改变通过标准。正式基线审查完成后交人确认需求+用例+环境/操作约定。

结论格式：审查者实际身份与会话、需求/用例版本、范围、通过/需修改/阻塞、发现与证据、未覆盖项。总流程负责真实调度；经 Herdr Pi high 不可用时停止需要独立结论的交接，不伪造审查记录。

变更回流：Grill/讨论结论先回写需求 → 定位受影响用例 → 修订/补证 → 独立复核变化部分 → 人确认新基线；纯文字不改变规则时记录理由，不重跑无关审查。
