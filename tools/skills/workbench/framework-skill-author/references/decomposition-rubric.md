# Skill Pack 拆分准则

## 拆分单位

按“用户任务 + 独立决策过程”拆分，不按文档页、类名、模块名或导航栏目拆分。

候选 Skill 需要同时满足：

1. 有可识别的用户触发语句。
2. 与相邻 Skill 存在清晰边界。
3. 包含至少一个非显然的技术决策或不变量。
4. 单独加载即可改善一个真实任务。
5. 有足够官方来源支撑。

## 评分表

每项 0～2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 独立意图 | 无独立请求 | 偶尔独立 | 经常独立出现 |
| 决策密度 | 只是事实 | 少量选择 | 多个关键权衡 |
| 边界清晰度 | 高度重叠 | 可人工区分 | description 可准确区分 |
| 任务完整度 | 不能独立完成 | 仅辅助步骤 | 能支撑端到端子任务 |
| 来源成熟度 | 缺少官方依据 | 零散官方资料 | 官方指南/API/示例完整 |
| 变化节奏 | 内容极易过时 | 部分易变 | 核心规则稳定 |

建议：

- 10～12 分：独立 Skill。
- 7～9 分：优先并入相邻 Skill 或作为 reference。
- 0～6 分：不生成，交给 docs Skill 实时查询。

## 推荐的基础 Pack

多数框架可从以下角色中选择，不要求全部生成：

```text
FRAMEWORK-getting-started
  选型、架构边界、初始化和最小闭环

FRAMEWORK-CAPABILITY
  一个具有独立决策流程的核心能力域

FRAMEWORK-integration
  与外部运行时、协议或生态集成

FRAMEWORK-production
  权限、持久化、部署、观测和可靠性

FRAMEWORK-debugging
  具有框架特有证据链的排障

FRAMEWORK-docs
  最新 API、长尾问题和版本核验
```

## 合并信号

出现以下情况应合并：

- 两个 description 可以互换。
- 一个 Skill 总是作为另一个 Skill 的固定步骤出现。
- 两者共享大部分决策、来源和验证方法。
- 拆开后每个 Skill 都需要读取对方才能完成任务。

## 拆分信号

出现以下情况可拆分：

- 用户会独立提出该类任务。
- 技术风险、权限或验证方式明显不同。
- 所需 references 很大且通常无需同时加载。
- 版本节奏不同，例如稳定核心与实验性接口。
- 面向不同角色，例如应用开发者与框架贡献者。

## description 设计

description 应回答：

```text
做什么？
何时使用？
与最可能混淆的 Skill 有什么边界？
```

避免：

- “处理所有 FRAMEWORK 相关问题”。
- 罗列几十个 API 名称。
- 使用“最佳实践”等没有可识别意图的宽泛描述。
- 通过大量否定条件弥补本身边界不清。

## 重叠审查

为每个 Skill 至少写：

- 2 个应触发请求。
- 2 个不应触发请求。
- 1 个容易与相邻 Skill 混淆的请求及正确路由。

如果无法稳定路由，先调整拆分或 description，再写正文。
