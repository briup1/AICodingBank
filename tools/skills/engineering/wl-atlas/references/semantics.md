# 语义与确认指引

## 从一个操作说清目标

例：虚构借书站中，成员提交申请 → 管理员交书 → 管理员记归还。只有申请代码，没有归还记录，不能说借还闭环已完成；负责人选择登记册，不代表必须造一个归还页面，也不证明登记册已执行有效。

先画理想职责和协作，再拿证据标注现状。规划中的模块允许未完成；现存但不在近期扩建范围的能力仍保留。模块可重命名/拆并，不能因此丢掉能力语义。

## 先盘点存量，再判断扩建

地图覆盖目标与现状，不只是近期新增清单。沿项目公开入口、执行调度、人工确认和资源用量归属等实际资料盘点已有职责：网页、程序接口、命令行等有哪些入口，如何接收/安排任务，谁确认动作，消耗归到谁。这里只提示调查方向，不要求每项目都具备这些能力。当前不新增渠道，不等于删去已有命令行或接口；主链标题和动作连接也不能代替模块内独立能力的定义、现状与决定。

近期不建设的可选领域，仍要保留原目标范围里明确列出的具体职责及未决项，写清成立条件与取舍。例如资料中有受控发布、来源到下游的血缘追踪、质量异常与处理责任，不能只剩一个“数据治理”总称。按来源逐义覆盖或合理拆并，不因为不扩建就省略，也不因列在图中就升级为必建。未决项不能被同模块其他方向的“不做”覆盖。

## 定义核对对象、动作、结果

每项先从来源确认：对什么对象，做什么动作，得到什么结果，再判断能否合并或等价替换；名称相同或关键词相近不构成等价。三者任一改变，都要保留原职责并单独核实新方向，不擅自抬高目标。

- 按问题自动选择产品，处理的是用户问题和产品选择；网关按新版或地区分流，处理的是请求流量和服务实例。两者不能因都有“路由”就合并或互相继承决定。
- 来源可以核对，目标是能查到答案依据；统一引用界面是可能的展示增强。不得用尚未决定的新界面替换已有可追溯职责，也不把没有统一 UI 判作原职责未完成。
- 虚构借书站中，“按书号查到登记记录”不等于“新建统一查询面板”；沿用登记册可保留原查询能力，不能凭想象新增面板并据此提高目标。

## 按模块成立条件查漏，不把查漏单变成建设单

先确认本项目为何需要或暂不需要该模块，再沿资料和实现核对以下方向；不适用就说明原因，缺证就保留未核实。它们是调查问题，不是默认必做能力：

- 生命周期：如何进入、更新、生效、撤回和删除？旧副本、缓存或索引怎样失效？例如虚构借书站删掉目录中的旧书后，搜索结果是否还会显示它。
- 权限与安全：谁能读写，谁在执行时检查，模型服务凭据和部署密钥分别由谁保护？身份核验不能代替业务授权。
- 失败与质量：失败怎样可见、重试或恢复？数据何时可发布给下游，质量未达标会不会被当成正式数据？质量检查、优化和失败处理不能被一个“接入”词吞掉。
- 责任与影响：谁维护来源、规则、权限或共享能力，修改影响谁，管理操作是否留痕？局部资料管理不能冒充全组织数据治理。
- 未决方向：接入分流、版本路由等若在目标资料中出现，保留其独立取舍；已有明确不做的邻近功能不能替它作决定。

合并前列出来源中的重要语义；合并后逐义映射到能力 ID 及具体字段，标为已覆盖、待核实或不适用及理由。只写“资料管理”“运行管理”“密钥管理”而不说明更新删除、操作记录或各自凭据边界，不算覆盖。若语义需要不同条件、状态或决定，拆成能力；禁止靠条目数量相同判定无遗漏。此映射可写在本轮获准的审核记录，不向通用 Skill 填项目事实。

## 三个独立维度

| 维度 | 含义 | 防误判 |
| --- | --- | --- |
| 必要 | 不具备就不能兑现本项目当前明确职责 | 写明为何必须，不靠行业模板或代码存在判断 |
| 条件必要 | 某类产品/数据/环境/可选模块成立后才必须 | 条件独立保存，摘要、表与详情都保留；当前条件不成立仍可展示未来边界 |
| 扩展 | 不做仍能完成当前核心目标 | 已确认建设的扩展仍是扩展，不自动升为全局必要 |
| 已完成 | 有依据表明已定义目标范围内的开发已完成 | 不等于本轮复测或全场景验收通过；测试限制另记 |
| 部分完成 | 有实现基础，但缺目标行为或有直接证据表明目标尚未达成 | 指出具体行为差距，不能仅因本轮没重跑而降级 |
| 未完成 | 已核对范围，目标能力尚未交付 | 不能只因没找到文件就断言完全没有 |
| 尚未核实 | 现有资料不足以判断目标行为是否已实现，或直接证据互相冲突尚未查清 | 说明缺哪段实现依据，不把本轮未复测当成实现未知 |
| 沿用现有 | 选择现有能力、人工流程或外部服务 | 即使方式选定仍可尚未核实/部分完成 |
| 已确认要做 | 负责人明确选择建设或补齐 | 列采用方式及尚待确认细节，不扩大成完整平台 |
| 当前不做 | 有明确的不建设决定 | 写条件变化后重议；不代表永久放弃、关闭保护或删除存量 |
| 尚未决定 | 负责人没有明确选择 | 不以进度、默认推荐或相邻能力决定代选 |

必要性理由必须回答“缺少它会使本项目哪项职责无法兑现，以及何时成立”。“已确认建设”“负责人选择人工方式”“已经开发”都不是职责依据，禁止从 decision 反推 necessity；选择建设的扩展仍可为扩展。查询结果引用、人工反馈等按实际职责判断，不能只因被采用就升级为必要。

实现状态评价的是已定义目标范围内的开发完成情况；验证范围独立保留在 current/evidence。本轮没运行、没重验所有格式或没覆盖全部组合，本身都不构成降级理由；既有实现与历史依据仍须按其证明范围判断。反之，只看到函数名或一句“已有实现”也不足以自动判完成，须沿入口与目标行为核对。禁止为纠正降级而批量刷成已完成。

例：借书站的文件导入入口、处理链与既有记录足以表明目标格式已支持，本轮没有重测所有格式，仍可写已完成，并注明未复测；若目标格式尚缺解析逻辑则部分完成，若处理入口是否连通无据可查则尚未核实。若能力的明确目标本身是证明效果、实际恢复演练或交付评估，缺少该目标所要求的验证结果可构成真实差距，须指出目标条款，而非泛称“缺验证”。

允许状态与决定任意合法组合：已完成＋当前不做可能意指保留基础但不扩建；部分完成＋沿用现有须写明目标行为差距（含目标本身要求而尚缺的验证）；未完成＋当前不做不是待办。必须在采用方式解释清楚，避免表面冲突。

## 划分与追问

- 两方向状态/决定不同就拆开；共同定义可以简短，不能把不同取舍塞进一个标签。无须为每个小实现细节再建模块。
- 必要模块、条件必要模块、扩展模块各自从目标推导。可选模块内的必需能力必须显式带“决定建设该模块时”的条件，不冒充全局必要。
- 只对范围、数据或风险的真实缺口提问。示例：“社团现在只用网页，提醒先人工联系还是建设自动消息？”不要一次抛一大张术语矩阵。
- 确认后检查原决定是否被覆盖：更新能力采用方式、边界、问题列表；不同方向未被明确覆盖的决定不能擅自推断。
- 限制和授权保留原意，例如“暂不做提醒”不代表删除已有联系人，“使用外部服务”不代表外部身份自动获得本地记录访问权。

## 人工采用方式不抹掉补齐决定

复用人工入口只说明怎么做，不说明质量已够或没有剩余工作。沿用人工测试，与补齐交付评估、形成开放判断依据可以同时成立。先分别核对已有入口、已确认补齐内容及验收缺口；取舍不同时分为相关能力并各自给依据，不把质量补齐项统统改为沿用现有，也不把它扩大成新建整套平台。

虚构借书站中，管理员继续人工交接，不代表“开放目录前核对库存”这个已确认补齐步骤被取消。可以保留人工交接为沿用现有，把交付前核对单列为已确认要做；两者必要性仍各从职责推导。

## 白话操作结果在前

能力名称、定义、用途与关系动作先讲谁做什么、用户看到什么结果或避免什么问题。技术名只在白话之后的括号或依据中出现，不让读者先学源码。例如写“任务按接收顺序等待执行（FIFO）”，不写“FIFO 调度”；写“确认进程可接收新任务（ready）”，不以状态变量替代效果。清单文件（manifest）、执行权的有效期限（lease）也先解释含义。不要仅把术语改成中文音译。

## 证据写法

每项提供可定位来源与短结论，不复制会话或大段源码。路径用目标项目可追溯的相对位置、符号、需求编号或测试记录日期；不把凭证或私人主机路径放进可共享报告。依据有冲突时写明冲突，先保留未知或局部状态。

- 目标/决定：负责人明确选择、批准文档条目；不把作者建议写成已确认。
- 实现：入口与关键调用、数据归属、异常路径；有定义不保证入口已连通。
- 验证：命令、样本、环境与结果位置；只记录真正执行的范围。未跑或条件不足保留未覆盖。
- 未核实：给出本轮核对资料与实现缺证项；例如“只有需求描述，入口是否接通及处理逻辑尚无依据”，不把缺本轮执行记录等同于实现未知，不伪造测试编号。
