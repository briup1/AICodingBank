# 内容源格式

使用 UTF-8 JSON。以 `assets/example.json` 为完整、虚构的小例子。渲染器只依赖 Python 3.9+ 标准库；不执行数据中的代码，不解释 Markdown 或 HTML，也不主动打开证据链接。相同字段维护一份，所有展示从该源派生。

## 顶层字段（全部必填，不接受未知字段）

| 字段 | 格式与用途 |
| --- | --- |
| title/date | 非空文本；日期说明实际内容基线，不用报告生成时间冒充事实新鲜度 |
| goal | 非空文本；这个项目为谁解决什么问题 |
| scope | 非空文本；当前范围及与外部系统的职责界限 |
| workflows | 至少一项 `{name, steps}`；steps 为至少两条非空动作文本；开发交付与用户使用不同时通常各写一条 |
| modules | 至少一个模块，定义见下 |
| externals | 外部系统数组；没有时为 `[]` |
| relations | 关系数组；单一模块可为空，多节点必须全部参与至少一条关系 |
| boundaries | 至少一条非空文本；近期范围、未来触发条件、明确不做与权限限制 |
| questions | 非空文本数组；没有待确认项时为 `[]`，不能把问题删掉假装已决定 |

## 模块

`{id, name, responsibility, necessity, placement, capabilities}`。

- `id`：全报告唯一，小写字母开头，仅字母数字与连字符。能力/外部系统也使用同一唯一性检查；ID 不承担业务含义。
- `name/responsibility`：非空文本；模块叫什么、负责什么。
- `necessity`：见下；不接受单独“必要模块”标签而无理由。
- `placement`：`main` 主链模块、`branch` 按需子卡、`independent` 独立数据或辅助链、`support` 贯穿式支撑。主链通过关系排序，子卡由按需关系挂到真实主链节点下方；卡片自身就是两层折叠内容，不再生成另一个节点目录。独立与支撑分别分组，关系行明确标为补充而非顺序连线。没有固定模块数。
- `capabilities`：至少一项能力。可选/条件模块内能力不能写无条件“必要”；写条件必要并说明触发条件，或写扩展。

## 能力

`{id, name, definition, purpose, necessity, status, current, decision, approach, evidence}`。

- `definition`：完整但简短地说明“是什么”，在详情中展示。
- `purpose`：一句白话说明用途，在表格和详情中复用，不重复抄定义。
- `status`：`已完成 / 部分完成 / 未完成 / 尚未核实`，表示已定义目标范围内的开发完成情况，不表示本轮测试执行情况。不因未复测/未覆盖全部组合降级，也不因一句“已有实现”直接判完成；依据及目标行为差距按语义指引核对。目标本身要求证明效果或实际演练时，其结果缺失可为差距。
- `current`：非空文本，写已有基础、限制与差距；不要只重复 status。
- `decision`：`沿用现有 / 已确认要做 / 当前不做 / 尚未决定`，与 status 没有自动联动。
- `approach`：非空文本，写采用方式、保留什么、不扩建什么；未决定就写真实缺口。
- `evidence`：至少一项 `{source, finding}`，均为非空文本；source 为路径/符号/记录位置，finding 为证明范围与缺口。尚未核实时也写查过什么和未证实部分。证据仅在详情展示。

## 必要性对象

`{kind, reason, condition}`。

- `kind` 只能是 `必要 / 条件必要 / 扩展`。
- `reason` 必须为非空文本，说明相对项目职责为何这样判断。
- `condition`：kind 为条件必要时必须是非空文本，否则必须为空字符串。渲染器在条件必要标签后完整显示此条件，再显示 reason，不截取成无条件必要。

## 外部系统与关系

- 外部系统：`{id, name, responsibility}`。被主链直接按需调用的外部系统作为该节点下的虚线边框子卡，不统一放到末尾；不计本项目模块与能力。只参与数据/支撑补充关系的外部系统另列并明确提示查看关系行。实际属于本项目的能力不能塞入外部卡逃过差距分析。
- 关系：`{from, to, kind, action}`。from/to 引用模块或外部系统 ID，不引用能力；kind 为 `主链 / 按需 / 数据 / 支撑`；action 写清从谁到谁做什么及适用条件。
- `主链`：两端必须是 main，全部 main 通过该类关系连成单条有向线；按边排序后用垂直动作箭头连接相邻卡，不按模块数组猜顺序。禁止多入/分叉/循环/断裂。
- `按需`：仅支持 main → branch/外部系统，每个 branch 必须恰有一个主链父节点，外部系统最多一个按需父节点。渲染真实父节点下方的虚线分支、动作和目标卡，修改 from 会移动卡片，修改 to 会改变该分支的卡片。子卡并列且按关系数组顺序阅读，窄屏为单列，不使用坐标图或横向大画布。
- 不支持多层子卡、共享调用节点的多入或循环；显式失败，不复制卡片、不丢边、不伪造层次。先核对是否混入了请求返回方向或错误职责粒度；若确属复杂拓扑，说明当前模板不支持并请负责人选择其他表达，不能为通过校验篡改事实。
- `支撑`：必须从 support 指向具体受支撑节点，support 不可参与其他关系。`数据`：至少一端是 independent，表示独立供数/加工，普通请求内部传递写进主链/按需动作。两类仅输出标明类型、from/to 和动作的可见关系行，不模拟跨卡全连线，可有多个作用对象；这不是调用拓扑的替代入口，也不承诺推导先后或检查其业务环路。

## 写入与失败

`--check` 只做字段/条件/引用/唯一性等结构检查，不能判断业务决定是否真实。空模块、重复 ID/JSON 键、未知状态、缺字段、无效关系、条件缺失、字段错型均显式失败并指出位置；不静默补默认、不跳过坏项。报告存在时拒绝覆盖；修改数据后选新候选文件名。脚本不更新 README、不修改输入，也不创建目录。
