# 事实、设计与证据写法

方案正文中每个关键结论使用以下身份之一：

| 身份 | 含义 | 写法要求 |
|---|---|---|
| 当前事实 | 当前代码、获准运行结果或明确材料已经证明 | 写基线、证据位置和局限；不能把静态代码说成线上运行 |
| 设计目标 | 需求批准后希望实现的行为 | 标为目标，不写成已经存在 |
| 推荐方案 | 为达到目标提出的实现方式 | 说明改哪里、怎么改、为什么，不能代替用户批准 |
| 规则推导 | 由已确认目标和事实直接推导出的结果 | 标为推导，给出最小例子 |
| 待确认 | 证据不足或有多个合理结果 | 写缺什么、影响什么；不猜字段、表、接口或状态 |
| 验证结果 | 本轮实际执行过的检查 | 写命令/操作、基线、结果和未覆盖项；不把验收场景列表写成通过 |

## 就近证据

- 场景当前事实后面放最小证据定位，详细行号和命令可折叠。
- 证据至少包含来源类型、版本/环境和局限；历史截图、代码可达、目标示意不能互相替代。
- 没有证据的技术关系写“待核验”，不通过模块名或经验补齐调用链。
- 同一证据被多个场景复用时，正文保留各场景的结论，详细证据可统一折叠，不重复整段。
