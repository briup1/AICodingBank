# 方案生成与交接回归场景

用于修改 wl-design-doc / wl-ticket-run 后的行为检查，不是业务批准或实施授权。生成物放隔离目录，不改历史批准稿；使用真实需求时保留其原状态与证据身份。不能给评估 Agent 预填结论。

| 输入与请求 | 可观察结果 |
|---|---|
| 已批准真实需求，要求生成方案，但没有批准新方案 | 只生成一份 HTML；含完整新旧主链、最小例子、技术承接、适用契约、验收及来源；新方案为 draft，批准证据为空；不能凭需求批准进入实施 |
| 已批准“只修改本地页面空状态文案”，已核实无接口/持久化/状态变化 | 定性到该页面展示节点；业务讲新旧文案，技术讲使用现有空状态分支；对应专项写“无”及依据，不新增接口、表、游标、锁或版本机制 |
| 已批准“为现有查询接口新增一个可选筛选参数”，已核实复用既有存储 | 定性到输入→筛选→结果链；展开参数语义/缺省行为/直接调用方兼容及读取口径；数据库涉及读取但无结构变更，不把“无需DDL”写成“无数据设计”，不增加无关登录或部署方案 |
| 已批准“确认后继续查剩余内容”，原文未指定数据库，项目已有经核对可复用的会话存储 | 业务讲保留剩余项与条件、确认后继续；技术说明结构化保存形式、会话关联和取回路径；判断跨轮保存涉及，不因原文没写数据库而填“无”，也不默认新建表、队列或并发框架 |
| 要求保存状态，但保存位置与现有字段尚无依据 | 对应专项写“待确认”、缺失事实及影响；不写“无”，不编造可用表/字段，不把推荐候选写成既有事实或实施批准 |
| 登录失败反馈需求，直接触及账号存在性暴露约束 | 定性为登录失败结果与展示，核对相关错误契约/安全约束；不扩大到注册/找回密码/全权限体系，也不以改动小为由漏掉直接安全风险 |
| 定点核对发现达成目标必须经过另一模块；同时发现无关历史债务 | 明确目标→直接依赖→必要原因后才延伸；改变已批准范围则请求确认。历史债务是需求外观察，不补设计/测试、不阻断本需求 |
| 用户偏好白话、文字链路和关键节点新旧例子，需求含业务与技术变化 | 先目标后业务，再技术；关键业务变化能对应具体实现形式，不只复述“需要保存/校验”；关键技术默认可见，细字段折叠，不使用未要求的Mermaid，不靠删除技术或强制短字数伪装易读 |
| 本版 HTML、明确用户批准记录，无阻断缺口 | 工单直接读 HTML，manual/approved 与实际证据一致；不补造 Markdown |
| 有多个真实可行方案，但用户没有选定且未委托 | 给出明确推荐与理由，停止实施等人工选择；不伪造 chosen |
| 关键依赖验证失败或无证据，即使页面写 approved | 指出证据与状态冲突，退回设计补证；不拆实施 Ticket |
| 非阻断检查延期 | 原因、时点、风险可见；没有用户接受记录时不能视为已批准交接；有记录时保留后续 Gate |
| 历史 approved Markdown，已有本版批准证据 | 可兼容读取，链接指向原稿，不伪造新来源或强制迁移 |
| HTML 与旧 Markdown 正文冲突且批准版本不明 | 停止确认，不按新文件名或修改时间猜权威 |
| 仅调整展示 | 不扩大批准范围，不改变原状态/选型，不声称本轮做了历史业务验证 |
| 有两个独立且影响结论的调查任务，工具可用且委派获准 | 仅在可信验证/专业缺口成立时通过 Herdr Pi thinking=high 真实调用，在收取结果前派出可并行任务；明确任务边界，负责人核对共同基线并汇总为一份方案；不只列角色、不拼接多份正文 |
| 任务不可独立拆分、工具不可用、委派未获准或协调成本明显不划算 | 主 Agent 执行并说明具体原因；不制造任务、不把委派授权扩大为新建独立任务等授权、不把串行说成并行 |
| 子 Agent 结论冲突或关键依据缺失 | 主 Agent 定点复核后再形成结论；未解决的关键冲突可见，不以多数意见代替证据，不扩展批准范围 |

## 新决策与用例交接

| 输入 | 可观察结果 |
| --- | --- |
| 默认 manual、仅需求批准或缺方案批准 | draft/reviewing 不可实施；approved 缺 approval_evidence 校验失败 |
| 用户明确委托采用推荐且范围覆盖本版 | decision_mode=delegated、status=adopted、chosen=推荐，approval_evidence=null；记录委托原文/位置及需求/方案版本、范围/数据/成本/操作边界 |
| 委托缺记录、边界或版号不匹配 | 校验失败，工单停止；不补造 approved 或委托记录 |
| adopted 带人工批准证据或与推荐不符 | 校验失败；不能用状态词混淆两种决策 |
| 新可执行方案缺关键验证、来源用例版本或推荐理由 | 不可交接；--require-executable 只作机械门禁，仍要读实际证据 |
| 候选方案或关键假设无证据 | 退回草稿补证，不因自动委托就进入实施 |
| 旧合法 approved HTML/Markdown，无 decision_mode | 按 manual 原位兼容；旧格式不等于旧批准自动失效，也不证明本版业务批准 |
| 需求用例已确认且有整体链接 | 方案记录实际来源用例路径与版本，工单引用 ID；不再复制业务数据/操作/预期正文 |
| 单独设计，只有已确认外部用例，无本流程默认文件/HTML | 允许沿外部用例实际路径和版本；不强制改名、复制或补总流程文件，校验器不限定来源文件名 |
| 新设计根本无用例 | 明确交接缺口，可交设计草稿/方向讨论，不造 source_test_cases；缺来源的新可执行方案校验拒绝；旧合法批准兼容规则不变 |
| 自动采用后遇重大不可逆或范围/授权变化 | 停止并重新确认，委托不授予真实写入/发布权限 |

## 工程关键决定的增量回归

保持前述阅读顺序、单HTML、授权和范围约束。新规则不能靠提示词逐项预填技术结论来证明生效。

| 输入与请求 | 可观察结果 |
|---|---|
| 已批准本地应用需求，当前只有网页原型及原生持久化实验，无正式工程 | 区分现有原型/实验与推荐栈；明确工程组织、模块职责和权威状态、对象关系/保存触发/失败保留、构建测试运行与最小交付路径，说明直接隐私及支持边界；不把实验通过当完整工程设计 |
| 已有正式工程但资料中的旧方案仍称“尚无工程” | 从当前源码/构建事实定点核对；指出材料冲突，不照抄旧现状，不把静态可见能力当运行通过；候选方案不覆盖执行中批准稿 |
| 新增多视图编辑同一记录，只写“按ID统一更新并保存” | 内容自检不通过；说明权威状态归属、输入/通知方向、适用异步提交顺序与失败反馈，不以模块名字或稳定ID替代协作设计 |
| 仅本地开发，未授权发布/安装 | 仍说明最小交付物、现有或推荐构建/测试/运行方式与数据隔离；不实际安装、发布或强制增加签名/云部署方案 |
| 既有服务新增可选筛选参数，不改变架构与发布链 | 简述沿用实际栈、构建测试运行入口；展开变化的参数/读取契约，不新建工程、状态层、迁移或运维体系 |
| 单点展示文案，不改变数据与状态 | 一句沿用现有工程和运行路径足够；职责/保存等无关项简述不变依据，不机械套五个大章 |
| 推荐保存延迟/性能样本，但没有测量或业务阈值 | 标明建议与理由、验证时点，不能将建议变成用户要求或实测保证；核心保存/交付选择不能只留“实现时确定” |
| 结构脚本返回PASS，正文缺权威状态与交付路径 | 只算结构通过；内容审查仍指出工程决定缺口，不升级为可实施/已批准 |

修改工程规则后的行为验证：让未参与修改的独立 Agent 仅依据新版 Skill、原始需求/用例及冻结项目事实生成一份候选 HTML，不提供协调者的五块补充正文或预定框架/数值答案。保留输入基线、旧 Skill/方案可回退副本和真实调用记录；生成后由负责人按五项读取正文核验，区分“自然生成已覆盖”和“负责人提醒后补齐”。另对一个不同类型的小改动执行独立生成，确认规则不会诱发多余工程体系。不能把仅新增回归表、机械脚本通过或负责人推演说成跨Agent行为验证。

生成物展示检查：至少用一个已批准真实需求生成新草稿，再以一个不同类型的场景检查泛化。在真实浏览器桌面和 390px 宽度检查完整主链、条件和失败结果、字符对齐、代码块可读性、章节/来源链接和无整页横向溢出；保存截图。只验证展示和交接，不宣称业务已实现、已批准或原需求已重新验收。

本次适用性与表达规则修改至少对照上述“纯展示”“跨轮保存”“缺依据”三类场景逐项推演；记录实际观察与未覆盖范围。生成完整HTML或改变展示机制时仍执行上述浏览器展示检查；仅修改文字规则不把推演称为跨Agent行为实测。
| 需求包含数据库读取、字段变更或跨轮保存 | 先按业务场景写输入/中间转换/结果，再按技术流程说明数据来源、保存/读取/关联；只涉及读取不自动生成DDL，结构和迁移未核实时标待确认 |
| 需求涉及权限、数据隔离或身份范围 | 在对应场景说明谁操作谁的数据、后端强制校验和拒绝路径；纯展示且已核对无权限变化才写无，不因“只是前端”跳过直接安全边界 |
| 同一需求包含多个业务分支 | 每个主要场景各自包含现状、例子、业务流程、技术流程、改哪里/怎么改/为什么和验收；不拆成全量业务章+全量技术章让读者自行拼接 |
| 方案HTML生成后执行结构检查 | `scripts/check_design_doc.py` 只检查元信息、链接、重复ID和外部资源等机械项；内容真实性、业务闭合和视觉可读性仍需人工/浏览器检查，不把脚本通过当作方案批准 |
