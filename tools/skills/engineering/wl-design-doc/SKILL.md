# 方案设计（wl-design-doc）

## 目标与边界

本 Skill 的职责是把**已批准的需求**转化为一份能让人看懂、让实现 Agent 知道改动边界、让评审者能够批准的方案设计。

核心原则：

- 先定性、再划界：从已批准目标定位业务线和变化节点，核对后只沿直接影响链调研与设计。
- 按“目标 → 白话业务流程 → 对应技术实现 → 总结与验收”组织阅读，不先堆技术名词。
- 模板完整不等于每项填满；先判断专项适用性，不涉及写“无”，信息不足写“待确认”。
- 表达保持简洁；白话不等于省略实现方式或把关键技术全部折叠。
- 简洁压缩的是重复描述，不是工程决定。按下文“工程关键决定”核对技术底座、职责与状态、数据保存、运行交付及直接质量约束；可嵌入既有场景/专项，不新增固定大章节。
- 方案以业务场景为最小阅读单元：每个主要场景都从现状事实、最小例子、业务流程走到技术实现和验收。
- 方案停留在业务流程、模块职责、接口/数据契约和关键边界；不写函数级施工步骤。
- 证据支撑关键判断，但不让取证过程占据正文。
- 只在确有取舍或风险时增加专项章节，不为填模板制造内容。
- 最终用户只接收一份美观、可独立打开的 HTML。
- 先保证读者能沿一条场景链读懂，再补跨场景专项；不以固定章节数量或模板填满作为完整标准。

本 Skill **不负责**：需求确认、代码实现、详细任务拆分、提交发布、通用 HTML 发布体系或特定代码取证工具的操作手册。

## 前置与出口

- 前置：需求确认文档已批准（`status: approved`）。未批准时先执行 `wl-req-confirm`。
- 独立使用允许已确认的外部用例（现有测试文档/工单或其他来源），记录实际路径与版本即可，不要求本流程文件、默认文件名或先生成用例 HTML；不复制第二套正文。根本无用例时明确列为交接缺口，可继续方向讨论/设计草稿，但不可补造 source_test_cases 进入实施；不造来源。旧合法批准仍按下文兼容读取，不因缺本流程文件否定真实批准。
- 设计阶段只读调查和写方案，不写业务实现代码。
- 有真实的高成本或业务取舍时写清影响并给出明确推荐与理由；不为形式制造多方案。普通细节由 Agent 按项目约束决定；重大不可逆、范围/授权变化必须停下确认。
- 默认人工确认本版方案才能实施；仅在用户明确委托且边界覆盖本版时，可自动采用有依据的推荐。采用不等于人工批准，不代表代码已实现、测试通过或外部写入获准。

## 唯一最终产物

固定生成：

```text
docs/requirements/NNNN-slug/design.wl-design-doc.html
```

规则：

- 只生成、只交付这一份 HTML；不生成或保留 `design.wl-design-doc.md`、证据报告、独立图文件或其他平行正文。
- HTML 必须是单文件，可脱离工作区直接打开；样式、脚本和图形资源默认内嵌。
- HTML `<head>` 必须包含：
  - `<meta name="generator" content="wl-design-doc">`
  - `<meta name="artifact-schema-version" content="1">`
- 页面可见区域显示标题、需求标识、状态、来源需求、创建/更新时间和当前选型。
- 生成和视觉检查遵守同目录的 `doc-html-style.md`。HTML 解析成功不等于视觉验收通过；浏览器不可用时如实说明。
- 历史 Markdown 只能作为读取/迁移输入；不能因为兼容历史而重新生成 Markdown。

### 批准信息与阶段交接

- HTML 用一个 `<script type="application/json" id="wl-design-meta">` 保存需求标识、来源需求、`status`、创建/更新时间、`chosen`、`approval_evidence`。新方案同时写 `requirement_version`、`design_version`、`source_test_cases: {path, version}`、`decision_mode: manual|delegated`、明确的 `recommendation` / `recommendation_reason`、`critical_validation: {status, evidence}` 和 `delegation_evidence`；可见标签同源读取。JSON 转义 `<`，只作数据、不执行。
- 新方案 `status: draft`，尚未选定时 `chosen: null`，`approval_evidence: null`，`delegation_evidence: null`；候选推荐不是可执行决策。
- **manual（默认）**：用户明确批准本版及范围才标 `approved` 并填写真实 `approval_evidence`；有多方案时记录用户选型。委托不能填成人工批准。
- **delegated（显式委托）**：实际用户委托记录为 `delegation_evidence: {record, requirement_version, design_version, scope, data_boundary, cost_boundary, operation_boundary}`；每项非空，版本须与本版一致，范围须覆盖当前推荐。只有边界内且关键假设已验证，才能 `status: adopted`、`chosen: <recommendation>`，`approval_evidence` 保持 null。委托是独立决策证据，不是 `approved`。沉默、需求批准或旧版批准均不能代替委托。
- 新版可执行方案（approved/adopted）须有非空来源用例路径/版本、需求/方案版本、明确推荐及理由，且 `critical_validation.status: verified` / `evidence` 非空。字段存在不代表证据真实，负责人必须读实际记录及技术证据。重大不可逆、授权/范围/数据/成本变化或关键证据不足时回到草稿/确认，禁止自动实施。
- 同一需求目录先检查现有 HTML 和历史 `design.wl-design-doc.md` / `design.md`。并存时核对正文和批准版本；无法确定则停止询问，不凭文件名或时间选权威，不覆盖旧批准稿。
- 纯展示重生成保留原批准范围、`status`、`chosen` 和证据身份；变更契约、业务行为或范围须重新确认本版决策及边界，不能沿用旧版批准/委托。历史 approved 文档无 decision_mode 时按 manual 兼容，不补造委托或当前来源。
- 下游 `wl-ticket-run` 直接读取 HTML 正文及上述元信息，不要求为交接补造 Markdown。

## 设计前：先定性与划界，再定点调研

### 1. 接收需求，确定本次业务线

复用需求确认文档中的已批准目标和范围，不重新做一轮需求分析。将长描述提炼为用户最终要得到的结果；多个不同诉求按各自业务线区分，不把同一业务步骤机械拆成多个任务。

先提出归属与范围，再用项目导航、现有入口及直接相关代码做最小核对：

```text
原始诉求 / 已批准目标
  → 属于哪条业务线、哪个使用场景
  → 现有链路上改变哪个节点
  → 核对入口、直接调用方与必要依赖
  → 确定调研和设计边界
```

在摘要中用几行记录：目标、业务归属、变化节点、直接涉及范围、不涉及范围及未知项；不另写定性报告。模块名不是范围证明：“登录失败提示”不能自动扩成注册、找回密码或整个权限体系。

后续调查、设计、测试与 Review 只覆盖这条影响链。只有直接阻止目标成立或造成直接回归的依赖才可延伸，先说明“哪个目标 → 哪条依赖 → 为什么必须核对”；发现需改变已批准业务范围时先请求确认。无关债务只记为需求外观察，不自动修复或补设计。归属未知时做最小定位或询问，不凭标题猜定性、不全库扫描。

### 2. 判断专项适用性

依据目标、变化节点和现有事实选择需要展开的设计；不是按关键词套章节，也不因业务原文未提数据库就断言没有保存需求。每项先给结论和简短依据：

| 判断 | 写法与后续动作 |
|---|---|
| 涉及 | 指向本次业务步骤或直接依赖，展开必要设计 |
| 不涉及（已核对） | 写“无，本次不涉及”及一句依据，跳过详细设计 |
| 信息不足 | 写“待确认”及缺什么、影响什么；不能写“无”或补造实现 |

第4节的专项表用于防遗漏；不涉及项合并在表中，不再建空章节。初判可随直接证据修正，不把“无”当作以后不核对的豁免。每个新增技术构件必须能回答“解决本次哪个具体问题”；游标、行锁、版本检查、幂等、队列等不是模板默认配置。

### 3. 在边界内核实事实

开始深入调研前确认：

1. 目标项目、当前分支/版本和工作区范围。
2. 项目自己的规则、入口、测试方式和相关文档。
3. 本需求涉及的现有入口、模块职责、调用关系、数据/状态流和关键限制。
4. 本次涉及的实际技术底座：从构建配置、依赖声明、直接源码或运行记录核对语言/框架、关键版本、工程组织、存储、构建/测试与运行方式。区分正式资产、原型/实验、推荐新增；缺正式工程就明确写无，不把实验栈当正式栈，不以推荐技术替代现状。只核对影响本次决定的版本和直接依赖，不盘点全库。
5. 需求、现状和方案之间的边界：
   - **当前事实**：代码或获准运行结果已经证明；
   - **设计目标**：批准后准备实现；
   - **假设/待确认**：尚未证明，不能写成事实；
   - **验证结果**：本轮实际执行过的检查及结果。

优先读取与本需求直接相关的代码、测试、配置和运行证据，不做无关的全库考古。可以使用 CodeGraph 或其他工具定位，但不把任何特定工具写死为必经流程；工具输出必须用源码或运行结果定点复核。

正文只保留会影响方案理解或批准的依据。详细路径、命令、行号和工具输出可放 HTML 的“补充依据”折叠区；没有证据的关系标为“待确认”，不伪装成确定调用链。

## 执行方式：按需并行

- 开始调查前，主 Agent 先确认共同需求范围、项目基线和操作边界，判断是否有两个以上可独立开展、会影响方案结论的调查或验证任务。不要为并行制造任务、扩大调查或固定团队。
- 只有存在负责人无法可信补齐的独立验证或专业缺口且已获委派授权时，才通过 Herdr 启动 Pi 子 Agent，显式 thinking=high；不可用或不能确认 high 生效时说明阻塞，不改用其他宿主、不伪称独立完成。实际委派时，委派授权不等于新建独立任务、启动服务或外部操作的授权。同一轮先派出可并行任务，再按依赖收取结果，不逐个等待后再派下一个。各任务交代输入、输出、完成标准及边界，说明它解决的具体缺口；工具或预算限制不能并行时如实说明，不声称已并行。
- 主 Agent 保留下一步立即依赖的工作；子 Agent 只承担边界明确的现状检索、关键假设验证或按需 Review，返回结论、依据和未确认项。等待期间，主 Agent 推进不依赖这些结果的工作，不重复调查同一问题。
- 主 Agent 核对结果是否对应共同基线，处理证据冲突，统一形成推荐和最终 HTML；关键冲突未解决前不写确定结论。禁止让多个 Agent 各写整份方案再拼接，Review 不能代替实际验证。
- 没有独立任务、未获委派授权、工具不可用或协调成本明显不划算时，由主 Agent 执行，并简短说明具体原因；遵守项目及宿主约束，不绕过操作授权。
- 分工、真实调用和结果整合留在任务过程记录，不作为技术方案固定章节；未真实委派不得声称完成独立审查，也不能仅凭 Agent 数量声称提速。最终仍只交付一份方案 HTML。

## 设计推导方法

### 1. 先确定最小完整方案

先列出已确认的目标、现有资产和不可妥协的约束，画出能够完成业务的最小链路。至少用一个正常场景和适用的失败场景检查链路是否闭合。需求包含多个业务分支时，先拆成场景，再分别闭合，不把不同场景的技术细节混成一条总链。

每个关键新增或变化都说明：

```text
具体场景 → 原方案哪里不够 → 最小变化 → 下游结果 → 验收方式
```

### 2. 用调用方行为校验设计

接口、数据结构和模块边界先从调用方如何使用来推导：

```text
谁发起 → 传入什么 → 系统做什么判断 → 得到什么结果 → 哪些内部细节不应暴露
```

每个主要场景至少给一个最小例子；例子必须能看出“输入 → 中间转换 → 结果”。真实运行例子、规则推导例子和目标示意要标明身份，不能把推导写成运行事实。

必要时给 1～2 个简短调用/使用示例，但不写实现代码。检查公共边界是否泄露存储、传输或框架细节，是否存在无意义的透传层、重复状态所有者或两套完成同一任务的路径。技术方案必须就地回答：**改哪里、怎么改、为什么这样改**；“为什么”应说明与当前项目约束、复用资产、兼容性和可回退性的关系，不写脱离证据的“最佳”。

### 3. 工程关键决定：场景能读懂，还要能据此实施

在场景推导后，沿同一个输入核对下面五项。它们是最低内容责任，不是强制五个章节；已有场景/专项说清就引用该处，不复制正文。每个适用项写清**当前依据 → 本版推荐决定及理由/代价 → 验证方式或未决影响**。不涉及时给一句核对依据。

| 决定 | 至少回答什么 | 适用边界 |
|---|---|---|
| 技术底座与选型 | 当前实际使用什么、复用什么、新增什么；关键兼容条件及为什么适合本次目标。原型、实验与正式资产分开 | 所有方案均简述；单点改动一句沿用即可。新工程/引入框架时说明选型与构建基础，真实存在替代路线才比较 |
| 模块职责与状态归属 | 谁接收操作、谁持有权威状态、谁执行副作用；调用/通知方向、成功失败如何回到调用方 | 跨模块/多视图/异步状态变化时展开；单点展示不新造分层。稳定ID或“统一状态”不能替代具体归属与更新路径 |
| 数据与保存边界 | 关键对象/关系和生命周期、存取责任；有持久化时说明保存触发、提交/事务边界、失败保留与恢复；涉及线程/异步则说明顺序与一致性 | 已有能力复用须指出实际契约；不强制DDL或新存储。预览/内存编辑/已保存状态不能混为一谈 |
| 工程运行与交付 | 如何在现有工程接入、构建、测试和运行；新工程说明组织方式及最小可运行交付物。环境/开发数据隔离、支持范围及适用升级回退边界 | “本轮不发布/不安装”只限制执行授权，不免除说明如何交付；已核对不变的现有发布链一句复用，不生成无关部署体系 |
| 直接质量约束 | 本次直接涉及的隐私/权限、兼容与恢复约束；有容量/响应风险时给验证规模或测量方案及依据 | 区分既定要求、建议测试样本、实测结论；不凭空承诺性能数值，不因本地/无账号就跳过数据暴露与日志边界 |

普通可逆技术细节由 Agent 给本版推荐，不把所有工程选择都推给用户。具体数值无事实依据时可作为有理由的候选参数/测试样本，不能写成已确认要求或已达指标。若尚未决定的事项会让实现者重新选择核心框架、状态归属、存储提交方式或交付路径，应补决定或显式标为阻断；不能只写“实现时确定”再宣称可实施。非阻断调优可后置，说明验证时点与残余风险。

设计决定与可行性验证分别检查：实验通过只能证明对应能力；不能替代正式工程的职责、状态、数据和交付设计。关键技术假设未验时仍遵守原有草稿/批准门禁，不为补齐文字虚构实测或接受风险。

### 4. 只对重要取舍做压力测试

以下情况才展开演进、迁移、回滚、安全、性能或运维分析：

- 设计难以回退或会影响已有数据/外部调用方；
- 存在已确认的未来要求或可信的高成本变化；
- 涉及权限、并发、异步、外部系统、公共接口或线上发布。

没有可信依据时，不为“未来可能”提前增加抽象；但已知的兼容、一致性、隔离和恢复约束不能省略。

## 文档结构（固定阅读顺序，场景数量按需求决定）

不把六节当成每次必须填满的表格。最终阅读顺序固定为：

```text
方案目标与定性边界
  → 场景 A：现状事实 → 最小例子 → 业务流程 → 技术流程 → 改哪里/怎么改/为什么
  → 场景 B：现状事实 → 最小例子 → 业务流程 → 技术流程 → 改哪里/怎么改/为什么
  → 跨场景专项与取舍
  → 实施边界与验收
```

简单需求可以只有一个场景和一份短验收；复杂需求再增加场景和专项。保留以下内容职责，但不强制生成空章节：摘要、场景闭环、适用专项、取舍、实施边界和验收。

### 1. 方案摘要与范围

**回答：为什么改、要得到什么、属于哪条业务线、什么不做？**

表达形式：1～3 段白话 + 目标/非目标清单 + 必要时的需求覆盖表。

必须说明：

- 当前问题、用户最终得到的结果，以及已核对的业务归属和设计边界；
- 本次方案结论或待用户决定的事项；
- 本次实现什么；
- 明确不实现什么；
- 哪些现有行为保持不变；
- 需求较多或容易遗漏时，用简表建立“需求 → 方案覆盖 → 验收”关系。

### 2. 场景闭环：现状、例子与业务流程

**回答：这个场景现在是什么样，用户给什么输入，业务上要怎么变化？**

每个主要场景按以下顺序写，不跨到另一个总技术章节再拼接：

```text
场景目标与范围
  ↓
当前真实情况：代码/运行/历史材料分别证明什么，局限是什么
  ↓
最小例子：输入 → 中间转换 → 当前或目标结果
  ↓
以前：完整业务流程
  ↓
改后：完整业务流程
  ↓
关键变化：旧行为 → 新行为 → 下游结果 → 验收方式
```

要求：

- 业务流程用纵向 ASCII 图，节点写完整业务动作；
- 例子优先贯穿后续技术流程，不在技术部分换成无关抽象数据；
- 当前事实、设计目标、推荐方案、推断和验证结果必须区分；
- 当前事实就近附证据和局限，不能只把“看过代码”的证明藏到末尾；
- 业务图只写业务顺序、判断、结果和必要失败出口，不塞锁、版本比较、事务回写等内部机制；
- 用 `[保持]`、`[新增]`、`[修改]`、`[删除]`、`[待确认]` 标识变化；
- 没有旧入口时明确写“纯新增”，不虚构旧流程。

### 3. 场景承接：技术流程、改动位置与设计理由

**回答：为了完成刚才这个场景，具体改哪里、怎么改、为什么这样改？**

每个主要场景紧跟自己的业务流程写技术承接，不把所有技术节点集中成一份全局清单：

```text
同一个最小例子
  → 进入哪个现有技术边界
  → 在哪里转换、校验或保存
  → 数据传给谁 / 如何关联
  → 下一步如何读取或使用
  → 如何得到业务流程中的目标结果
```

每个场景至少说明：

- **改哪里**：现有入口、模块、接口、数据记录或展示节点；引用当前事实，不只列模块名；
- **怎么改**：数据如何产生、转换、保存、关联、读取、回写和失败；必要时画技术数据流或时序图；
- **为什么这样改**：复用什么、保持什么兼容、解决哪个业务问题、接受什么代价；存在真实替代方案时再比较；
- **证据与局限**：当前实现依据什么，哪些只是推荐设计，哪些需实施前核验。

如果技术变化包含两个以上步骤，必须有技术文字链路或图；单点文案、单字段映射等简单变化可用短句，但仍要回答三件事。技术方式默认可见，长字段、源码行号、异常全集和历史证据折叠；不能把“保存在哪里、如何取回和协作”全部藏起来。

### 4. 跨场景专项设计

**回答：除了场景内技术承接，哪些共用专项确实需要设计？**

先给适用性表，结论只能是“涉及 / 无，本次不涉及 / 待确认”，每行写一句与目标或直接依赖相关的依据；只展开“涉及”和会阻塞设计的“待确认”。专项是查漏层，不是阅读主线。上文“工程关键决定”给出适用项的最低深度，本表只决定放在哪里展开；不能用适用性结论代替具体设计。

| 专项 | 何时需要展开 | 必要内容（按实际变化选择） |
|---|---|---|
| 数据与存储 | 本次读取口径、保存、数据结构或数据生命周期需要设计 | 来源、读写/保存形式、关键内容及关联方式；结构变化时再写字段、迁移、回填和回滚 |
| 接口与协作契约 | 本次涉及接口或模块间数据交换、返回/错误语义 | 调用方、输入输出、变化字段、必要错误与兼容；复用不变接口不编造新契约 |
| 状态、异步与并发 | 跨步骤/跨轮状态、异步回调或竞争会直接影响结果 | 状态承接、完成/失败口径；只有存在重复副作用或竞争证据时设计控制 |
| 安全、权限与隔离 | 本次改变身份、访问范围或数据暴露，或直接触及已有约束 | 身份、资源归属、后端强制校验、拒绝路径和隔离；不做无关全量加固 |
| 性能与容量 | 目标含性能要求，或直接影响链有已知容量限制 | 对应规模、约束和必要处理；不虚构指标、缓存或分页机制 |
| 外部依赖、发布与恢复 | 本次依赖外部能力、改变部署，或有明确迁移/恢复问题 | 依赖条件、必要兼容/发布顺序和恢复边界；不因“最终要发布”自动增加部署方案 |

判断专项不能只看需求有没有出现关键词：需求说“记住”可能意味着跨轮存储，需求说“只允许自己看到”一定需要权限隔离；反过来，纯展示文案且已核对无接口、数据和权限变化时，对应专项写“无，本次不涉及”。信息不足写“待确认”，不编造表、字段、锁、队列或版本机制。

### 5. 复用、取舍与风险

**回答：为什么采用这个方案，复用了什么，代价和风险是什么？**

先用短段总结推荐方案、选择理由和实际代价；没有需用户拍板的事项时明确写“无”。待决定事项用“问题 → 推荐 → 用户可感知影响”表达，不让用户在正文里寻找编号。只有存在多个真实可行方向、重大架构选择或难以逆转的决策时，才增加方案比较表：

| 方案 | 适用条件 | 优点 | 代价/风险 | 结论 |
|---|---|---|---|---|

必须记录选择理由和接受的代价。复用分析仅在存在复用资产、兼容约束或“为何不能复用”的决策时展开，不为形式盘点全库。

风险从第4节适用项和关键假设归纳，只写对目标或批准有实际影响的后果，不把专项正文再抄一遍。没有证据的未来演进不展开；未决问题明确是否阻塞批准。

### 6. 实施边界与验收

**回答：后续实现 Agent 从哪里开始，什么结果才算完成？**

表达形式：直接影响范围 + 可观察验收 + 最小验证方法；简小任务可用短清单，不为了六节模板强制生成完整DoD或验收大表。

写清：

- 需要改动的模块范围；
- 需要复用的现有能力；
- 明确不应修改的边界；
- 实施前置条件和依赖方向；
- 本次构建、测试、运行与最小交付路径，以及与现有工程的接入关系；只写方案级决定，不写函数级步骤。不发布不等于不设计交付；不变的现有路径可简述复用依据；
- 来源用例链接和版本、对应正常/失败/权限/重复/兼容等适用用例 ID；具体数据/操作/业务预期引用原用例，不复制第二套验收正文；技术验证另列与本次实现直接有关的最小检查；
- 验证方法和完成标准；
- 尚未执行的验证及原因。

可以写“先完成契约，再完成业务链路，再接入调用方”的依赖方向，但不在这里生成函数级施工步骤、完整 Ticket、负责人、工时或提交计划；这些交给后续任务拆分/实现 Skill。

## 场景生成与机械检查

复杂需求先按 [场景卡片](references/scenario-template.md) 组织内部内容，再生成唯一 HTML；事实身份和证据写法按 [证据与状态](references/evidence-and-status.md) 执行。生成后可运行：

```bash
python3 tools/skills/engineering/wl-design-doc/scripts/check_design_doc.py /path/to/design.wl-design-doc.html
# 工单交接加 --require-executable，草稿不得进入实施。
```

该脚本只检查机器可判定的 HTML 结构，不替代内容审查、浏览器视觉检查、业务测试或用户批准。

## 按需图形规则

默认生成每个主要场景的业务主流程图；技术变化包含两个以上步骤时，同时生成对应技术流程或数据流图。简单单点变化无需为了形式画图。只有以下问题无法用短文或表格说明时才补充专门图：

| 需要解释的问题 | 补充形式 |
|---|---|
| 跨哪些模块以及谁调用谁 | 模块/调用链图 |
| 数据从哪里来、如何转换和保存 | 数据流图 |
| 状态如何迁移、哪些动作被禁止 | 状态图 |
| 异步、并发、等待、回调、超时、重试 | 时序图 |

所有图必须标明关系含义；未知关系标为待确认；不为凑格式重复主流程。

## 最小自检

交付 HTML 前检查以下五件事：

1. **场景闭合**：每个主要场景都有现状事实、最小例子、业务流程、对应技术流程和结果；正常及必要失败路径说清楚。
2. **技术可评估**：每个场景都明确改哪里、怎么改、为什么；技术数据流、相关职责、适用契约及必要异常清楚；不是业务目标的复述，也没有下沉到函数级施工。
3. **范围未膨胀**：定性与边界明确；专项有涉及/无/待确认及依据；每个技术构件能对应本次问题，没有把推测或无关债务写成需求。
4. **验证可判断**：每个核心需求都有可观察的验收结果；实际执行、静态推断和待验证事项明确区分。
5. **工程决定可接手**：沿同一操作核对上文五项，现有栈与推荐栈分清，职责/权威状态、适用数据提交与失败处理、运行交付和直接质量约束具体可定位。不是只列技术名或“统一处理”，不把决定留空后用实验通过代替；无关项不扩写。检查正文与元信息、历史引用的当前/目标身份一致。

影响方案成立的关键假设必须用最小证据验证，例如复核现有契约、表结构或最小实验；记录实际输入、结果和依据，不把推演写成实测。关键验证失败或仍无证据时，方案退回草稿，只能请求补证或方向讨论，不能请求可实施方案批准、标记 `approved` / `adopted` 或进入实施。非阻断验证可留到后续，但须写明原因、时点和残余风险；默认由用户明确接受，委托模式也只能在实际委托明确覆盖的风险边界内采用，不自行扩大风险接受范围。

最小可解释性检查：读者只读默认展开内容，就能沿任意一个场景回答“当前是什么 → 输入是什么 → 业务怎么变 → 技术改哪里/怎么改/为什么 → 结果如何验收”。答不出就修改场景正文，不增加审查章节。遵循用户/项目的沟通偏好：默认白话、文字链路和关键节点新旧差异；没有明确要求不用Mermaid。段落按一个问题组织，不堆多个技术主题；重复的批准声明、限制和证据集中维护，但影响决策的未知与风险不可藏进折叠区。

HTML 视觉检查至少确认：正文开场先讲摘要和主流程；流程图空格与分支可读；表格不过度拥挤；补充信息不会打断主阅读路径；页面在桌面和窄屏可读。

修改本 Skill 后，按 [回归场景](references/regression-scenarios.md) 检查生成、批准和交接行为；结构检查不能代替场景执行。

## 与后续流程的边界

```text
已批准需求
  ↓
wl-design-doc：确定业务流程、设计边界、契约和验收
  ↓
人工批准 approved / 明确委托后采用推荐 adopted（证据及版本核对）
  ↓
任务拆分/实施 Skill：拆垂直任务、定义依赖、逐项实现和测试
  ↓
代码审查与实现后验证
```

实现中如果反复出现同类 workaround、调用方必须了解内部规则、或实现持续偏离方案，应暂停继续堆补丁，回到方案重新确认边界。

## 禁止事项

- 需求未批准就进入方案设计。
- 把当前代码事实、设计目标和验证结果混为一谈。
- 为了显得完整而强制填满专项、增加多方案、专项图、未来抽象或通用检查清单。
- 用模块名或关键词替代需求定性；把信息不足写成“无”；在业务图塞内部机制，或用业务目标复述替代技术实现说明。
- 把所有场景的业务流程和技术流程拆成两个孤立总章节，要求读者自行拼接；没有最小例子或没有“改哪里/怎么改/为什么”就宣称方案完整。
- 把业务流程图伪装成函数调用图。
- 把函数级施工步骤、详细 Ticket 或提交计划塞进方案正文。
- 生成 Markdown、独立证据报告或与 HTML 平行的第二份方案正文。
- 用未执行的检查结果宣称已验证或已批准。
