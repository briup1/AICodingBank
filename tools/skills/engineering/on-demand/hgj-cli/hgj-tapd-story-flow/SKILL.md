# TAPD 需求/任务工作流

用于把用户描述忠实整理成 TAPD 需求或任务，并在确认后写入。

如果用户提供完整版本需求并要求“创建迭代”，改用 `hgj-tapd-iteration-flow`，由该工作流统一创建迭代、需求和前后端任务。本工作流只处理单独的需求或任务。

## 需求拆分与原文一致性

当用户提供需求文档并要求拆分或创建具体需求时：

- 把原需求文档和用户在当前上下文中明确给出的后续澄清作为拆分结果及需求正文的唯一内容来源。
- 优先沿用原文的编号、标题和条目边界。只有原文明确列出多个独立具体项时才继续拆分，不根据常识、代码实现或类似业务自行增加具体项。
- 每条拆分后的需求必须能回溯到原文中的明确条目或段落。标题优先使用原文标题；原文没有标题时，只从对应原文提取不引入新含义的短标题。
- 拆分时直接对照原文，不以 Agent 生成的摘要、开发计划或代码分析代替原文继续拆分。
- 描述应直接使用对应原文，只允许不改变语义的分段和格式整理。不得扩写、缩写为不同范围、混入其他条目内容，或补充原文未写明的功能、规则、流程、条件、例外、风险、依赖和验收标准。
- 对角色、字段、状态、公司名称、金额、日期、时限、文案等具体信息保持原文，不自行替换术语或润色业务值。
- 信息缺失或表述有歧义时，引用对应原文向用户澄清；在用户明确补充前不要推断补齐。
- 在写入前为每条需求保留原文编号、标题或可定位段落的对应关系，并逐项检查需求正文没有原文和用户明确澄清之外的业务内容。

## 创建前必须确认

- `workspace_id`
- 类型：需求 `stories` 或任务 `tasks`
- 标题
- 描述 / 验收标准
- 处理人 / 开发人员
- 优先级
- 迭代或父需求（如有）

如果缺少 `workspace_id`，先查询用户参与项目并让用户选择。不要默认使用不确定的项目。

## 推荐描述结构

以下结构只用于整理原文中已有的对应内容。原文没有内容的章节直接省略，不要为了填满模板生成内容。

```md
## 背景

## 目标

## 范围

## 验收标准

## 风险与依赖
```

## 写操作规则

创建或更新前必须按拆分项展示对应的原文编号、标题或段落，以及即将写入的完整标题、项目、类型、处理人和描述，并等待用户确认。
