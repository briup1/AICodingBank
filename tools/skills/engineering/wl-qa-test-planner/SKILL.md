# 测试用例生成

目标：不熟悉项目的人也能找到入口，按步骤操作，取得结果并与预期比对。用例是操作说明，不是规则摘要，也不是执行报告。

输出约束版本：2（2026-10-20）。这是 `softaworks/agent-toolkit` 的 `qa-test-planner` 的个人精简策略入口，不是上游改名副本。上游仅作字段参考，输出以下面的约束为准。

## 来源与按需加载

- 上游：https://github.com/softaworks/agent-toolkit/tree/main/skills/qa-test-planner
- 上游登记：工作台根目录 `skills-lock.json` 中的 `qa-test-planner`。
- 模板：`../../../../vendor/softaworks__agent-toolkit/skills/qa-test-planner/references/test_case_templates.md`（相对本 Skill 真实目录；宿主为软链时先解析真实位置）。
- 生成前只读取相关模板章节；不照搬上游的执行历史、字段表或整个 QA 计划。模板缺失时明确说明，按下方格式继续，不自动安装或同步。
- 不加载上游 `SKILL.md`、Bug/Figma/回归指南，不调用上游脚本；不依赖其他 Skill。

## 输入与范围

需要需求或用户故事、验收标准，以及已提供的角色、环境、数据限制。可以接收界面说明、接口契约和已有用例。

只覆盖本次需求及直接受影响的最小回归路径。只追问会改变测试步骤或通过条件的关键问题；其他缺口明确标为待确认。不得编造金额、状态码、接口路径、时限、权限规则或页面行为。可以设计合成测试数据，但须标清需要预置的关系，不能说成已经存在的账号、候选或记录。

重写已有用例时保留用例 ID、需求追踪、优先级、业务预期、边界值和待确认事项；改变表达不等于批准改变规则。原矩阵中的数据和反例不能因缩短正文而丢失。

## 执行链路

1. 列出已确认需求与测试范围。沿用原始需求 ID；没有 ID 时分配 R-001 等标签并附原文摘要。区分事实与假设。
2. 按实际规则拆分正向、异常、边界和状态变化场景；适用时采用等价类、边界值。规则未知的边界值标为待确认。
3. 按业务影响设置 P0/P1/P2；相同触发条件、动作和预期的场景合并，数据差异可参数化。不要凑用例数量。
4. 为每个场景写出前置条件、具体测试数据、逐步操作和可观察、可判定的逐步预期。需要恢复数据时注明清理要求，不实际执行写操作。
5. 对照每条需求检查覆盖和遗漏；直接影响的旧行为只保留必要回归用例。未知预期标为阻塞/待确认，不写成确定事实。

## 默认输出

使用中文 Markdown；需要 HTML 时从同一份 Markdown 生成，不维护两份业务正文。不新装导出工具。

### 1. 范围、入口与公共准备

- 简要列出覆盖、不覆盖、需求正文链接及版本、用例基线版本。
- **测试入口**：已知目标环境和完整业务页面地址时，按角色/业务页面给可点击链接。多条共用时放分组开头，单条专属时放该条元信息处；步骤直接接着该页面操作。HTML 中链接放在代码块外。
- 只有路由、没有站点地址，或缺供应商/记录标识时，写“待补齐”及已知菜单路径；不拼猜测地址，不把含占位符的路径当可用链接。不把原型、用例阅读页、未经确认的Dev/Beta或其他任务地址当成目标业务页。
- 路由来自代码、页面尚未核验时明确区分。已有准确地址可列出并注明未验证可达，不为生成用例登录或提交业务请求。链接不得携带密码、Token或Cookie；本机回环地址标明“仅本机”。
- **公共准备**：账号角色、权限、环境、基础数据、日期时钟和执行限制只写一次；单条的特殊状态并入测试场景，特殊数据并入测试数据。
- **执行顺序**：同一账号、同一页面且相互独立的检查集中完成，再换页面/角色。共享登录和导航，不共享本应独立的任务、样本或未重置状态；有并发/独立会话要求时保留。
- **待补齐项**集中列出，必要时标用例/步骤编号；缺条件不能计通过，不在每条末尾重复“未执行、阻塞”。
- **执行记录约定**只放 [统一记录约定](../../../execution-profiles/test-execution.md) 的引用，不复制字段和目录规范。生成用例时不填执行结果，不创建测试轮次或在线记录功能；实际测试由执行者读取约定。
- 清理要求公共部分写一次；确有特殊清理动作时纳入该条步骤及预期，不添加固定尾巴。

### 2. 测试用例

按业务部分分组（如 A：查询、B：导出），不按技术层或优先级替代业务分组。每条标题下只留一行元信息：`对应需求（Trace）：R-001；优先级：P0。`，有专属页面入口时再加一行链接。

正文只保留三个字段：**测试场景**、**测试数据**、**测试步骤**。

- 场景：一句话说清“在什么页面/状态，检查什么”，不讲背景故事。
- 数据：给具体输入、文件内容/获取方式和必要准备。共用数据引用明确编号；只替换一个值时写清原值、新值及其他不变。避免“同样准备”“合法数据”而不给来源；未知项集中挂待补齐。
- 步骤：编号树展开；共用动作放父节点，分支放子节点，分支内动作按执行顺序编号。每个检查点紧跟“预期”，说明到哪里看、哪个值或状态应该怎样。不能只写“正常、异常更新、按规则校验”。
- 共用校验确需复用时，作为树内有编号的执行步骤，并明确“每个分支执行后回到哪一步”；不另起“结果检查/保存检查/拦截检查”区，不让读者拼接正文。不同分支预期不同则写在各自分支。
- 测试步骤与多路径不用表格；不要用表格重新列同一份操作和预期。覆盖索引可用表格，但不能成为步骤的第二份正文。
- 不加“检查、实际、状态、后置条件/清理、结果判定”等重复字段或固定尾巴。表达直接用“测试场景、测试数据、测试步骤、预期”，不用“用什么数据、怎么判断”等问答式标题或劝说段落。
- 简洁不能牺牲可执行性：不得用“所有入口、各变体、逐项检查”代替入口、数据及各自预期；不为减少重复删除负向、边界、并发和恢复条件。

格式示例（示意页面名称，不预设业务规则）：

````markdown
### TC-001：文件与文字识别

对应需求（Trace）：R-001；优先级：P0。

**测试场景**：在识别页面，检查文件和文字能否生成对应任务。

**测试数据**：指定测试文字；将同一内容保存为UTF-8文本文件 example.txt。

**测试步骤**：

```text
1. 打开已提供链接的识别页面
   1.1 文件识别
       1.1.1 只上传example.txt，点击“开始识别”
             预期：生成文件识别任务。
       1.1.2 打开本次任务原文
             预期：关联example.txt，原文与文件内容一致。
   1.2 文字识别
       1.2.1 返回识别页面，只粘贴测试文字，点击“开始识别”
             预期：生成新的文字识别任务。
       1.2.2 打开本次任务原文
             预期：内容与刚才粘贴的文字一致。
```
````

### 3. 覆盖与缺口

列出 `需求 → 用例 ID/步骤编号 → 正向/异常/边界或不适用原因`，以及未覆盖项、假设和待确认问题。按 Trace 反查 `用例 → 需求/直接回归依据` 防越界；具体数据、操作和预期只维护一次，已有历史 AC 可原位引用，不再复制 AC/TC 两份正文。

交接注明基线版本、整体链接、缺口及审查/确认状态；生成不等于独立审查、人工确认或执行通过。独立审查调度由调用方负责，不作为本 Skill 的新增生成步骤，也不依赖总流程私有文件。

### 4. HTML 展示检查（需要 HTML 时）

- 字段标题使用 `**测试场景**：内容`，不要使用 `**测试场景：**内容`；部分 Markdown 解析器会把后一种写法的星号原样显示。测试数据、测试步骤同理。
- 字段标题正常渲染为加粗文本，不能显示 Markdown 星号；链接应为可点击的锚点，编号树保留缩进和换行。不要靠全局删除星号破坏合法正文。
- 使用已有渲染工具做最小验证：三个字段渲染为对应元素、编号树不乱行、入口链接没有被放进纯文本代码块；需要真实浏览器核验时另按获准能力处理。
- 不让通用草稿说明冒充当前环境事实；生成完成不等于业务环境就绪。不能把静态 HTML 检查说成真实页面验收。

## 交付自检与停止

- 每条用例能追踪到需求或直接回归依据，有优先级、数据、步骤和明确预期。
- 已考虑相关正向、异常、边界；不适用或信息缺失时说明原因。
- 没有重复场景，没有把未执行用例写成通过，没有用猜测填补业务规则。
- 不输出测试排期、发布门禁、Bug 报告、Figma 对照或业务自动化代码；不执行业务测试、业务脚本或业务写操作。仅允许生成文档及对生成产物做静态校验，不把它算业务测试。
- 用例与缺口交付后停止。需要实际执行或其他能力时另按用户请求处理。
