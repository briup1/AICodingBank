# 维护项目资料

本次变化 → 受影响的唯一正文 → 最小修订 → 核对证据。先读[统一契约](../harness-pack/references/shared-protocol.md)，只读本次受影响的[模板](../harness-pack/assets/harness-template/)和[内容标准](../harness-pack/references/content-standard.md)对应段落。不以运行过setup为前提，不自动调用setup。

## 执行

1. **确定输入**：明确目标项目、本次需求/决策或变更范围。用户给了提交/分支就核对实际diff；只有工作区变化则按相关文件记录范围。没有可靠基准时询问，不猜“上次运行”；没有稳定资料变化输出“无需同步”，不建空记录。
2. **定位正文**：从实际项目入口映射找到Owner，沿直接调用方/依赖核对。规则/流程变化归rules，业务/术语/数据/契约归Wiki；需求与样本仍在原需求目录。overlay只改个人补充，团队正文问题给建议补丁。
3. **最小修订**：原位更新受影响段落，保持共享标题与二级章节，章内按复杂度选紧凑或详细格式；新增缺失文档用同一模板，不重建全部底座。依据代码只能更新事实/默认实践，不能替用户批准新规则；未实现内容仍标拟采用，不把测试失败改成通过。新增/冲突规则或结构迁移须确认；本轮已明确授权的事实同步不重复逐句审批。
4. **验证与交付**：执行统一结构检查并回读正文/引用。已采用统一结构的文件不得引入漏章/改名/错序；历史异构正文默认只做差异报告，未获迁移授权不强改，不能把“未规范化”报通过。记录实际检查与未验证项，保留历史证据及未提交修改。涉及测试入口时按共用入口卡约定补齐填写提示与账号预留 JSON，将已确认入口完整 URL 填入“环境”而非文字标签；保留用户已填账号、密码和URL，不因未知账号而删占位对象，也不为无关同步读取凭据。

## 记录与停止

仅长期规则、模块职责/关键契约或须保留理由的重要取舍变化，才在本需求 `docs/changes/日期-主题/规范变更.md` 更新简短记录；局部修复、链接和一般事实补齐直接改原文。记录包含：关联来源、前后变化、修改位置、确认与验证；正文来自[变更模板](../harness-pack/assets/change-template/规范变更.md)。已有需求目录即复用，沿项目已有结果契约，不造平行报告。无需需求文档的维护可建日期-维护主题目录，仅放必要记录。

同输入再次使用无额外diff，不重复追加记录。校验失败只修本次文档；遇到并发改动停下，不用reset/clean覆盖。交付后停止，不改业务代码、不运行业务测试、不自动提交、安装或发布。测试凭据只按[入口卡边界](../harness-pack/references/testing-entry.md)处理，不读真实密码来做资料同步。
