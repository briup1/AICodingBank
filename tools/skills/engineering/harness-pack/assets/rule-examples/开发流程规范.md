# 开发流程规范

> 虚构示例：四份范文共用“本地待办应用”，仅演示结构、粒度和表达，不代表真实项目或实测结果。不得把示例中的路径、技术栈、命令或规则直接当作目标项目事实。

范围：本地待办应用；状态：当前；依据：虚构项目的协作约定及 docs/changes/README.md；“当前”仅指示例设定。

## 需求与资料归宿

每项需求归档在 docs/changes/YYYY-MM-DD-主题/。以“勾选待办后保存完成状态”为例，同目录维护：

- requirement.wl-req-confirm.md：目标、范围与批准记录；HTML 从它生成。
- design.wl-design-doc.html：需要设计时的方案唯一正文。
- test-cases.wl-qa-test-planner.md：具体数据、操作与预期；HTML 从它生成。
- test-runs/轮次/：实际执行后才建，保存既有格式的结果及必要证据。

调用需求、设计、用例能力时显式指定上述需求目录，不使用其默认目录另存一份。小范围文案或链接修正可直接在原正文修改，不强制创建全套产物。

## 从需求到交付

以这项需求为例：

确认勾选后应发生什么 → 明确用例及必要方案 → 获准后实现 → 按[测试规范](测试规范.md)验证 → 交付差异、证据与未覆盖项。

需求和用例中的业务结果保持同一批准版本；具体步骤只在用例正文维护，不抄进流程规范。

## 确认与操作边界

已确认（示例设定）：需求确认不等于获准实现，测试通过不等于获准发布。实现、外部写入、提交和发布分别核对本轮授权，不因进入下一阶段自动获得许可。

若从“仅当前浏览器保存”变为“跨设备同步”，须重新确认范围与用例，再调整方案；不能作为顺手优化直接实现。

## 完成与资料回写

交付说明写清改了哪里、实际验证结果和未覆盖项；失败或未运行不得写成通过。证据与结果写回本需求的执行记录，格式和通过判据沿用测试规范，不在此复制测试步骤。

若改动长期职责，例如页面开始调用远端服务，更新原有工程结构及相关规则；有重要取舍时在同需求下补规范变更.md。普通样式修正不额外建规范记录。

## 来源与未覆盖

- 来源：示例协作约定及 docs/changes/README.md，均为虚构材料；没有真实批准或交付记录。
- 待确认：首次发布由谁审批、如何回退；首次发布前确认，当前流程不代表已具备发布能力。
