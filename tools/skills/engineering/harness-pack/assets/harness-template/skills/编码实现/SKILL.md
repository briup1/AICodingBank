# 编码实现 Playbook

> 状态：草案（待人工确认）

## 前置条件

- 本 playbook 是开发流程 2.3 的展开实现；风险=高时编码完成后须经专家评审（开发流程 2.4 插入）。
- 目标、验收和影响链路已确认。
- `rules/工程结构.md` 能指出修改落点，`rules/编码规范.md` 能说明对应模块的写法。
- 受影响接口和状态在 Wiki 中有完整契约；缺失时先补草案并确认，不靠猜测编码。
- 缺陷已有失败复现；新行为已有可执行验收。

## 上下文准备

只加载与本次变更相关的规则/wiki 文件（≤3 个），不全量灌入。技术血肉（框架用法、API 形态、事务/并发写法）以 `rules/编码规范.md` 对应组件节为准，本 playbook 不内嵌任何技术栈细节。

## Step 1：选择最小扩展点

沿 `调用方 → 契约 → 提供方 → 状态/外部系统 → 返回` 检查所有受影响路径，在共享根因或既有扩展点修改。优先复用 helper、客户端、handler、store、adapter、注册表、Hook 和平台原生能力。

**完成标准**：每个拟改文件都有必要性；未创建与现有机制平行的新入口。

## Step 2：按依赖和契约排序

依据项目实际链路安排实现顺序，例如先更新权威 schema/契约，再更新提供方和调用方；具体顺序服从 `rules/工程结构.md`，不套固定分层。

接口变更必须成套处理：

```text
权威契约
  → 提供方解析/校验/错误/副作用
  → 调用方序列化与失败处理
  → 状态投影
  → 测试与文档派生视图
```

## Step 3：按模块规范实现

- 使用 `rules/编码规范.md` 中该模块的代码落点、默认实现、不变量、错误/并发/权限/清理规则。
- 已确认规范必须遵守；默认实践应遵循，偏离时记录理由和影响。
- 提议不作为门禁；未决安全、数据或不可逆操作先停止询问。
- 新命名（概念、字段、状态值）先查 `wiki/领域术语.md` 与 `wiki/数据模型.md` 第 3 节，禁止自造同义词或发明状态值。
- 只实现验收需要的最小行为，不顺手补不存在的层或重构无关代码。

## Step 4：验证完整链路

- 先运行最小失败复现或新增行为测试，再运行受影响模块检查。
- 覆盖最近的错误、乱序/并发、权限、断线、取消或资源清理场景。
- 协议变更核对请求、响应、错误和调用双方；状态变更核对权威源、投影和迟到结果。
- 执行 `rules/开发流程规范.md` 中对应变更矩阵，记录未运行项和原因。

## Step 5：文档同步判断

出现模块职责、默认实践、接口、状态、术语或验证能力变化时调用 `harness-sync`；没有稳定增量时明确“无需同步”。

## 输出

- 最小代码变更和每个文件的职责；
- 实际验证命令、退出结果和证据；
- 覆盖的边缘场景；
- 未验证风险、偏离的默认实践及理由；
- Harness 同步结果。
