# Setup / Sync 统一契约

两入口共用本契约、同一套模板及只读检查器，不依赖彼此运行历史。setup建立/补齐；sync维护指定变化。普通局部修改直接更新Owner即可，不要求额外工作流。

## 目录与职责

```text
AGENTS.md                           启用后的真实项目入口（已有则保留）
docs/harness/
  AGENTS.md                         草案入口；启用后只指回真实入口
  rules/工程结构.md                   模块职责、依赖、运行链与改动落点
        编码规范.md                   项目特有写法、禁止项与最小正反例
        开发流程规范.md                阶段、产物、批准与交付责任
        测试规范.md                   按改动选验证、证据、操作边界
  wiki/业务模型.md                    能力、业务规则和主/错误路径
       领域术语.md                    有歧义的项目术语及名称对应
       数据模型.md                    数据/状态Owner、生命周期与隔离
       接口协议.md                    消费方必须知道的契约语义

docs/changes/
  README.md                         需求归档与规范变化的组织约定
  YYYY-MM-DD-主题/
    requirement.wl-req-confirm.md    需求唯一正文，HTML同源生成
    design.wl-design-doc.html        方案唯一正文
    test-cases.wl-qa-test-planner.md  具体身份、输入、样本、步骤与预期
    规范变更.md                       长期规则/重要边界或取舍变化时才需
    assets/                          有附件时才需
    test-runs/轮次/result.json       实际执行时才建，沿现有记录字段契约
                   evidence/        有截图/日志等原始证据才建
.harness-local/testing.md            个人测试入口卡（先核验忽略）
```

新建/获准统一的项目不另建ARCHITECTURE.md或CONTEXT.md：工程结构承接架构职责，领域术语承接名称与歧义，业务背景和范围归业务模型。已有正文先承接内容、修引用，依赖旧路径的入口只留薄指针；团队或未获迁移许可的原Owner继续复用，不自动删除或制造双正文。

不再生成docs/harness/changes、skills或agents。目录是允许的内容集合，不要求全部存在。新项目最小集是入口、开发流程、测试规范；无测试网址/账号也按[测试入口卡](testing-entry.md)保留最小地址表、可填写账号 JSON 和填写提示，未知值留空或标待填写，不造账号；已有账号索引只引用。工程结构/Wiki有依据才建。

`docs/changes`是新项目需求归宿，调用需求/设计/用例能力时明确传入该目录，不能让工具默认另建docs/requirements。已有需求路径保留，入口与开发流程映射其真实Owner；迁移需另获准，不能双写。需要规范变更记录时放同一需求目录。新项目的测试结果/证据也在该需求目录下，向测试执行方显式指定test-runs轮次目录，复用既有result.json格式而不是新造格式。目录归档不等于全部提交：需求、方案、用例和必要结论按项目约定跟踪；执行前确认test-runs原始响应、截图和日志的忽略或受控保存方式，提交前核对脱敏与暂存清单，不包含密码或登录态。已有执行记录保留原位置并引用，不复制迁移。新建目录用实际首次建立日期，不伪造业务发生时间，同日重名复用原目录或补有意义的主题，不反复编号复制。

## 同结构，不同内容

[共享模板](../assets/harness-template/)是标题、二级章节顺序的唯一标准；章内条目提供推荐格式而非强制字段。两Skill不得各自定义另一套格式：

- 新建或获准规范化的rules/Wiki：标题及二级章节顺序完全沿模板，不增删/改名；项目差异放三级及以下条目。无适用内容的章节写“不适用：理由”；未知写“待确认：具体问题与触发时点”，不留空和模板提示。
- 不需要的整份文件不建；目录完整不等于内容完整。共用模板不提供默认技术栈、数据库、响应包或架构分层。
- 每份开头用一行“范围：…；状态：当前/拟采用/混合；依据：…”说明适用范围。规则条目注明已确认/默认实践/待确认，事实附实际源码/配置/契约来源；有例外就写例外，不设中央规则ID或置信度账本。
- 二级以下按内容选择短段落、列表、表格或模板的详细条目。简单规则可一行写清适用范围、动作与依据，不强制正反例、多级标题和重复字段；只有容易误解的行为才补最小例子。复杂条目可沿模板字段展开，不再强制其标题与次序。只引用既有Owner时在固定章节说明来源与缺口。
- 每个事实只有一个裁决正文；同源生成物不独立编辑。已有OpenAPI/schema/架构说明继续拥有事实，Harness写必要任务摘要和指针，不抄全集。

rules 的[四份最小完整范文](../assets/rule-examples/)与 Wiki 的[四份最小完整范文](../assets/wiki-examples/)沿用同一个虚构的本地待办应用；生成或规范化某份规则或 Wiki 前，按模板链接只读对应范文，参照章节完整度、内容粒度及具体表达，不要求项目正文与范文等长或使用相同章内格式。范文不是可运行项目或已验证案例，其中的技术栈、路径、命令、规则与确认状态均不能作为目标项目事实；无依据时仍写具体未知或不生成该文件。范文位于模板目录之外，不随底座复制进目标项目。

模板中的括号提示必须以实际正文、不适用或具体未知替换。仅有相同标题仍可能内容空泛，须同时按[内容标准](content-standard.md)做代表任务回读；机械检查不能证明事实或业务正确。

## 既有项目和个人接入

模板结构变更属于显式协议修订：同时修改模板、独立测试预期和两入口的适用说明，列出受影响项目的迁移差异；不得通过同步业务内容悄悄改章名。未迁移的旧项目明确标结构不一致，不冒充跨版本通过。

对已有非标准资料，先确定正文位置与结构差异。获准整理时，将原内容完整映射进固定章节并修链接；旧消费者路径不便动则保留原路径。未获准改结构的外部Owner只映射，不要求改造，交付标“复用外部结构，未规范化”，不能当作统一结构通过。可对明确的现有文件运行检查器`--file`，无需复制到标准路径。

共享项目的个人结构在 `.harness-local/` 下使用同样的rules/wiki与AGENTS，需求笔记在 `.harness-local/changes/日期-主题/`；团队已有需求仍只引用。公共正文的原结构不受个人模板强制；个人只记录差异，方法见[个人接入](local-overlay.md)。

## 草案、启用与变化

需求批准、目标方案、当前实现、测试通过与发布分别表达。草案入口在docs/harness/AGENTS暂存，顶部必须声明“草案未启用，不覆盖根/子树现行规则”，正文只作为待确认材料，不得执行其中拟议规则。声明不保证宿主跳过此文件，不为验证自动加载而启用草案；只有用户确认/本轮明确委托覆盖的规则才启用。启用时保留原根规则并合并薄路由，暂存入口改为指回真实入口的短引用，不能同时维护两份根规则。overlay入口只有个人路由，不声称自动加载。

普通业务迭代按开发流程推进，不要求先启动setup。sync更新本次受影响的Owner；仅新增/调整长期规则、改变模块职责或关键契约、有须保留理由的重要取舍时才写同需求规范变更记录。局部修复、链接更正和不涉及上述变化的事实补齐直接改原文，不建记录，不将提交日志复制到文档。删除整份唯一历史、改业务代码、写库、安装、发布、自动提交均不包含在文档授权中。写入前核对当前内容与已读基线，冲突时合并或停止，不覆盖并发编辑。

## 验证与对接

两Skill均在生成/修改规则或Wiki后执行（路径为本Pack实际路径，不复制脚本进业务项目）：

```bash
python3 <pack>/scripts/check_structure.py <项目>/docs/harness
# 个人模式传 <项目>/.harness-local
# sync只核验本次受影响正文；已有Owner保留原路径也用此方式：
python3 <pack>/scripts/check_structure.py --file 编码规范.md <现有正文路径>
```

setup检查本次生成集，sync用--file仅检查本次影响的正文，不将无关历史问题升级为阻断。检查器只读，仅检查存在的标准正文；默认路径下非标准命名会报错（旧Owner可用--file映射），缺整份文件允许，实际检查数量会输出，零文件不算成功。校验标题、二级章节的精确顺序/唯一性、非空正文及模板提示；不强制章内条目字段或示例数量；不读取账号卡、不写文件、不证明秘密保护或真实契约。错误必须报告并修本次引入的差异；未获准修的历史差异单列。

再走三条最小读取链：找改动点（无源码明确未知）、开始需求（实际归宿与批准边界）、准备测试（网址和账号入口，不能把登记当登录成功）。检查链接指向真实文件、状态无自相矛盾、共享文档无秘密值。相同输入重跑不重复正文/记录、不重写批准。未核验运行行为、宿主自动加载或凭据就分别标明，不扩大为业务测试。
