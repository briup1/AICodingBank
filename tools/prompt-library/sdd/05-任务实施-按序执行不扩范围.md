# 05 任务实施：按序执行，不扩范围

**什么时候用**：tasks.md 已确认，进入实际编码
**什么时候别用**：任务清单还没定；只是探索性试验代码
**产出**：代码改动 + 每个任务的完成报告（改了哪些文件、跑了哪些测试、结果、遗留）
**状态**：未实测（2026-11-09 入库）

---

```text
现在开始按照 tasks.md 执行开发。请严格遵循 spec.md、plan.md 和项目级工程规范。

要求：
1. 按照任务依赖顺序执行。
2. 修改代码之前先检查现有实现。
3. 优先复用已有模块和组件。
4. 不得擅自改变业务规则和技术约束。
5. 不得擅自扩大本次开发范围。
6. 每完成一个任务，执行对应的测试。
7. 发现 Spec 存在缺失或技术设计存在冲突时，暂停相关工作并报告。
8. 更新 tasks.md 中的完成状态。

每个任务完成后，输出：
1. 修改了哪些文件。
2. 实现了哪些功能。
3. 执行了哪些测试。
4. 测试结果。
5. 是否存在遗留问题。

不要仅生成代码片段，必须实际修改项目文件并运行验证。
```

## 原文附带的并行建议

- 小任务交给单个 Agent；相互独立的任务可以并行。
- 存在共享文件、数据库结构或接口依赖的任务，应控制并行度。
- 关键架构变更、数据迁移和权限逻辑必须人工审核。

---

## 差异

`wl-auto-delivery` 已覆盖执行与证据要求。本条可借鉴的具体条款：
**第 7 条「发现 Spec 缺失就暂停并报告」**——把"卡住"变成合法动作，
而不是让模型自行补全后继续跑。
