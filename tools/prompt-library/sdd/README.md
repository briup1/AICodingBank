# Spec 驱动开发（SDD）

**出处**：《Spec 驱动开发（SDD）实战指南》，公众号文章
<https://mp.weixin.qq.com/s/d6qMg9T4K-zO4MSr0cbM9A>，2026-11-09 入库。

**核心主张**：在写代码之前，先把需求、行为、约束、接口和验收标准定义清楚，再让 AI 按规范开发。
流程是 需求分析 → Spec → 技术设计 → 任务拆解 → AI 实施 → 测试验收。

**适用前提**：需求边界清楚、能事先写出可验收的规范。探索型任务（还不知道要做什么）不适用。

**规模分档**（原文给的判断，可直接用）：

| 任务规模 | 采用多少流程 |
| --- | --- |
| 简单修改 | 直接提示词 + 测试 |
| 普通功能 | Spec + Plan + Tasks + Implement |
| 复杂模块 | 完整 SDD + 自动化测试 + 人工审核 |
| 核心架构变更 | 加架构决策记录、安全审查、迁移验证 |

## 读这套的结论

6 条里 4 条你已经有对应 Skill。**真正值得带走的只有两样**：

1. 需求追踪矩阵（需求 ID ｜ 实现位置 ｜ 测试用例 ｜ 验收结果）—— 全库 grep 无命中，是可补的缺口。
2. 「提问时机」这处取舍 —— 原文主张规则未定就先问、禁止推断；`wl-req-confirm` 主张先读完材料再提问。
   两者不必然冲突（读完材料再问 ≠ 不问），但优先级需要定一次，别两处各说各话。

其余 4 条留在这里当参照：以后遇到同类文章，先对照本表，不再重复收录。
