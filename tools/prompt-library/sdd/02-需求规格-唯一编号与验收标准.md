# 02 需求规格：唯一编号与验收标准

**什么时候用**：需求确认完了，要落成一份实现和验收共用的契约
**什么时候别用**：只需要口头结论；需求本身已经是技术方案
**产出**：spec.md（概述／用户故事／功能需求／业务规则／异常／验收标准）
**状态**：格式参照，未在本工作台实测

---

## 骨架

```markdown
## 1. Overview
实现多租户 Agent 会话管理。

## 2. User Stories
- 用户可以创建 Agent Session。
- 用户可以查询自己的 Session。
- 用户可以删除自己的 Session。

## 3. Functional Requirements
FR-001：创建 Session
- 用户必须指定 Agent ID。
- 系统必须验证 Agent 是否存在。
- 创建成功后返回 Session ID。

FR-002：查询 Session
- 用户只能查询自己所属 Tenant 的 Session。
- 不允许跨租户访问。

## 4. Business Rules
- 每个 Session 必须归属于一个 Tenant。
- 每个 Session 必须关联一个 Agent。
- Session 创建后不能修改所属 Tenant。

## 5. Exception Handling
- Agent 不存在：返回 404。
- 无权访问：返回 403。
- 数据库异常：返回统一错误响应。

## 6. Acceptance Criteria
- 可以正常创建 Session。
- 不允许跨租户访问。
- 非法参数能够被正确识别。
- 并发更新不能造成状态覆盖。
```

## 编写要点

- 每条需求有唯一 ID；每条描述明确的系统行为。
- 业务规则不能留给 AI 猜测；正常流程和异常流程都要覆盖。
- 每条重要需求都能对应验收条件。
- 不追求越详细越好，只写对实现和验收真正有约束力的内容。
- 一个 Spec 对应一个需求或功能变更，不是一个项目的全部需求。

## 差异

这是需求契约的结构模板，不是可执行提示词。`wl-req-confirm` 已承担同类产物，
本条价值在**第 5、6 节固定成骨架**和 FR-001 编号格式——编号是 06 追踪矩阵的前置条件。
