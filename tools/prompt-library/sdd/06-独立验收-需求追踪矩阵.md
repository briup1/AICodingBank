# 06 独立验收：需求追踪矩阵

**什么时候用**：开发自称完成，需要对照原始 Spec 做验收
**什么时候别用**：开发还在进行中；刚才是同一方自己检查自己
**产出**：需求追踪矩阵 + 缺陷清单 + 修复后重测结果
**状态**：未实测（2026-11-09 入库）· 本套里唯一确认的差量

---

```text
现在请作为独立的软件质量工程师，对本次开发进行验收。不要假设开发阶段生成的代码是正确的。
请重新阅读 spec.md、plan.md 和 tasks.md，并检查实际代码。

重点检查：
1. 每条功能需求是否完整实现？
2. 是否存在业务逻辑错误？
3. 是否存在权限和数据隔离漏洞？
4. 是否存在异常处理遗漏？
5. 是否存在并发和事务问题？
6. 是否存在性能和资源管理问题？
7. 是否符合原有架构和技术规范？
8. 自动化测试是否覆盖关键验收条件？

执行必要的静态检查、单元测试和集成测试。

输出需求追踪矩阵：
| 需求 ID | 实现位置 | 测试用例 | 验收结果 |

对于未通过的项目，列出缺陷、影响和修复建议。
修复完成后重新执行测试，直到满足验收条件，或者明确报告无法解决的问题。
```

---

## 差异（这是真差量）

「需求追踪矩阵」四列结构在本工作台全库 grep 无命中，`wl-requesting-code-review`
和 `at-review` 都没有等价要求。可考虑补进现有审查链路，而不是新建 Skill。

前提是 02 有需求编号、04 有任务↔需求关联——矩阵不可能凭空生成。
这也说明这套方法是一条链，单独抽第 06 条用不了。

另一句关键约束：**「不要假设开发阶段生成的代码是正确的」**——
把验收方和被验收方在提示层面强制分开，避免自证。
