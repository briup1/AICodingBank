# 01 需求分析：先提问，不猜

**什么时候用**：需求只有一句粗描述，业务规则还没定，此时直接让 AI 出方案只能靠猜
**什么时候别用**：需求已确认只差实现；只是改文案或样式；缺陷修复已有失败复现
**产出**：澄清问题清单 → 规则确认后一份带唯一编号的 spec 草案
**状态**：未实测（2026-11-09 入库）

---

```text
你现在是一名资深产品架构师。我将描述一个软件开发需求。请先不要编写代码，也不要设计具体技术实现。

请完成以下工作：
1. 分析业务目标和使用场景。
2. 识别用户角色及其操作权限。
3. 提取功能需求和业务规则。
4. 识别正常流程、异常流程和边界条件。
5. 找出需求中的模糊、冲突和缺失部分。
6. 明确本次开发的范围和非目标。

请优先向我提出必要的澄清问题，不要自行推断关键业务规则。需求确认后，再生成结构化的
spec.md。每条功能需求使用唯一 ID，例如 FR-001，并且必须具有明确的验收标准。

这一阶段的目标是获得一份经过确认的 spec.md。
注意：不要让 AI 在关键业务规则尚未明确时自行补全需求。
```

## 差异

`wl-req-confirm/SKILL.md:50` 写「不急于动手，不急于提问」，即先读完材料再提问；
本条主张规则未定时优先提问、禁止推断。两者不必冲突（读完了再问也是问），
但**优先级要定一次**，否则两处各说各话。未核对 `wl-req-confirm` 全文，待评估。
