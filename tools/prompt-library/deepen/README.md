# 更深入，而不是更大

**出处**：用户 2026-11-09 提供，原始出处未标注。

**核心主张**：要让一版需求变强，不是加篇幅、加条目，而是**提高判断标准**——先问
“这一行的顶尖专家会怎么做”，再回头改题目。

**适用前提**：你已经有初版题目或需求，正准备让 AI 重写。什么都没有的时候不适用，
那时该先做澄清。

## 适用领域

它不描述内容，只描述“判断标准从哪来”，所以四问换成四个可填槽位：专家超出你要求的动作、
最原始的一手素材、具体方法与工具、你我之外的第三方证据。适用条件因此是两条：
**存在专业梯度**，且**结果能被外部核验**。

第 1、3 问多数领域答案雷同，真正决定效果的是第 2、4 问填什么：

| 领域与场景 | 第 2 问的「原始素材」 | 第 4 问的「第三方证据」 |
| --- | --- | --- |
| 需求与产品 | 真实操作录屏、工单原文、埋点原始日志 | 用户能否自己走完流程；可复算的转化数据 |
| 技术选型与架构 | 现网指标、慢查询日志、真实流量采样 | 压测可复现、改动可回滚、关键路径可测 |
| 缺陷排查 | 未加工的报错原文、完整日志、最小复现输入 | 同一输入修复前失败、修复后通过 |
| 数据分析与报告 | 自己导出的一手明细表 | 别人拿同一份原始数据能否算出同一结论 |
| 写作与内容 | 一手访谈、原始材料、自己的初稿 | 读者能否复述核心结论；事实能否逐条溯源 |
| 招聘与面试 | 真实工作样本，而非简历自述 | 同一标准下另一位面试官独立打分是否收敛 |
| 学习与研究 | 论文原文、官方文档，而非二手解读 | 能否复现实验或跑通官方示例 |
| 方案对比与决策 | 各方案的一手成本数据 | 决策时给出的具体预测事后能否复盘 |
| 测试用例设计 | 真实缺陷记录，而非需求文档转述 | 用例在被打回的版本上是否会失败 |
| 复盘与总结 | 当时的原始记录（聊天、日志、邮件） | 结论能否被当事人以外的记录佐证 |

一句话：**这四问不会自动让你变深，能拿出什么当「原始」和「第三方」才会。**
拿不出来时，它只会给你一份更漂亮、同样空洞的成品。

## 不适用

| 场景 | 原因 |
| --- | --- |
| 简单事实查询 | 无专业梯度，四问均得空答 |
| 已有明确规范的执行（按模板填表） | 标准外部给定，不需要“专家会做什么” |
| 纯审美偏好 | 无第三方证据可核，只有你的偏好 |
| 线上故障处置、紧急恢复 | 不能为了深入而延误，先恢复再深挖 |
| 合规与法规类 | 标准由外部规定，第 1 问容易让模型编造“专家通常还会……” |

## 读这套的结论

四问里最难、也最值钱的是第 2 和第 4 问：

- **第 2 问要“最原始的素材”**——它逼你交出未加工的一手材料。你一交出整理好的二手结论，
  模型就只能在你已有的框里打转，深度上不去。
- **第 4 问要“你我之外的证据”**——和 `sdd/06-独立验收-需求追踪矩阵` 是同一个思路：
  自己说对不算对，得有第三方能核的东西。

第 1 问（专家会做什么我没要求的事）最容易得到漂亮但空泛的答案，需要你反手追问
“具体到哪一步、交付物长什么样”，否则只会收到一份行业吹捧。
