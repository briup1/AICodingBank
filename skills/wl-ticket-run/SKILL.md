# 工单执行（wl-ticket-run）

开发流程的第三阶段。目标是在保留需求追踪和验收边界的同时，减少重复读取上下文、重复测试和重复审查，自动执行到验收。

**前置条件**：`design.md` 状态为 `approved`；多方案场景下已有选定方案（`chosen`）。

## 核心模型

不要把 Ticket、Agent 和执行生命周期绑定为一对一：

- **Ticket**：一个可观察、可验收的需求结果，负责追踪范围和 G/W/T。
- **执行工作包（execution group）**：一组高耦合 Ticket，是 Agent 分配、`/goal`、统一测试和 Review 的基本单位。
- **内部步骤**：工作包内的实现顺序，没有独立业务结果时不单独建 Ticket、不分配新 Agent。
- **Gate**：统一测试、Code Review、Beta/生产验证、发布审批等门禁，不作为普通编码 Ticket。

```text
approved design
  → 影响域与耦合分析
  → 拆分可验收 Ticket
  → 合并为执行工作包
  → 工作包内串行开发
  → 工作包级统一测试 + Review
  → 全局回归与外部验证 Gate
```

## 第一步：分析影响域

拆票前先读取仓库规则、设计、现有代码和工作区状态，列出：

- 受影响的业务链路、接口、数据模型、核心模块和非功能约束；
- 预计修改文件与已有未提交改动；
- Ticket 间的依赖、共享文件、共享夹具和发布关系；
- 可量化的成功标准、风险操作和外部验证项。

先画依赖与耦合关系，再决定拆分；不要根据章节数、技术层数或设计文档的小标题机械拆票。

```text
单一、内聚的结果             → 少拆或不拆 → 1 个执行工作包
多个结果但共享核心写集       → 多 Ticket  → 1 个执行工作包串行开发
多个结果且契约稳定、写集分离 → 多工作包    → 可并行开发
跨库迁移或宽重构             → 分阶段      → 按依赖串行推进
```

## 第二步：拆分 Ticket

### 默认按纵向业务结果拆分

优先按用户可观察、可独立验收的纵向结果拆分，使每张 Ticket 尽量贯穿实现所需的层，而不是按 Controller、Service、Repository、前端、后端等技术条线横切。

允许技术阶段拆分的例外：

- 跨库宽重构或数据迁移，需要 expand–migrate–contract；
- 共享基础能力本身具有稳定契约和独立验收结果；
- 仓库文件数、风险或上下文限制要求分阶段推进。

即使采用技术阶段，也应围绕稳定接口和可验证结果组织，不能产生只有“写了一层代码”但无法验收的 Ticket。

### Ticket 内容

每张 Ticket 必须包含：

- 业务结果和范围；
- blocking edges；
- 明确的 Out of Scope；
- 可验证的 G/W/T 验收标准；
- 预计影响文件或模块；
- 风险和必要的外部 Gate。

```text
- [ ] Given <前置状态>, When <动作>, Then <可观察结果>
```

需求约束也必须写成验收项。Ticket 的大小以“边界清晰、可验收、可追踪”为准，不以“必须对应一个新 Agent 或一个上下文窗口”为准。

## 第三步：组合执行工作包

新生成或已有的 Ticket 都必须先分组，禁止默认一票一 Agent。

### 默认合并到同一工作包

满足任一条件时优先合并并由同一持续 Agent 串行实现：

- 修改同一接口、数据模型、核心链路或核心模块；
- 大量共享写入文件、测试夹具或运行上下文；
- 后一 Ticket 必然继续修改或推翻前一 Ticket；
- 单张 Ticket 完成后没有完整可用价值；
- 必须一起发布、回滚或验收；
- 契约尚未稳定，跨 Agent 会增加沟通和集成成本。

高耦合但规模较大的任务可以拆成多个串行 Ticket 或内部阶段，但仍由同一实现 Agent 持续负责；只有超过仓库限制或上下文明显无法承载时才拆成新的工作包。

### 允许分成不同工作包

只有同时基本满足以下条件，才值得分配不同 Agent 或并行开发：

- 各自有独立可观察结果和独立测试方法；
- 输入输出契约已经冻结；
- 写入文件范围基本不重叠；
- 不依赖对方的中间实现状态；
- 可以独立失败、回滚或延期；
- 并行收益明显高于上下文同步、合并冲突和集成成本。

按业务域或“条线”切分只是候选方式，不是目标；最终依据是验收独立性、耦合度、写集冲突、风险隔离和集成成本。

### 记录执行计划

在 Ticket 目录维护简短执行计划，至少记录：

- 工作包包含的 Ticket；
- 工作包间依赖和是否允许并行；
- 每个工作包的预计写入范围；
- 实现 Agent、统一测试/Review Gate 和外部 Gate。

如已有细粒度 Ticket，保留其编号和验收追踪，只调整执行分组，不必为合并开发重写全部 Ticket。

## 第四步：分配与执行

- 一个执行工作包只分配一个持续实现 Agent，并使用一个 `/goal`；goal 聚合组内全部 Ticket 的 G/W/T。
- 工作包内按依赖串行开发，不在每张 Ticket 后重启完整测试和 Review 生命周期。
- 低耦合工作包才可进入 `/list` 并行；存在共享写集或不稳定契约时必须串行。
- 同形状的小改动合并为一次派发，不创建多个 Agent。
- 实现中发现问题，交回原实现 Agent 修复；不要新建替代实现 Agent 重新读取上下文。
- 测试和审查 Agent 只在统一门禁阶段介入；多个独立审查视角可以并行。

如果项目或需求要求 TDD，在工作包开始时先建立覆盖整个工作包的测试矩阵并写出失败测试，再串行完成组内实现；不要为每张细 Ticket 重复创建“失败测试 → 实现 → 全量回归 → Review”的独立生命周期。

### 执行纪律

1. **台账**：在需求或 Ticket 目录维护共享 `progress.md`，记录完成项、验证证据和决策。未获授权不得自行 commit；无 commit 时记录 diff、命令或文件证据。
2. **熔断**：同一问题连续修 3 次不过，暂停并上报，不无限重试。
3. **停机**：仅在不可逆操作、安全敏感动作、仓库外副作用、契约不清或所有路径都依赖猜测时询问用户。
4. **默认自动推进**：不在每次拆票或分组后要求人工确认。只有分组方案存在显著成本差异、多个工作包争用同一核心写集、超过仓库限制或涉及外部高风险操作时才确认。
5. **保护工作区**：不覆盖、回退或夹带用户及其他任务的已有改动。

## 第五步：统一测试与 Review

测试和 Review 的门禁粒度是执行工作包，不是单张 Ticket：

1. 组内所有 Ticket 的实现串行完成；开发期间只运行必要的快速反馈测试。
2. 一次性运行工作包聚焦测试和相关回归，并逐条审计聚合后的 G/W/T。
3. 启动统一 Code Review；测试与独立审查可并行。
4. 问题全部交回原实现 Agent 集中修复，再统一复测和复审受影响部分。
5. 所有工作包稳定后，运行需求级全量回归、端到端场景和边界测试。
6. Beta、生产、发布或真实外部写入只进入相应 Gate，按授权执行；不能执行时给出可操作的人工验证路径。

声称完成前必须提供实际命令和结果，不得使用“应该通过”。全部验收完成后再将需求状态置为 `done` 并回写总览。

## 切分与分组的目的

- 让需求结果可追踪、可验收；
- 让同一上下文和同一写集尽量由一个 Agent 连续负责；
- 只在安全且有净收益时并行；
- 降低重复读仓库、重复测试、重复 Review 和合并冲突；
- 控制单次修改规模、失败影响面和回滚成本；
- 把编码、验证、发布等不同性质的工作放入正确生命周期。

## 禁止事项

- 按设计章节或技术层机械拆票；
- 默认一张 Ticket 对应一个 Agent、一个 `/goal` 和一轮完整门禁；
- 高耦合 Ticket 分配给不同实现 Agent；
- 工作包内并行修改同一写集；
- 每完成一张细 Ticket 就重复全量测试和 Code Review；
- 跳过 G/W/T、台账或真实验证；
- 熔断后继续重试；
- 未经授权执行不可逆、生产、发布或仓库外写操作；
- 虚报完工。
