# 阶段路由

以用户本次希望得到的结果为主，以已有证据为辅。**一次请求只选择一个当前阶段**；完成后再决定是否进入下一阶段。没有实际证据，不得宣称阶段完成。

```text
理解事实？ --------> Observe / 观察
确认目标？ --------> Confirm / 确认
决定做法？ --------> Design / 设计
产生改动？ --------> Execute / 执行
证明正确？ --------> Verify / 验证
保存经验？ --------> Learn / 沉淀
```

| 阶段 | 何时进入 | 完成证据 | 优先复用 |
| --- | --- | --- | --- |
| **Observe / 观察** | 用户只想了解项目、现象、资料或历史，不要求持久变更 | 基于真实文件、命令或可信来源的事实结论 | 项目阅读、调研、诊断能力 |
| **Confirm / 确认** | 新需求或行为变化的目标、边界、价值、验收尚未确认 | 已批准需求，或清晰且可验收的小任务边界 | `wl-req-confirm`、`wl-brainstorming` |
| **Design / 设计** | 目标已稳定，但接口、复用、风险或实施路径仍未确定 | 已批准方案；简单任务则为用户批准的最小方法 | `wl-design-doc`、`wl-writing-plans`、方案审查类 Skill |
| **Execute / 执行** | 用户要求产生改动，且目标与修改边界已经稳定 | 实际产物、命令结果和范围证据 | `wl-ticket-run`、`wl-subagent-driven-development`、`wl-investigate` |
| **Verify / 验证** | 已有实现或产物，需要判断正确性、质量或是否可交付 | 实际测试、审查或验收结果 | `wl-requesting-code-review`、测试与浏览器验证能力 |
| **Learn / 沉淀** | 已验证结论具有跨会话或跨项目复用价值 | 写入适当的 Memory、知识库或项目文档 | EXTENDING.md 分类树 |

判断冲突时依次裁决：

```text
用户明确指定阶段
  -> 已批准文档或既有任务状态
  -> 用户本次希望得到的结果
  -> 仍无法唯一判断时，只问一个会改变阶段的澄清问题
```

阶段不是必须走满的流水线：

- 只读问题可在 Observe 结束。
- 范围明确的简单操作可直接进入 Execute，但写代码前仍说明最小方法并获得批准。
- Bug 修复属于 Execute，内部先复现、再修复、再验证。
- 提交、部署等操作可直接进入 Execute，但必须遵守授权和安全边界。

进入阶段后，从当前宿主的可用能力列表中选择**最小能力组合**，按需加载对应 Skill，不全量加载。
