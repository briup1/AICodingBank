# 需求确认（wl-req-confirm）

开发流程的第一阶段。目标：先查清系统现在怎么运转，再把“为什么改、哪里变、结果是什么、如何验收”变成一份人审批准的文档。现状、新旧对照与差异清单属于这份文档，不另建独立讲解 HTML。

**为什么**：返工最贵的根源不是代码写错，而是需求理解错——照单执行了一个本可被质疑推翻的方案。本 skill 的核心价值在"质疑需求本身"。

**职责范围（先划边界，再走流程）**：本阶段只回答三个问题——**要什么**（What）、**为什么**（Why）、**怎么算完成**（验收）。**不决定“怎么实现”**（How）：技术选型、未来架构与模块划分、接口定义、参数取值属于方案设计。允许读取现有架构、CodeGraph 和源码核实业务链路；调研依据不等于提前决定实现。

### 固定边界：按表执行，不凭“像不像技术”判断

对准备写入的每一项内容，按下表自上而下分类；命中后执行对应动作。**无法归类默认放入待确认 Q，不自行扩展白名单。**读代码只改变证据来源，不改变内容归属。

| 内容命中条件 | 本阶段固定动作 | 允许的表达例子 |
|---|---|---|
| 定义未来的函数、类、接口签名、数据库表结构、框架、中间件、线程/队列、重试/缓存参数 | 不进入需求正文；来源索引标“实现候选，留待设计”，不作选型 | 不写“新增某表/使用线程池”；仅保留背后的业务目标 |
| 本需求的业务对象/术语、参与人、判断条件、业务字段含义、步骤顺序、业务状态、业务记录或结果 | 必须在对应业务节点或规则解释；附证据，未知则 Q | “结算单位是谁、依据什么确定”“谁申请开票、谁审核、何时算已开票” |
| 已核验的现有行为，不论通过页面、代码还是运行证据查到 | 写入现状；明确证据类型及基线，不升级为已确认的未来规则 | “当前代码路径为申请→审核→开票”；没有运行证据不写“线上已验证” |
| 原文或用户明确提出的目标行为、业务约束 | 写入目标与差异；保留来源和确认状态，不自动批准 | “审核通过后才允许开票”；未确认的产品要求仍标待评审 |
| 源码文件路径、commit、CodeGraph 节点等定位信息 | 仅写证据索引，正文引用 E 编号；不展开函数级调用图 | E01 指向核对过的代码位置 |
| 与本需求无关的业务概念或技术细节 | 不扩展调查，不放入正文 | 不为解释开票而全量介绍财务系统 |
| 材料冲突、关键条件缺失、动机推测或不能归入以上类别 | 记录 Q、影响的 D/AC 和需确认的问题；不填写确定结论 | “结算单位有两个候选，选择依据未知” |

混合句先拆开再分类。例如“审核通过后写入新建发票表”：保留“审核通过后产生开票记录”这一已明确的业务要求，表结构留给设计。不能因含有技术词把整条业务规则删掉，也不能借“业务流程”之名保留实现选择。

核心业务概念首次出现时，在对应节点用“它指什么 → 本次由谁/按什么规则决定 → 对后续有什么影响”解释，并给一个引用 AC 的最小例子；无依据的部分写 Q。术语定义的唯一归宿仍遵守第 5 步，不另建重复术语表。

**出口条件**：需求文档被用户明确批准（frontmatter `status` 置为 `approved`）。未批准前，禁止进入方案设计。

## 流程

### 1. 看全貌
读完用户提供的全部需求材料（口述、文档、链接）。不急于动手，不急于提问。

### 2. 调研现状：先立足当前，再看未来
从入口到结果查清本次需求触及的链路，不全库扫描，也不只复述 PRD：

1. 读取项目约束、Wiki/README、已有结构图或业务流程图，定位相关入口、参与方和上下游。检查资料的版本；架构图是线索，不自动等于现状。
2. 有 `.codegraph/` 或项目指定的图工具时，按项目规则优先用 `explore/search/callers/impact/node` 定位相关链路，再定点补读未覆盖的源码、配置或测试。图中已返回的源码不重复读取。核对图与当前代码基线；图不可用、过期或不完整时说明局限，按项目允许的只读方式补证，不伪称已调用工具。
3. 有 UI 时，运行获准访问的现有页面并实拍关键状态；后端行为沿实际入口核实分支、执行顺序及记录结果。静态阅读不能证明已经部署、真实调用成功或运行时一定并行；必要时用获准的只读日志、测试等补证。未经授权不提交业务表单、写真实数据或启动外部服务来取证。
4. 用 `E01…` 记录证据类型、环境/分支/commit 或材料版本、采集时间、场景、定位及局限。正文区分“运行观察”“当前代码可确认”“历史原型”“目标示意”“推断/待核验”。PRD 声称“线上事实”、历史截图、代码可达，都不能替代当前环境核验。
5. 先写出一条宏观的**现状链路**和最小例子，再解释产品为什么要改。无法核实的节点标未知，说明缺少的证据及其对需求判断的影响；只能交付带缺口的草稿，不能用猜测补齐旧流程。全新能力写明“当前无此能力/入口”的依据，不虚构旧页面。

### 2.1 新旧对照与全量差异：本阶段的必需内容
先检查两个固定条件，不能凭“这个需求复杂不复杂”自行选择：

- **U（界面变化）**：需求明确增删改页面、可见文案/字段、展示状态、按钮、交互入口之一。
- **B（行为变化）**：需求明确改变业务判断、计算结果、步骤先后/独立办理、状态变化、记录生成/查询口径、通知对象或触发条件之一。按钮只改文案属于 U；按钮改去向或改变记录也命中 B。

| 条件 | 必须交付 | 不执行 |
|---|---|---|
| U=是，B=否 | 原页面/目标页面对照、D→AC；保留该页面在现有链路的位置 | 不新增无关后端流程图 |
| U=否，B=是 | 旧/新业务流程对照、D→AC | 不伪造 UI 截图 |
| U=是，B=是 | 页面与业务流程两种对照，共用 D→AC | 不用截图替代按钮后的业务结果 |
| 任一条件无法确定 | 已确定的部分照做；未知项记 Q，文档保持 draft | 不把未知当“否”，不补造对照 |
| U=否，B=否 | 写明材料没有提出上述变化，列 Q 确认需求目标 | 不虚构新功能或差异 |

对照资料不足时也按固定降级处理：
- 没有可核验的旧页面/旧流程：显示“现状未核验 + 缺少什么证据”，不画猜测版旧系统。只有已证实的新能力才写“无旧入口”。
- 没有目标页面：默认显示“目标页面待补”，先在 D 中记录明确的可见变化；**只有用户明确要求制作目标示意时**才在隔离副本中演示，未明确的布局/交互仍不补定。
- 目标节点、条件、顺序或失败结果未明确：相应位置标 Q，不连出确定路径。其余有依据的目标链路可以继续写。
- 串行改并行：只有原文/用户明确要求业务可独立办理时才画并行；是否等待全部完成、失败如何处理分别核对。不得以性能优化为由主动改图。

**UI：原样的系统与目标变化放在一起。**
- 改前优先使用所针对环境的真实页面；只有本地页面或历史原型时，标清版本和局限，不能称为当前线上。目标截图使用已有目标原型；缺稿与隔离示意按上面的固定降级规则处理。所有目标画面标“目标原型/目标示意”及确认状态，不得冒充实现或已批准的设计。
- 保留原布局、字段、按钮和上下文，不用重画的简化卡片冒充旧系统。围绕同一业务场景，尽量使用相同数据、视口及页面位置；样例、日期、数据集不同或混入关联需求时逐项说明，不能把价格/数量/顺序差异全部归因于本需求。
- 覆盖受影响的关键可见状态与按钮后的去向，如列表、详情、弹层/表单、状态提示及后台记录。截图表达不了的动作、记录和状态，用下面的流程补齐。隐私数据最小化，必要脱敏要标明，不修改承担比较结论的字段；不额外开放页面分享。

**业务逻辑：旧流程与目标流程并列，不把后端硬画成 UI。**
- 以“谁发起 → 业务步骤 → 条件/分支 → 记录或状态 → 谁得到什么结果”为骨架；节点使用业务用语。沿用相同节点编号 `N01…` 和方向，显式标新增、修改、删除、保持。默认文字流程图，HTML 可渲染对应图形；用户未要求时不用 Mermaid。
- 明确顺序、并行、汇合及必要的异常路径；每个改动节点引用差异编号，并给最小输入/动作与新旧结果（完整验收样例只写一次）。按钮不能只连到“成功”：还要交代是否跳转、何时记点击、何时算正式提交等实际涉及的业务结果。
- 旧图根据调查证据画；目标图根据原文或用户确认画。不能因“看起来更快”自行把串行改并行。并行只是技术实现的候选、且不改变已要求的可观察行为时，留给设计阶段；目标缺依据则标待确认，不冒充未来事实。

例如，只有材料明确要求两项业务可独立办理并在两者完成后增加汇总时，才能这样表达（仅示例，不是默认方案）：

```text
改前：N01 接收 → N02 核对资料 → N03 核算金额 → 返回结果
改后：N01 接收 ─┬→ N02 核对资料 ─┐
               └→ N03 核算金额 ─┴→ N04 汇总〔新增〕→ 返回结果
变化：N02/N03 从先后变为独立办理；N04 等两项完成再汇总。
样例：同一份申请的资料和金额核对都完成后才给最终结果；一项失败如何处理单独确认。
```

**全量差异：使需求可核对，也能转成验收。**
- 逐项回查所有需求材料和现状证据，列 `D01…`：增/删/改/保持、所在页面或业务节点、旧行为、目标行为、下游结果、证据/确认状态、规则 `R…` 与验收 `AC…` 引用。全量是本需求范围，不是罗列全系统。
- 不漏 UI 之外的筛选、导出、记录类型、历史数据口径、状态、异常与必要“不应改变”项。没有旧证据写“未核验”，不是“旧版没有”；未确认的目标链接 `Q…`，不要编造确定的验收预期。
- 原文每个独立要求都应落到差异项、排除项或待确认项；每个差异项都有相应验收场景或明确的待确认阻塞。可多对多，不为了凑一对一拆出重复用例。差异项写最小新旧结果，完整前提/操作/断言只在验收章节维护。

以上内容直接进入 `requirement.wl-req-confirm.md` 与对应 HTML；图片是附件，图形与表格是正文的另一种呈现，不建立平行事实来源。

### 2.2 先分配内容归属，禁止同义扩写
生成前先给信息确定唯一归属，再组织章节；不是把源材料按不同标题复述多遍。下列职责可合并或省略空章节，不强制凑数量：

| 内容 | 唯一完整正文 | 其他位置怎么用 |
|---|---|---|
| 目标、价值、质疑 | 需求重定义 | 阅读说明仅导航，不再复述范围或规则 |
| 角色与收益 | 用户故事 | 不逐条复制字段、校验与验收结果 |
| 通用业务约束、字段和状态 | 业务规则；简单需求可直接置于需求重定义 | 给规则稳定编号，其他章节引用；不把具体输入输出抄回规则 |
| 已核验现状与局限 | 现状链路；证据位置统一放证据索引 | 先让读者看到现在怎么运转，再讲为什么；动机不重抄现状 |
| 新旧变化、影响 | 新旧页面/流程对照 + 全量差异清单 | 图与截图标注 D 编号；差异行引用规则与验收，不另写完整样例副本 |
| 不做及延期范围 | Out of Scope | 验收不再次描述范围外功能的目标行为 |
| 具体前提、操作与成功标准 | 唯一的“具体验收场景”章节 | “验证方案/验收标准/参考示例/测试场景”等近义栏目合并；其他位置只放编号或链接 |
| 材料来源与未决事项 | 来源/待确认 | 来源说明不重述业务正文；未决问题引用规则/样例，不再复制预期结果 |

重复的判断是：相同适用条件下，同一约束、输入输出或结论在多处完整出现，或只换了措辞而没有新增信息。规则与证明它的实例不是重复；不同角色、状态、边界、失败路径有不同验收意义时不得误删。为独立理解样例而保留必要上下文和字段名是允许的。

### 3. 重定义需求（本 skill 的招牌环节，禁止跳过）
回答三个问题并写进文档：

1. 提出需求的人，**最终目标**是什么？（不是他描述的方案，是他要的结果）
2. 当前需求描述的方式，是达成最终目标的**最佳方式**吗？
3. 如果不是——**提出异议**，给出更好的路径和理由，显式挂在文档里等需求方确认。未发现替代方案时写“在已核验范围内暂未发现替代路径”，并列出限制；证据不足写待确认，不能默认宣称“已求证、最佳”。

### 4. 方案剥离（源材料夹带方案时的必经处置）
现实中的需求材料（尤其是 PRD）几乎必然夹带方案层内容：技术选型、模块名、配置结构、参数建议值。**禁止誊抄进需求文档**，按三类分流：

1. **方案背后的真实意图** → 提炼为需求或客观约束（例：PRD 写"实现 docker provider"→ 需求是"脚本与宿主机文件系统/网络隔离"，约束是"部署环境无 Docker"）；
2. **方案本身** → 作为候选参考原样移交方案设计阶段，需求文档中至多一句"实现选型留待设计"；
3. **被否决的方向** → 写入 Out of Scope 封存，防下游滑回旧方案。

### 5. 术语沉淀
对话中说清的领域术语，当场写入项目根目录 `CONTEXT.md`（只放术语，不放实现细节）。用户用词与术语表冲突、或与代码矛盾时，立刻质问澄清，不带入下游。

### 6. 拆分用户故事
用 Matt 式格式穷举，每条讲清价值：

```
As a <角色>, I want <能力>, so that <价值>
```

写不出 so that 的故事，说明价值存疑——回第 3 步质疑。故事中出现技术选型、组件名、配置项 = 越界，同样回炉重写。用户故事用 Matt 式对齐价值；第 8 步用普通场景表明确验收结果，正式 G/W/T 格式与工单拆分留给工单阶段。

### 7. 明确不做什么（Out of Scope）
逐项列出本期不做的事。被否决的方案方向也写进来（防下游讨论滑回旧方案）。

### 8. 具体验收场景（唯一验收正文）
每个可观察的核心规则都要有具体场景证明，不能只写“功能正常”“字段正确”。原始需求已有示例时合并、补齐和追溯来源；没有示例时主动由规则推导，不要求用户先写测试用例。表格字段见下方产出模板；每条预期结果同时写明必要的禁止副作用。

推导方式按需求选择，不固定八例，也不机械遍历所有组合：
- 功能/表单：从用户完成一件事的正常路径开始，再检查空结果、修改、清除、恢复等适用边界。
- 逻辑/状态：固定一个正常样例，每次改变一个决定结果的条件；覆盖适用的角色、状态、阈值两侧与边界，检查重复、顺序变化和失败恢复。
- 计算/查询：使用可核算的具体数据和期望结果，检查空值、零值、边界与组合条件。
- 权限/隔离：明确谁操作谁的数据，以及允许结果与不得暴露/修改的内容。
- 同步/批处理：说明初始数据、执行/重跑/中断步骤和最终数据，不用“同步成功”代替结果。
- 性能等非功能要求：先确认规模、环境和度量标准再构造场景，不擅自填耗时、并发数或容错阈值。

区分“原文明确”“由已知规则推导”“待确认的建议”。不能从规则唯一推出结果时，把分歧挂到待确认项；不通过写预期结果偷做业务决策。整份文档的批准状态仍单独核对。样例通过只证明这些场景，不等于所有输入正确；通用规则仍需成立，后续可增加同类变体。

验收结果的选择固定为：原文明示的结果 → 直接引用；由已确认规则能唯一推出的结果 → 写推导依据；有两个以上可能结果或缺关键条件 → 链接 Q，不选其中一个充当成功标准。这里产出验收要求，不自动扩展为业务测试开发任务，也不把列出 AC 宣称为测试通过；调研中实际执行的获准检查只记录为现状证据。

样例保留稳定编号；公共前提和公共禁止结果只写一次，各例引用，且单独读取时能定位其依赖。覆盖清单如确有需要只放“规则编号 → 样例编号”，不再写第二遍操作和预期。验证方式可作为样例属性，不另建一张含相同结果的“验证方案”表。只描述可观察行为，不写内部组件断言、技术实现或业务成效指标。

### 9. 交付前语义去重与覆盖检查（强制）
先核对现状、目标与验收是否连得起来，再执行以下去重检查：
- 现状可追溯，历史/原型/线上不混称；目标中没有无依据的新节点、并行或副作用。截图与流程中的版本、场景、数据差异已标明。
- 每个受影响页面或业务节点能定位差异项，每项差异能定位 AC 或 Q；逐项回查原文，不能仅宣称“全量”。未改事项和必要失败路径仍保留。
- 没有函数级方案越界，也没有因禁止方案而删掉核实过的业务事实。最终 HTML 的现状、对照、差异与验收可直接互相导航，不要求人再打开另一份解释页拼起来。

逐节核查后才生成 HTML；发现不成立则回到对应规则或样例修订：
1. 为每条规则、完整样例、排除项确认唯一归属；删去同义复述，跨节使用稳定编号/锚点引用。不要仅用相同字符串检测替代语义审查。
2. 特别检查“验证方案 vs 参考场景”“规则 vs 字段说明”“重定义 vs 阅读说明”“不做事项 vs 验收”是否维护了两份同义正文；冲突不得通过任选一份来掩盖，要记录依据或待确认。
3. 不在摘要、用户故事、新旧对照、来源说明中再次展开已存在的完整样例、规则或排除清单。
4. 合并后逐项核对原规则的正常、边界、异常及必要禁止副作用仍有覆盖；不为了去重删除不同前提下的有效样例。每个核心规则有样例，每个样例能定位依据；未决结果明确标注。
5. 检查编号唯一、引用可达，HTML 中跨章节锚点应自动切到目标章节，不能落在隐藏面板。
6. 交付时简述合并了哪些内容以及保留哪些独立边界；不另往需求正文附一份重复的审查报告。检查是本轮真实执行的审查，不宣称有未实现的自动语义去重器或能绝对保证未来不重复。

## 生成物身份与文件名（强制）

- 新建文档固定命名 `requirement.wl-req-confirm.md` 与 `requirement.wl-req-confirm.html`；不另存一份旧名正文。项目可覆盖归档目录，不省略文件名中的 Skill 名。
- Markdown frontmatter 必须包含 `skill: wl-req-confirm` 和 `artifact_schema_version: 1`；这里的版本是生成物身份协议版本，不冒充 Skill 源码版本。`source` 继续表示业务材料来源。
- HTML 必须从 Markdown 同步身份字段：`<meta name="generator" content="wl-req-confirm">`、`<meta name="artifact-schema-version" content="1">`。侧栏顶部显示 `wl-req-confirm` 标签及“产物规范：1”；不能只写在 HTML 注释中。
- 文件名、Markdown 字段、HTML meta 和可见标签必须一致。按 `doc-html-style.md` 完成身份检查和可读性检查后才能交付；仅有标识不代表内容合规、用户批准或真实执行记录。

### 历史兼容与阶段交接

- 同一需求目录先找新命名，再兼容 `requirement.md` / `design.md` 及配套 HTML；引用与锚点指向实际找到的文件名，不硬编码不存在的新名。
- 新旧同阶段文件同时存在时，先核实是否同一正文及批准版本；不能直接选新文件覆盖旧批准，无法确定则停下询问。
- 已有历史文件原位维护，不批量改名、不复制双份正文；缺少身份字段时标记“来源未确认”，不从标题、布局或目录推断来源。只有在明确授权的重新生成中，才为新生成产物写入当前 Skill 身份，不追溯声称历史来源。
- 文件名和来源标识不改变 `status` / `chosen`，下游仍需核对用户明确批准的证据。
