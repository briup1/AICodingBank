# 方案可达性审查

在独立上下文中扮演对抗性方案审查子 Agent。目标不是多找问题，而是回答一个问题：

> 从已实现的真实原点出发，严格执行方案声明的流程与契约，能否稳定到达需求的可观察终点？

只审查，不实现代码。只提出闭合链路所需的最小修正，不重新设计产品或扩展需求。

## 与相邻 Skill 的边界

- 本 Skill 验证**端到端可达性**：原点、逐跳交接、状态演化、假设和终点证明。
- `wl-plan-eng-review` 验证**工程交付就绪度**：架构、迁移、安全、性能、发布、回滚及测试策略。
- 两者都需要时，先做可达性审查；链路成立后再做工程评审。

## 独立上下文约束

由父 Agent 调度时，使用 fresh-context 子 Agent，只传入：

1. 需求最终目标及验收标准；
2. 方案文档路径或正文；
3. 仓库根目录及允许读取的证据范围；
4. 已确认的硬约束与 Out of Scope；
5. 本 Skill 路径。

不传父 Agent 的预设结论。子 Agent 必须独立读取方案、仓库约束、相关代码、协议和测试。宿主不支持子 Agent 时可在当前上下文执行，但必须明确标注“未获得独立上下文”。

## 工作流

```text
定义终点
  → 固定真实原点
  → 建立事实/约定/假设账本
  → 还原端到端链路
  → 逐跳验证流程、状态与契约
  → 执行正常及高风险反例实验
  → 证明终点可观察且可验收
  → 给出可达性裁决
```

### 1. 定义可观察终点

把最终目标写成可检查的后置状态：用户动作、系统结果、关键数据或状态变化、成功/失败的可观察信号及验收证据。

**完成条件：** 不依赖“功能完成”“正常工作”等循环表述，任何人都能据此判定是否到达终点。若做不到，记录为验收 Gap。

### 2. 固定真实原点

从当前代码、协议、测试或运行证据确认实际入口、已有状态、数据来源、能力边界和可复用接缝。不得从理想架构、计划新增能力或未经验证的前置状态开始。

**完成条件：** 原点中的每项能力均有证据；未证实项进入假设账本。

### 3. 建立证据账本

逐项分类，禁止混用：

- **事实**：当前代码、协议、测试或运行结果可以证明；
- **方案约定**：方案明确新增但尚未实现；
- **待验证假设**：链路依赖但无证据；
- **已否定假设**：与现状或硬约束冲突；
- **未知项**：现有输入不足以判断。

证据优先级：运行行为/测试 → 当前代码/生成协议 → 已批准契约/架构文档 → 方案约定 → 经验推测。

**完成条件：** 每个影响链路成立的陈述都有分类和证据位置；推测没有伪装成事实。

### 4. 还原并逐跳验证链路

对每一次模块、进程、服务、存储或用户边界交接，记录：

```text
前置状态
  → 触发方
  → 处理方/状态所有者
  → 输入及生产者
  → 契约与传输方式
  → 校验/转换/副作用
  → 输出及消费者
  → 后置状态
  → 下一步触发
  → 失败终态与观察方式
```

相邻步骤必须满足：`上一步后置条件 ⊇ 下一步前置条件`。同时验证数据、控制、身份、时间和错误语义；任一维度无法衔接就是候选 Gap。

**完成条件：** 从原点到终点不存在未展开的“然后”“系统会”“自动同步”等魔法跳转。

### 5. 执行思维实验与反证

用最小具体样例完整执行正常路径，再按方案风险选择反例：非法/空输入、下游失败或超时、部分成功、重复与重试、并发与乱序、中断与恢复、旧数据/新旧版本并存、权限或会话切换。

主动反证“字段必有、顺序固定、只执行一次、共享同一状态、写后立即可见、全组件同步升级、统一兜底即可恢复”等假设。避免无关场景的组合爆炸。

**完成条件：** 主路径及每个可能阻断目标的高风险分支，都有明确终态、状态收敛方式和验证手段。

### 6. 给出裁决

裁决只能是：

- **可通过**：关键链路闭环，且没有未解决阻断项；
- **有条件通过**：链路可成立，但列出的条件必须先验证或补齐；
- **不可通过**：存在明确断点、契约冲突或已否定的关键假设；
- **信息不足**：缺少决定可达性的必要输入。

“待验证假设”不得支撑“可通过”。按阻断、高风险、待澄清、非阻断优化分级；优化项必须与可达性问题分开。
