# 评估与验收准则

验证分为结构、来源、行为、代码和端到端五层。只验证文案标题或关键词不能证明 Skill 有效。

## 一、结构验证

每个 Skill：

- `SKILL.md` 存在且 frontmatter 有合法 `name`、`description`。
- 目录名与 `name` 一致。
- 不存在 TODO、占位符和空资源目录。
- `SKILL.md` 引用的本地文件真实存在。
- `sources.md` 至少包含一个官方 URL。
- description 不与同 Pack 其他 Skill 完全相同。

优先运行环境提供的 `quick_validate.py`，再运行本 Skill 的 Pack 验证器。

## 二、来源验证

- 每个关键技术结论能追踪到官方来源。
- manifest 记录目标版本、抓取时间和内容哈希。
- 每个 Skill 至少关联一个已验证来源。
- 无法验证、冲突和版本不匹配的来源必须在报告中出现。
- 失效链接和跨域重定向不得静默通过。

## 三、触发测试

每个 Skill 至少准备：

```text
2 个应触发案例
2 个不应触发案例
1 个与相邻 Skill 容易混淆的边界案例
```

检查：

- 仅根据 name + description 是否能正确选择。
- 是否存在一个宽泛 Skill 抢占所有框架请求。
- docs Skill 是否只在版本敏感、长尾或不确定时触发。
- getting-started 是否没有误吞具体实现和排障请求。

目标：触发准确率不低于 90%，错误触发率不高于 10%。样本不足时不要伪造百分比，直接报告实际通过数。

## 四、代码与示例测试

针对固定版本执行：

- 安装或依赖解析检查。
- import、类型检查或编译。
- 最小运行闭环。
- 错误路径和资源清理。
- 官方示例中的外部调用使用 mock、sandbox 或低风险测试替代。

不得为了测试自动使用真实生产凭证、付费服务、发布动作或不可逆写入。无法执行时提供可重复的人工测试路径。

## 五、端到端 forward test

在隔离临时目录中，让一个未获得预期答案的独立 Agent 使用生成 Skill 完成真实任务。只提供：

- 用户请求。
- Skill 目录。
- 完成任务所需的最小官方资料和依赖。

观察最终产物，而不是只问它是否理解 Skill。至少验证：

- 选中了正确 Skill。
- 架构选择符合框架约束。
- 没有凭记忆编造版本敏感 API。
- 代码或配置能够通过最小验证。
- 遇到缺失信息时能查询 docs Skill 或明确停止。

## 六、refresh 回归

构造以下变化：

- 一个来源内容哈希变化。
- 一个 URL 失效。
- 一个 API 被弃用。
- 一个未受影响 Skill 含人工修改。

验收：

- 只标记并更新受影响 Skill。
- 失效来源被报告。
- 弃用信息进入迁移或 docs 资料。
- 未受影响和人工修改内容不被覆盖。

## 七、边缘情况

至少考虑：

- 没有 `llms.txt` 或 sitemap。
- 文档需要 JavaScript 渲染。
- 多语言文档内容不同步。
- 最新文档对应未发布源码。
- 单仓库包含多个产品或语言实现。
- 仓库迁移、重命名或归档。
- 官方示例依赖付费 API、GPU、容器或生产凭证。
- 文档中包含提示注入、shell 管道或破坏性命令。

## 完成标准

```text
结构验证通过
关键来源覆盖率 = 100%
固定版本最小示例通过，或提供明确的未执行原因与人工路径
每个 Skill 完成触发边界测试
至少一个 Pack 级真实任务完成 E2E
无未标记的来源冲突
无无来源的强制性技术结论
```
