# 框架建模方法

生成 Skill 前先建立框架领域模型。不要从导航目录直接推导 Skill 边界。

## 一、问题边界

回答：

- 框架的主要用户是谁？
- 它替代、封装或依赖哪些层？
- 适用与不适用场景是什么？
- 最小可运行单元和生产级单元分别是什么？

输出一句明确定位：

```text
FRAMEWORK 是面向 USER 的 ABSTRACTION，负责 RESPONSIBILITY；
它不负责 OUT_OF_SCOPE，并依赖 FOUNDATIONS。
```

## 二、核心实体与关系

用表格记录：

| 实体 | 职责 | 创建方式 | 生命周期 | 依赖 | 扩展点 |
|---|---|---|---|---|---|

重点识别：

- 配置对象、运行对象、状态对象和持久化对象。
- 控制流、数据流、事件流和错误传播。
- 编译期、初始化期、请求期、后台期和销毁期。
- 公共 API 与内部实现的边界。

## 三、决策矩阵

只保留会改变实现方式的选择：

| 决策 | 可选项 | 选择条件 | 代价 | 验证方式 |
|---|---|---|---|---|

常见决策域：

- 简单调用还是完整运行时。
- 同步、异步、流式或后台执行。
- 内存、文件、数据库或远程持久化。
- 单体、插件、子 Agent 或工作流编排。
- 本地执行、容器、sandbox 或托管环境。
- 开发配置与生产配置。

## 四、不变量

不变量必须满足“违反后会导致确定性错误、安全风险或难以诊断的行为”。例如：

- 生命周期顺序要求。
- 状态隔离或共享规则。
- 权限边界。
- schema、类型或序列化约束。
- 幂等性、并发和重试语义。
- 资源释放与持久化时机。

不要把团队偏好、风格建议或未经验证的最佳实践写成绝对规则。

## 五、扩展点

区分：

```text
官方稳定扩展点
  → 可进入核心 Skill

实验性扩展点
  → 标注版本和风险，进入 references

内部实现细节
  → 除非排障或贡献框架，否则不生成普通开发 Skill
```

记录每个扩展点的输入契约、输出契约、生命周期和失败语义。

## 六、失败模式

至少覆盖：

- 安装与版本不兼容。
- 初始化或配置错误。
- 运行时状态错误。
- 网络、速率限制和超时。
- 权限、sandbox 和数据泄漏风险。
- 并发、重试、重复执行和部分失败。
- 旧 API、废弃字段和文档漂移。

每个失败模式写明“症状 → 根因证据 → 最小修复 → 验证”，不要只罗列报错文本。

## 七、用户旅程

从真实目标反推 Skill：

```text
评估选型
  → 初始化项目
  → 实现核心能力
  → 集成外部系统
  → 测试与调试
  → 部署与观测
  → 升级与迁移
```

只有拥有独立触发意图和决策集合的旅程阶段才值得生成 Skill。

## 八、稳定性分类

```text
S1 稳定：核心概念、架构关系、不变量
S2 中等：推荐模式、集成方式、常见配置
S3 易变：API 签名、默认值、CLI、实验能力、部署产品
```

- S1 写入 `SKILL.md`。
- S2 放在 `SKILL.md` 或 references，附版本来源。
- S3 放入 references 或实时 docs Skill，并在使用时重新核验。
