# 方案设计（wl-design-doc）

## 目标与边界

本 Skill 的职责是把**已批准的需求**转化为一份能让人看懂、让实现 Agent 知道改动边界、让评审者能够批准的方案设计。

核心原则：

- 先讲用户/调用方要完成什么，再讲技术如何承接。
- 先画完整主流程，再补模块、契约、风险和验收。
- 结构保持完整，表达保持简洁；白话不等于删掉必要的技术构件。
- 方案停留在业务流程、模块职责、接口/数据契约和关键边界；不写函数级施工步骤。
- 证据支撑关键判断，但不让取证过程占据正文。
- 只在确有取舍或风险时增加专项章节，不为填模板制造内容。
- 最终用户只接收一份美观、可独立打开的 HTML。

本 Skill **不负责**：需求确认、代码实现、详细任务拆分、提交发布、通用 HTML 发布体系或特定代码取证工具的操作手册。

## 前置与出口

- 前置：需求确认文档已批准（`status: approved`）。未批准时先执行 `wl-req-confirm`。
- 设计阶段只读调查和写方案，不写业务实现代码。
- 有真实的高成本或业务取舍时，必须把选项和影响写清，并等待用户决定；普通实现细节由 Agent 按项目约束决定。
- 方案需要用户批准后才能进入实施。批准不等于代码已经实现或验证通过。

## 唯一最终产物

固定生成：

```text
docs/requirements/NNNN-slug/design.wl-design-doc.html
```

规则：

- 只生成、只交付这一份 HTML；不生成或保留 `design.wl-design-doc.md`、证据报告、独立图文件或其他平行正文。
- HTML 必须是单文件，可脱离工作区直接打开；样式、脚本和图形资源默认内嵌。
- HTML `<head>` 必须包含：
  - `<meta name="generator" content="wl-design-doc">`
  - `<meta name="artifact-schema-version" content="1">`
- 页面可见区域显示标题、需求标识、状态、来源需求、创建/更新时间和当前选型。
- 生成和视觉检查遵守同目录的 `doc-html-style.md`。HTML 解析成功不等于视觉验收通过；浏览器不可用时如实说明。
- 历史 Markdown 只能作为读取/迁移输入；不能因为兼容历史而重新生成 Markdown。

### 批准信息与阶段交接

- HTML 用一个 `<script type="application/json" id="wl-design-meta">` 保存需求标识、来源需求、`status`、创建/更新时间、`chosen` 和 `approval_evidence`（用户实际批准记录的可追溯位置及批准范围）；可见标签从此元信息读取，不另维护一份状态。JSON 仅作数据读取，内嵌时转义 `<`，不作为代码执行。
- 新方案为 `status: draft`，未选定或没有多方案时 `chosen: null`，未批准时 `approval_evidence: null`。只有用户明确批准本版及其范围后才能标 `approved`；多方案还须记录用户实际选定的方案。文件标识、旧版批准或本次规则优化的批准都不能代替业务方案批准。
- 同一需求目录先检查现有 HTML 和历史 `design.wl-design-doc.md` / `design.md`。并存时核对正文和批准版本；无法确定则停止询问，不凭文件名或时间选权威，不覆盖旧批准稿。
- 纯展示重生成保留原批准范围、`status`、`chosen` 和证据身份；变更契约、业务行为或范围须重新批准，不能沿用旧版批准。
- 下游 `wl-ticket-run` 直接读取 HTML 正文及上述元信息，不要求为交接补造 Markdown。

## 设计前：确认事实，不绑定工具

开始前确认：

1. 目标项目、当前分支/版本和工作区范围。
2. 项目自己的规则、入口、测试方式和相关文档。
3. 本需求涉及的现有入口、模块职责、调用关系、数据/状态流和关键限制。
4. 需求、现状和方案之间的边界：
   - **当前事实**：代码或获准运行结果已经证明；
   - **设计目标**：批准后准备实现；
   - **假设/待确认**：尚未证明，不能写成事实；
   - **验证结果**：本轮实际执行过的检查及结果。

优先读取与本需求直接相关的代码、测试、配置和运行证据，不做无关的全库考古。可以使用 CodeGraph 或其他工具定位，但不把任何特定工具写死为必经流程；工具输出必须用源码或运行结果定点复核。

正文只保留会影响方案理解或批准的依据。详细路径、命令、行号和工具输出可放 HTML 的“补充依据”折叠区；没有证据的关系标为“待确认”，不伪装成确定调用链。

## 执行方式：按需并行

- 开始调查前，主 Agent 先确认共同需求范围、项目基线和操作边界，判断是否有两个以上可独立开展、会影响方案结论的调查或验证任务。不要为并行制造任务、扩大调查或固定团队。
- 有合适任务，且委派工具可用、权限允许时，必须实际调用子 Agent，使用宿主允许的子 Agent 接口；委派授权不等于新建独立任务、启动服务或外部操作的授权。同一轮先派出可并行任务，再按依赖收取结果，不逐个等待后再派下一个。各任务交代输入、输出、完成标准及边界，说明它解决的具体缺口；工具或预算限制不能并行时如实说明，不声称已并行。
- 主 Agent 保留下一步立即依赖的工作；子 Agent 只承担边界明确的现状检索、关键假设验证或按需 Review，返回结论、依据和未确认项。等待期间，主 Agent 推进不依赖这些结果的工作，不重复调查同一问题。
- 主 Agent 核对结果是否对应共同基线，处理证据冲突，统一形成推荐和最终 HTML；关键冲突未解决前不写确定结论。禁止让多个 Agent 各写整份方案再拼接，Review 不能代替实际验证。
- 没有独立任务、未获委派授权、工具不可用或协调成本明显不划算时，由主 Agent 执行，并简短说明具体原因；遵守项目及宿主约束，不绕过操作授权。
- 分工、真实调用和结果整合留在任务过程记录，不作为技术方案固定章节；未真实委派不得声称完成独立审查，也不能仅凭 Agent 数量声称提速。最终仍只交付一份方案 HTML。

## 设计推导方法

### 1. 先确定最小完整方案

先列出已确认的目标、现有资产和不可妥协的约束，画出能够完成业务的最小链路。至少用一个正常场景和适用的失败场景检查链路是否闭合。

每个关键新增或变化都说明：

```text
具体场景 → 原方案哪里不够 → 最小变化 → 下游结果 → 验收方式
```

### 2. 用调用方行为校验设计

接口、数据结构和模块边界先从调用方如何使用来推导：

```text
谁发起 → 传入什么 → 系统做什么判断 → 得到什么结果 → 哪些内部细节不应暴露
```

必要时给 1～2 个简短调用/使用示例，但不写实现代码。检查公共边界是否泄露存储、传输或框架细节，是否存在无意义的透传层、重复状态所有者或两套完成同一任务的路径。

### 3. 只对重要取舍做压力测试

以下情况才展开演进、迁移、回滚、安全、性能或运维分析：

- 设计难以回退或会影响已有数据/外部调用方；
- 存在已确认的未来要求或可信的高成本变化；
- 涉及权限、并发、异步、外部系统、公共接口或线上发布。

没有可信依据时，不为“未来可能”提前增加抽象；但已知的兼容、一致性、隔离和恢复约束不能省略。

## 文档结构（固定六节，按需展开子节）

### 1. 方案摘要与范围

**回答：为什么改、要得到什么、什么不做？**

表达形式：1～3 段白话 + 目标/非目标清单 + 必要时的需求覆盖表。

必须说明：

- 当前问题和最终目标；
- 本次方案结论或待用户决定的事项；
- 本次实现什么；
- 明确不实现什么；
- 哪些现有行为保持不变；
- 需求较多或容易遗漏时，用简表建立“需求 → 方案覆盖 → 验收”关系。

### 2. 当前与目标流程

**回答：事情现在怎么走，改后怎么走，为什么会改变结果？**

每个关键场景按此顺序：

```text
一句话说明变化
  ↓
以前：从入口到结果的完整流程
  ↓
改后：同一场景的完整流程
  ↓
关键变化：旧行为 → 新行为 → 最小例子 → 下游结果
```

表达形式：

- 先用白话描述用户或调用方场景；
- 使用纵向 ASCII 流程图，节点写完整业务动作；
- 明确正常路径、关键判断、失败出口和最终结果；
- 用 `[保持]`、`[新增]`、`[修改]`、`[删除]`、`[待确认]` 标识变化；
- 业务流程箭头表示业务推进，不冒充函数调用；
- 只有主流程解释不清时，才补调用链图、数据流图、状态图或时序图；
- 新功能没有旧入口时明确写“纯新增”，不虚构旧流程。

流程图不是全部方案。流程之后必须能定位模块、契约和验证；但不要把主图切碎成函数调用树。

### 3. 目标设计与模块职责

**回答：哪些边界变化，哪些模块负责，模块如何协作？**

表达形式：模块/服务职责表 + 必要的模块关系图或数据流图 + 简短设计理由。

至少说明：

- 哪些能力复用、扩展、新增或明确不改；
- 每个受影响模块负责什么、不负责什么；
- 模块之间如何传递关键数据或结果；
- 关键不变量和边界校验放在哪里；
- 调用方不需要知道哪些内部细节。

不要求写函数名、类名、局部变量或逐行改法；只有当某个接口或类型本身就是跨模块契约时，才展示其必要形状。

### 4. 接口、数据与状态契约

**回答：模块之间交换什么，成功/失败/重复/不可用时各自做什么？**

表达形式：输入/输出/错误/状态表，必要时附短 JSON、事件或状态图示例。

按命中情况说明：

- 输入、输出和字段语义；
- 空值、多值和缺失字段；
- 成功、失败、拒绝、无权限和空结果；
- 重复请求、幂等、超时、重试和并发一致性；
- 数据写入、状态迁移和事务边界；
- 旧调用方、旧数据或外部系统的兼容要求。

只写会影响协作、行为或验收的契约，不写内部算法和函数拆分。

### 5. 复用、取舍与风险

**回答：为什么采用这个方案，复用了什么，代价和风险是什么？**

默认给出一个推荐方案。只有存在多个真实可行方向、重大架构选择或难以逆转的决策时，才增加方案比较表：

| 方案 | 适用条件 | 优点 | 代价/风险 | 结论 |
|---|---|---|---|---|

必须记录选择理由和接受的代价。复用分析仅在存在复用资产、兼容约束或“为何不能复用”的决策时展开，不为形式盘点全库。

按命中情况增加：

- 数据迁移、回滚和发布顺序；
- 安全、权限和数据隔离；
- 性能、容量和并发；
- 外部依赖、监控和运维；
- 已知未来变化的简短压力测试；
- 风险、假设和未决问题，以及它们是否阻塞批准。

### 6. 实施边界与验收

**回答：后续实现 Agent 从哪里开始，什么结果才算完成？**

表达形式：实施边界清单 + 验收场景表 + 最小验证方法。

写清：

- 需要改动的模块范围；
- 需要复用的现有能力；
- 明确不应修改的边界；
- 实施前置条件和依赖方向；
- 正常、失败、权限、重复、兼容等适用验收场景；
- 验证方法和完成标准；
- 尚未执行的验证及原因。

可以写“先完成契约，再完成业务链路，再接入调用方”的依赖方向，但不在这里生成函数级施工步骤、完整 Ticket、负责人、工时或提交计划；这些交给后续任务拆分/实现 Skill。

## 按需图形规则

默认只生成业务主流程图。只有以下问题无法用短文或表格说明时才补图：

| 需要解释的问题 | 补充形式 |
|---|---|
| 跨哪些模块以及谁调用谁 | 模块/调用链图 |
| 数据从哪里来、如何转换和保存 | 数据流图 |
| 状态如何迁移、哪些动作被禁止 | 状态图 |
| 异步、并发、等待、回调、超时、重试 | 时序图 |

所有图必须标明关系含义；未知关系标为待确认；不为凑格式重复主流程。

## 最小自检

交付 HTML 前只检查以下四件事：

1. **主链完整**：每个关键场景都从入口走到结果，正常和必要失败路径都说清楚。
2. **边界可实施**：模块职责、契约和关键异常足以让后续 Agent 开始工作，但没有下沉到函数级施工。
3. **范围未膨胀**：目标、非目标、保持不变和未决问题清楚，没有把推测写成需求。
4. **验证可判断**：每个核心需求都有可观察的验收结果；实际执行、静态推断和待验证事项明确区分。

影响方案成立的关键假设必须用最小证据验证，例如复核现有契约、表结构或最小实验；记录实际输入、结果和依据，不把推演写成实测。关键验证失败或仍无证据时，方案退回草稿，只能请求补证或方向讨论，不能请求可实施方案批准、标记 `approved` 或进入实施。非阻断验证可留到后续，但须写明原因、验证时点和残余风险，批准时让用户明确接受；Agent 不自行接受风险。

最小可解释性检查：读者不展开证据，能从主链与例子说清入口/结果、分支去向、保持/变化、同一输入的新旧差异，以及差异怎样改变后续结果；答不出就修改正文，不增加一套审查章节。

HTML 视觉检查至少确认：正文开场先讲摘要和主流程；流程图空格与分支可读；表格不过度拥挤；补充信息不会打断主阅读路径；页面在桌面和窄屏可读。

修改本 Skill 后，按 [回归场景](references/regression-scenarios.md) 检查生成、批准和交接行为；结构检查不能代替场景执行。

## 与后续流程的边界

```text
已批准需求
  ↓
wl-design-doc：确定业务流程、设计边界、契约和验收
  ↓
用户批准方案
  ↓
任务拆分/实施 Skill：拆垂直任务、定义依赖、逐项实现和测试
  ↓
代码审查与实现后验证
```

实现中如果反复出现同类 workaround、调用方必须了解内部规则、或实现持续偏离方案，应暂停继续堆补丁，回到方案重新确认边界。

## 禁止事项

- 需求未批准就进入方案设计。
- 把当前代码事实、设计目标和验证结果混为一谈。
- 为了显得完整而强制增加多方案、专项图、未来抽象或通用检查清单。
- 把业务流程图伪装成函数调用图。
- 把函数级施工步骤、详细 Ticket 或提交计划塞进方案正文。
- 生成 Markdown、独立证据报告或与 HTML 平行的第二份方案正文。
- 用未执行的检查结果宣称已验证或已批准。
