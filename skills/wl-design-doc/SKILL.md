# 方案设计（wl-design-doc）

开发流程的第二阶段。目标：产出一份**人能看懂、开发能定位、依据能核验的可批准方案**。读者先沿白话流程理解改了什么及结果，再按需查看实现与证据；证据支撑正文，不能代替正文。

**为什么**：实施期的混乱几乎都源于设计期欠的债——接口没定清、复用没盘点、风险没暴露。本 skill 把债前置：最小验证不通过的方案，根本没资格进入开发。

**前置条件**：`requirement.wl-req-confirm.md`（兼容历史 `requirement.md`）状态为 `approved`。否则先走 wl-req-confirm。
**出口条件**：用户批准方案（若有多个方案，用户已明确选定其一，记入 frontmatter `chosen`）。

## 生成物身份与文件名（强制）

- 新建文档固定命名 `design.wl-design-doc.md` 与 `design.wl-design-doc.html`；不另存一份旧名正文。项目可覆盖归档目录，不省略文件名中的 Skill 名。
- Markdown frontmatter 必须包含 `skill: wl-design-doc` 和 `artifact_schema_version: 1`；这里的版本是生成物身份协议版本，不冒充 Skill 源码版本。`source` 继续表示业务材料来源。
- HTML 必须从 Markdown 同步身份字段：`<meta name="generator" content="wl-design-doc">`、`<meta name="artifact-schema-version" content="1">`。侧栏顶部显示 `wl-design-doc` 标签及“产物规范：1”；不能只写在 HTML 注释中。
- 文件名、Markdown 字段、HTML meta 和可见标签必须一致。按 `doc-html-style.md` 完成身份检查和可读性检查后才能交付；仅有标识不代表内容合规、用户批准或真实执行记录。

### 历史兼容与阶段交接

- 同一需求目录先找新命名，再兼容 `requirement.md` / `design.md` 及配套 HTML；引用与锚点指向实际找到的文件名，不硬编码不存在的新名。
- 新旧同阶段文件同时存在时，先核实是否同一正文及批准版本；不能直接选新文件覆盖旧批准，无法确定则停下询问。
- 已有历史文件原位维护，不批量改名、不复制双份正文；缺少身份字段时标记“来源未确认”，不从标题、布局或目录推断来源。只有在明确授权的重新生成中，才为新生成产物写入当前 Skill 身份，不追溯声称历史来源。
- 文件名和来源标识不改变 `status` / `chosen`，下游仍需核对用户明确批准的证据。

## 产出

`docs/requirements/NNNN-slug/design.wl-design-doc.md`（+ 生成的 HTML）。Markdown 是唯一事实来源。

**HTML 生成规范见 `doc-html-style.md`**（S1 编辑出版·暖纸风 + 侧边导航布局），生成前必读。

HTML 交付前必须执行 `doc-html-style.md` 的“HTML 可读性检查”，尤其要展开代码块检查文字与背景；HTML 解析成功不能代替浏览器渲染验证。无法执行时如实标注，不宣称视觉验收通过。

### 新建设计文档的 frontmatter

```yaml
---
id: <需求编号>
status: draft
created: <YYYY-MM-DD>
source_requirement: <实际已批准的需求 Markdown 相对路径>
skill: wl-design-doc
artifact_schema_version: 1
chosen: null
---
```

`chosen` 仅在用户明确选择后填写，来源标识不代替批准。

## 设计前现状取证与 CodeGraph 新鲜度（强制）

新建设计或修改方案事实时，现状调用链、模块边界和关键函数关系必须来自当前代码证据，不能凭目录名、历史方案、旧截图或 CodeGraph 旧索引推断。**CodeGraph 是定位和关系检索工具，不是天然最新的事实来源。**

纯展示重生成不重新批准方案、不扩展业务范围：复核已有 Markdown、批准状态、来源和基线，保留历史证据的身份与缺口；不强制重建索引，也不把历史流程改称当前实现。若要新增或改变代码事实，必须回到下列取证步骤。

新建设计或刷新代码事实时，以及在切换分支、拉取代码、发生较大修改后，按以下固定步骤执行；不要跳步：

```text
确认目标仓库、分支、HEAD、工作区状态
  → codegraph status
  → codegraph sync <repo>（即使 status 看起来正常，也先同步一次）
  → 再次 codegraph status
  → 若未初始化、同步失败、仍报告过期或基线与当前代码不一致：codegraph index <repo>
  → 再次 codegraph status，记录最终索引状态
  → 仅在状态确认后使用 explore / context / node / callers / callees / impact
  → 对关键结论定点打开源码、测试、配置或运行证据复核
```

### CodeGraph 新鲜度固定判定

| 情况 | 固定动作 | 设计文档怎么写 |
|---|---|---|
| 无 `.codegraph/` | 不调用 CodeGraph；按项目规则用其他只读定位方式 | 标记“CodeGraph 不适用/不可用”，不伪称完成图查询 |
| `status` 显示最新，且 `sync` 后仍与当前 HEAD/工作区一致 | 可以用于定位和关系查询 | 记录仓库 HEAD、工作区是否有改动、索引时间/状态 |
| 有未提交改动 | 先 `sync`；确认工具是否包含工作区改动 | 若图只覆盖已提交基线，所有未提交相关结论必须直接复核源码，并标“图索引未覆盖/部分覆盖” |
| `status` 过期、基线不匹配或 `sync` 失败 | 不使用旧图支撑结论；先 `index` | 记录失败原因；重建未成功前，结论只能是部分证据/待核实 |
| `index` 后仍不能反映当前代码，或工具异常 | 停止依赖该图继续展开 | 保留缺口和影响范围；不能用旧图拼出确定调用链 |

“Index is up to date”只表示工具自己的索引检查通过；还要核对它对应的仓库路径、分支/HEAD、工作区改动和本轮读取时间。CodeGraph 输出的源码片段视为已读，不重复通读；但对关键分支、状态写入、外部副作用和异常路径仍需定点复核，避免把关系索引当作业务语义证明。

### 证据分层

- **E-ARCH**：当前代码确认的模块/服务边界、依赖方向和外部系统关系。
- **E-FUNC**：当前代码确认的关键函数、调用者/被调用者、条件分支与副作用。
- **E-RUN**：测试、只读运行观察、日志或最小验证证明的实际执行结果。
- **E-DESIGN**：拟新增或拟修改的设计节点；必须链接已批准需求、复用依据和验证方式，不能伪装成已有代码。
- **E-GAP**：索引过期、工作区未覆盖、运行条件缺失或业务语义无法从代码确定的缺口。

图节点和连接的依据必须能在开发定位或证据区映射到上述类别，不要求在主图每个节点旁堆编号；关键未知连接及影响批准的缺口必须就地标“待确认”。“当前代码存在”不等于“线上实际执行”，“方案拟新增”不等于“已经实现”。

## 设计原则：最小完整方案 + 演进压力测试

适用于接口、数据模型、状态流程、模块/服务拆分、前端交互和性能方案，不只用于减少接口字段。**从最小完整方案开始，再用可信的未来变化检验它；为高成本变化提前保留边界，为低确定性的未来功能暂缓实现。**“简单”按整体理解、维护和演进成本判断，不按字段数、代码行数或服务数判断。

### 第一轮：推导最小完整方案

先列明已确认目标、现有资产和不可妥协的约束，再画出能够完成业务的最小链路。用实际正常场景及必要失败场景检验，发现缺口才增加字段、状态、存储、组件或处理步骤。

每个关键增量说明：**具体场景 → 原方案哪里不够 → 最小改动 → 下游行为如何变化 → 新增成本与验证方式**。检查是否能复用已有能力，以及新增信息是否重复或可无歧义地推导；可推导不是一律删除，若为兼容、性能或调用方独立性保留，说明理由和一致性规则。

最小方案是设计推导起点，不是允许上线的残缺版本。权限和企业数据隔离、并发一致性、防重复、必要审计、外部接口兼容，以及迁移保护和恢复等适用约束，从第一轮就必须纳入。不能以“先跑通”“现在量小”为由延期处理。

### 第二轮：演进压力测试

对关键且难以回退的设计，检查最可能或后果重大的后续变化：

- **变化依据**：区分已确认的后续要求、有证据的合理预期、纯假设；引用需求、路线图、调用方、数据规模或既有演进记录。不虚构增长数字、排期或变化概率；没有可信依据时如实说明。
- **影响范围**：变化发生时，哪些接口、调用方、数据、状态和模块需要改动？是否涉及历史数据回填、外部系统升级或不可逆操作？
- **取舍**：比较现在预留边界的成本，与未来不预留的改造成本及风险。预留边界不等于提前实现未来功能；也不能为减少当前代码而忽略已知的高成本变化。
- **验证**：用一个具体变化场景沿链路推演；重要假设用最小实验验证。静态推演和实际执行分别标注，不把“看起来可扩展”写成已验证。

例：结果今天只需一个值，近期已确认还需展示来源、且外部调用方难以同步升级，则候选对象可能比原始值数组更合适；若无此方向且调用方可同步演进，不必提前增加来源字段。不是统一偏好某种结构，而是让演进成本参与选择。

### 方案中必须留下的结论

明确写出 **现在实现什么 / 为哪些变化提前做准备及理由 / 暂不支持什么及未来改造代价**，包括已接受的风险。推导过程只保留会影响决策的步骤，不为演示方法虚构中间版本。

将结论放入下方七节的相关位置，不另造平行文档体系。简单改动用短段落，重大取舍再用表格；无接口或无可信扩展场景时说明不适用，不强行增加抽象层。推导中发现需扩大业务范围或改变已确认规则时，回到需求确认，不自行批准。

## 文档结构（7 节，固定顺序）

### 1. 需求↔方案映射
表格：每个需求子项 → 实现它的方案模块 → 是否覆盖。方案与需求**不必一一对应**（可以一个模块覆盖多个子项），但**不得有遗漏**，且对应关系必须可追溯。HTML 中需求子项链接回 requirement.wl-req-confirm.html 对应锚点，双向可跳转。

### 2. 前后对比：先讲完整场景，再展开开发依据

这一节必须让读者不读源码、不展开证据，也能讲清入口、关键动作、条件分支、最终结果，以及本次变化。引用已批准需求中的业务对照，不复制整份需求验收正文。

#### 2.1 固定阅读顺序

每个关键场景按下面顺序呈现；场景标题用白话描述用户要完成的事情，不用“基线事实”“L1/L2”开场：

```text
一句话：以前哪里不够，这次改变什么
                ↓
以前：从入口到结果的完整流程
                ↓
改后：同一场景的完整流程，标出关键变化
                ↓
关键变化：旧行为 → 新行为 → 最小例子 → 下游结果
                ↓
按需展开：开发定位、源码证据与验证状态
```

- 功能全新时，“以前”画当前替代路径；确实没有则写“无，纯新增”，不虚构旧流程。
- 默认展开白话说明、新旧主图、关键变化例子和影响理解的范围限制。历史/当前/设计目标的身份用一句短提示保持可见，不让读者先读版本和取证过程。
- 编写顺序仍先取证后设计；阅读顺序先业务后证据。证据不足不能靠改写成白话掩盖，关键待确认项须出现在对应节点或说明旁。

#### 2.2 按读者理解选节点，不按源码切碎故事

| 层次 | 内容与粒度 | 展示方式 |
|---|---|---|
| 场景主链 | 用户动作 → 关键业务处理/判断 → 分支结果 → 用户可见结果；保留决定结果的存储、外部交互及失败处理 | 必须先展示，默认展开；明确标为“业务处理流程”，不是函数调用顺序证明 |
| 开发定位 | 把主链变化映射到模块/服务（L1）、关键函数或契约接缝（L2），注明复用/拟修改/拟新增及真实定位 | 主链之后按需展开；文字或表格足够时不强制另画重复图 |
| 专项图 | 主链不足以解释的调用边界、数据来源/保存、并发等待或状态迁移 | 命中实际设计需要才补，不为凑图重复表达同一件事 |

主图节点使用白话完整动作，例如“检查申请是否完整”，不以裸编号、函数名、map/null、CAS 等术语代替业务说明；具体符号和数据结构放开发定位。只保留会改变判断、结果、状态、记录、副作用、外部交互或失败处理的关键节点；省略不影响结论的 getter、格式化、日志和框架转发。

业务处理流程可以串起用户动作、业务处理和可见结果，箭头表示业务推进，不声称相邻节点一定直接调用。开发调用图的箭头只表示已核验调用；不能为了让故事连续而伪造调用边。

主图只画标题约定的场景；其他任务类型或入口的兼容行为放就近可见的范围说明，不塞进当前场景形成“全流程总图”。节点优先一行白话动作，理由、实现约束和例子放图旁；安全校验及必要失败结果仍保留，但不把全部协议细节搬进主图。

#### 2.3 统一纵向字符流程图

Markdown 是唯一事实来源；HTML 原样展示同一份完整纵向字符图，保留等宽字体、空格和换行。默认不生成 SVG/PNG、不使用 Mermaid、不引入绘图库或 nodes/edges 布局；只有用户明确要求其他格式时才例外。frontmatter 使用 `diagram_layout: vertical-ascii`，不改变业务 `chosen`、`status` 或批准范围。

```text
以前：
用户提交申请
      │
      ▼
直接保存申请
      │
      ▼
返回提交结果

改后：
用户提交申请
      │
      ▼
[新增] 检查申请是否完整
      │
      ▼
◇ 必填内容齐了吗？
      ├── 是 → 保存申请 → 返回提交结果
      │
      └── 否 → 返回缺失项提示，本次不保存
```

- 每个场景/版本从明确入口走到结果，是一幅完整连续图；禁止按每条边或短链拆成独立卡片，也不能只画入口到某个中间服务就结束。
- 变化标记使用 `[保持]`、`[修改]`、`[新增]`、`[删除]`、`[待确认]`，不靠颜色表达变化；连续保持步骤可在图旁一句话说明，不逐行堆标记。
- 判断用白话问句与 `◇`；分支写清条件、动作和结果。确有共同后续才显式汇合，终止分支不虚构汇合；回路沿外侧注明返回节点及条件。多入口按场景拆图，不猜连接。
- HTML 每幅图只展示一次。禁止重复粘贴整幅图，但必须解释关键变化；“旧行为 → 新行为 → 最小例子 → 下游结果”不算重复。
- 例：旧流程直接保存 → 新流程缺项时不保存 → 用户漏填联系人，收到缺项提示 → 后续处理不再收到这条不完整申请。例子应来自真实规则或明确的示意数据，不能补造业务事实。

#### 2.4 开发定位与按需补图

将主链变化关联到需求/差异/验收及源码依据；函数命名是定位而非提前批准，尚未存在的符号标“拟新增”。调用树不直接搬进正文。

| 主链仍解释不清的问题 | 补充形式 | 箭头含义 |
|---|---|---|
| 改动跨哪些模块/服务、实际由谁调用谁 | L1 模块/服务调用图；必要时 L2 关键函数切片 | 已核验的调用/返回 |
| 数据从哪来、如何转换、保存或读取 | 数据流图 | 数据流转，不代表函数调用顺序 |
| 异步、并行、等待、回调、超时、重试、汇合 | 时序图 | 消息、等待和返回；写清并行/汇合条件及失败处理 |
| 业务状态、可用动作、允许/禁止迁移 | 状态转换图 | 状态迁移及触发条件 |

专项图同样使用白话字符图，只表达其标注的关系。多种关系确有必要时分别补图；未命中不补，未知关系标缺口，不靠拆图掩盖。

#### 2.5 基线与证据不抢正文开场

- 详细仓库路径、分支/HEAD、工作区覆盖、CodeGraph 状态、采集时间、E 编号、源码行号及工具输出，集中到一处默认折叠的证据区；编号仍可定位和跳转。
- 主图保留简短身份提示，如“以前来自历史基线；改后是设计目标，尚未实现验证”。不能把历史定位或设计草图当当前源码/运行证明。
- 影响方案成立、批准或读者理解的限制及未确认事项必须默认可见，并贴近相关节点；不把风险全部藏进证据折叠。

### 3. 接口与契约设计
接口签名、请求/响应结构、数据模型、模块边界。契约是本阶段最重要的产出：批准后前后端/各模块按契约并行开发，改动需重新批准。

按上述两轮方法展示关键结构从最简输入/输出到最终契约的必要增量；说明空值、失败、多值等适用边界及调用方行为，不只贴最终 JSON。检查字段/状态是否重复，明确兼容和后续扩展的代价；已有契约不得仅为简化结构而破坏调用方。

### 4. 历史资产复用分析
**复用是默认，从零需要理由。**先对需求定性，再逐项盘点可复用/可扩展复用的资产，每项给出真实路径作为证据。确需从零开发的项，写出理由。

### 5. 多方案并列（有多个可行方案时必须有）
表格对比各方案的取舍，给出推荐及理由，然后**停下来让用户选择**——agent 不替用户拍板。选定结果记入 frontmatter `chosen`。

比较不仅看当前开发成本，还看可信变化下的改动范围、兼容/迁移成本及提前预留成本；不将“最短”或“最通用”自动等同于推荐方案。

### 6. 审查结论（附证据）
除三个维度外，必须审查主链解释与图证据：新旧流程是否走到结果，关键变化是否有最小例子；代码事实是否按适用的新鲜度步骤核验；历史证据是否保留身份；设计节点是否有需求/方案依据；开发定位是否对应主链变化，专项图是否确有必要。纯展示重生成不得声称完成未执行的源码或业务验证。

三个维度：可行性 / 复用性 / 规范性（代码风格、架构约束）。可行性审查同时检查当前完整性和演进压力测试，说明预留边界是否值得、未预留的代价是否可接受。

**铁律：每条结论必须附证据**——实际执行了什么命令、读了什么文件、看到了什么输出。**未执行的项目如实标注"未执行"**，说明留待何时验证。禁止表演式审查：没有证据的"通过"就是谎言。

### 7. 最小验证
- **人能否讲明白**：不展开证据、不读源码，只看主链和例子，逐项回答：①从哪开始、最终得到什么？②关键判断和各分支分别去哪？③改了哪些步骤、哪些没动？④一个具体输入在改前/改后有什么不同？⑤差异为什么改变下游结果？回答不出来就返工正文，不能靠补编号通过验收。
- **图与依据一致性**：抽查主链及实际补充的技术图的入口、关键分支、副作用和失败路径；没有证据的关系不得标为已确认，业务推进不得伪装成函数调用。
- **展示回归**：首次调整此表达规则时，用用户认可的真实场景重新生成对照，再以一个不同类型的小场景检查是否泛化；静态检查只确认结构，不代替内容审查及桌面/390px浏览器实拍。
- **风险点**：方案里最悬的假设是什么？（"看起来美好顺畅、实际有大山"的那个东西）
- **验证方法**：用最小实验暴露它——查真实表结构、跑通候选 SQL、起个最小服务调通接口。实验代码用完即弃，不进文档
- **结果与证据**：实际输出原文贴上来
- **结论用大白话写**：可行 / 不可行 + 一句话原因。检验标准：非技术读者第一遍就能看懂

## 执行顺序

```
批准需求与证据身份复核 → 按适用范围刷新代码证据 → 最小完整方案推导与演进压力测试 → 白话场景新旧主链 → 关键变化及最小例子 → 开发定位与必要专项图 → 三维度审查 + 可解释性/依据/展示验证 → 结论回填 → 提交用户批准（纯展示重生成保留原批准状态）
```

最小验证不通过 = 方案打回重做，不许带着失败结论请求批准。

## 禁止事项

- 需求文档未批准就开始设计
- 只给一个方案就请求批准（有多个可行方案时必须并列）
- 写没有证据的审查结论
- 替用户选择方案

- 以“最简单”为由省略当前正确性、安全、兼容或恢复约束
- 无依据地提前实现未来功能，或忽视已确认的高成本演进要求
