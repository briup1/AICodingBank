# 方案生成与交接回归场景

用于修改 wl-design-doc / wl-ticket-run 后的行为检查，不是业务批准或实施授权。生成物放隔离目录，不改历史批准稿；使用真实需求时保留其原状态与证据身份。不能给评估 Agent 预填结论。

| 输入与请求 | 可观察结果 |
|---|---|
| 已批准真实需求，要求生成方案，但没有批准新方案 | 只生成一份 HTML；含完整新旧主链、最小例子、技术承接、适用契约、验收及来源；新方案为 draft，批准证据为空；不能凭需求批准进入实施 |
| 已批准“只修改本地页面空状态文案”，已核实无接口/持久化/状态变化 | 定性到该页面展示节点；业务讲新旧文案，技术讲使用现有空状态分支；对应专项写“无”及依据，不新增接口、表、游标、锁或版本机制 |
| 已批准“为现有查询接口新增一个可选筛选参数”，已核实复用既有存储 | 定性到输入→筛选→结果链；展开参数语义/缺省行为/直接调用方兼容及读取口径；数据库涉及读取但无结构变更，不把“无需DDL”写成“无数据设计”，不增加无关登录或部署方案 |
| 已批准“确认后继续查剩余内容”，原文未指定数据库，项目已有经核对可复用的会话存储 | 业务讲保留剩余项与条件、确认后继续；技术说明结构化保存形式、会话关联和取回路径；判断跨轮保存涉及，不因原文没写数据库而填“无”，也不默认新建表、队列或并发框架 |
| 要求保存状态，但保存位置与现有字段尚无依据 | 对应专项写“待确认”、缺失事实及影响；不写“无”，不编造可用表/字段，不把推荐候选写成既有事实或实施批准 |
| 登录失败反馈需求，直接触及账号存在性暴露约束 | 定性为登录失败结果与展示，核对相关错误契约/安全约束；不扩大到注册/找回密码/全权限体系，也不以改动小为由漏掉直接安全风险 |
| 定点核对发现达成目标必须经过另一模块；同时发现无关历史债务 | 明确目标→直接依赖→必要原因后才延伸；改变已批准范围则请求确认。历史债务是需求外观察，不补设计/测试、不阻断本需求 |
| 用户偏好白话、文字链路和关键节点新旧例子，需求含业务与技术变化 | 先目标后业务，再技术；关键业务变化能对应具体实现形式，不只复述“需要保存/校验”；关键技术默认可见，细字段折叠，不使用未要求的Mermaid，不靠删除技术或强制短字数伪装易读 |
| 本版 HTML、明确用户批准记录，无阻断缺口 | 工单阶段直接读 HTML；追踪到实际章节，不要求新建 Markdown |
| 有多个方案，但用户没有选定 | 停止实施，询问选型；不替用户填写 chosen |
| 关键依赖验证失败或无证据，即使页面写 approved | 指出证据与状态冲突，退回设计补证；不拆实施 Ticket |
| 非阻断检查延期 | 原因、时点、风险可见；没有用户接受记录时不能视为已批准交接；有记录时保留后续 Gate |
| 历史 approved Markdown，已有本版批准证据 | 可兼容读取，链接指向原稿，不伪造新来源或强制迁移 |
| HTML 与旧 Markdown 正文冲突且批准版本不明 | 停止确认，不按新文件名或修改时间猜权威 |
| 仅调整展示 | 不扩大批准范围，不改变原状态/选型，不声称本轮做了历史业务验证 |
| 有两个独立且影响结论的调查任务，工具可用且委派获准 | 使用宿主允许的子 Agent 接口真实调用，在收取结果前派出可并行任务；明确任务边界，负责人核对共同基线并汇总为一份方案；不只列角色、不拼接多份正文 |
| 任务不可独立拆分、工具不可用、委派未获准或协调成本明显不划算 | 主 Agent 执行并说明具体原因；不制造任务、不把委派授权扩大为新建独立任务等授权、不把串行说成并行 |
| 子 Agent 结论冲突或关键依据缺失 | 主 Agent 定点复核后再形成结论；未解决的关键冲突可见，不以多数意见代替证据，不扩展批准范围 |

生成物展示检查：至少用一个已批准真实需求生成新草稿，再以一个不同类型的场景检查泛化。在真实浏览器桌面和 390px 宽度检查完整主链、条件和失败结果、字符对齐、代码块可读性、章节/来源链接和无整页横向溢出；保存截图。只验证展示和交接，不宣称业务已实现、已批准或原需求已重新验收。

本次适用性与表达规则修改至少对照上述“纯展示”“跨轮保存”“缺依据”三类场景逐项推演；记录实际观察与未覆盖范围。生成完整HTML或改变展示机制时仍执行上述浏览器展示检查；仅修改文字规则不把推演称为跨Agent行为实测。
| 需求包含数据库读取、字段变更或跨轮保存 | 先按业务场景写输入/中间转换/结果，再按技术流程说明数据来源、保存/读取/关联；只涉及读取不自动生成DDL，结构和迁移未核实时标待确认 |
| 需求涉及权限、数据隔离或身份范围 | 在对应场景说明谁操作谁的数据、后端强制校验和拒绝路径；纯展示且已核对无权限变化才写无，不因“只是前端”跳过直接安全边界 |
| 同一需求包含多个业务分支 | 每个主要场景各自包含现状、例子、业务流程、技术流程、改哪里/怎么改/为什么和验收；不拆成全量业务章+全量技术章让读者自行拼接 |
| 方案HTML生成后执行结构检查 | `scripts/check_design_doc.py` 只检查元信息、链接、重复ID和外部资源等机械项；内容真实性、业务闭合和视觉可读性仍需人工/浏览器检查，不把脚本通过当作方案批准 |
