# 需求确认（wl_req-confirm）

开发流程的第一阶段。目标：在动手之前，把"需求方到底要什么"变成一份人审批准的文档。

**为什么**：返工最贵的根源不是代码写错，而是需求理解错——照单执行了一个本可被质疑推翻的方案。本 skill 的核心价值在"质疑需求本身"。

**职责范围（先划边界，再走流程）**：本阶段只回答三个问题——**要什么**（What）、**为什么**（Why）、**怎么算完成**（验收）。**不回答"怎么做"**（How）：技术选型、架构、模块划分、接口定义、参数取值全部属于方案设计阶段，不是本 skill 的产出，也不是本 skill 可以"顺手写一点"的灰色地带。

边界判据：需求文档允许的最高颗粒度是**可外部观测的行为与客观约束**（如"无凭证返回 401"、"脚本无法读写工作区外路径"、"部署环境无 Docker"）；任何必须打开代码库才能写出的表述（组件名、配置项、provider 名、库/框架选型、重试次数、表结构）都是方案，禁止出现在产出中。

**出口条件**：需求文档被用户明确批准（frontmatter `status` 置为 `approved`）。未批准前，禁止进入方案设计。

## 流程

### 1. 看全貌
读完用户提供的全部需求材料（口述、文档、链接）。不急于动手，不急于提问。

### 2. 理解项目
探索代码库现状：目录结构、架构约定、CLAUDE.md/README、相关模块。需求必须落在对项目真实状态的理解上，而不是想象上。

### 3. 重定义需求（本 skill 的招牌环节，禁止跳过）
回答三个问题并写进文档：

1. 提出需求的人，**最终目标**是什么？（不是他描述的方案，是他要的结果）
2. 当前需求描述的方式，是达成最终目标的**最佳方式**吗？
3. 如果不是——**提出异议**，给出更好的路径和理由，显式挂在文档里等需求方确认。是最佳路径也要写明"已求证"。

### 4. 方案剥离（源材料夹带方案时的必经处置）
现实中的需求材料（尤其是 PRD）几乎必然夹带方案层内容：技术选型、模块名、配置结构、参数建议值。**禁止誊抄进需求文档**，按三类分流：

1. **方案背后的真实意图** → 提炼为需求或客观约束（例：PRD 写"实现 docker provider"→ 需求是"脚本与宿主机文件系统/网络隔离"，约束是"部署环境无 Docker"）；
2. **方案本身** → 作为候选参考原样移交方案设计阶段，需求文档中至多一句"实现选型留待设计"；
3. **被否决的方向** → 写入 Out of Scope 封存，防下游滑回旧方案。

### 5. 术语沉淀
对话中说清的领域术语，当场写入项目根目录 `CONTEXT.md`（只放术语，不放实现细节）。用户用词与术语表冲突、或与代码矛盾时，立刻质问澄清，不带入下游。

### 6. 拆分用户故事
用 Matt 式格式穷举，每条讲清价值：

```
As a <角色>, I want <能力>, so that <价值>
```

写不出 so that 的故事，说明价值存疑——回第 3 步质疑。故事中出现技术选型、组件名、配置项 = 越界，同样回炉重写。这一阶段只用 Matt 式（对齐人），验收级的 G/W/T 留给工单阶段。

### 7. 明确不做什么（Out of Scope）
逐项列出本期不做的事。被否决的方案方向也写进来（防下游讨论滑回旧方案）。

### 8. 验证方案
只覆盖**交付验收**维度，按需求选择适用项：接口验证 / 单元测试 / E2E。验收条目同样遵守边界判据——写可观测结果（"返回 403"、"读敏感文件失败"），不写验证哪个组件的内部行为。不写业务成效度量。

## 产出

```
docs/requirements/NNNN-slug/
├── requirement.md      ← 唯一事实来源
└── requirement.html    ← 生成物，供人阅读
```

- **HTML 生成规范见 `doc-html-style.md`**（S1 编辑出版·暖纸风 + 侧边导航布局），生成前必读
- 编号 NNNN 从 0001 起递增；slug 为英文短横线命名
- frontmatter：`id / slug / status / created / source`
- 状态机：`draft → reviewing → approved → designing → implementing → done`
- **Markdown 是唯一事实来源，HTML 是生成物**——只改 md，按 `doc-html-style.md` 重新生成 HTML；绝不直接编辑 HTML

## requirement.md 模板

```markdown
---
id: NNNN
slug: <slug>
status: draft
created: <YYYY-MM-DD>
source: <来源>
---

# 需求 NNNN：<标题>

## 需求重定义
**原始诉求**：…
**最终目标**：…
**异议**：（有异议则写出理由和替代路径，标注"需需求方确认"；无则写"已求证，当前描述是最佳路径"）
**约束**：（客观环境/资源限制，如"部署环境无 Docker"；无则省略）
**重定义后的需求**：…

## 用户故事
1. As a …, I want …, so that …

## 不做什么（Out of Scope）
- ❌ …

## 验证方案
| 维度 | 内容 |
```

## 禁止事项

- 不写实现决策——包括从技术选型到参数取值的任何"怎么做"；**即使源材料（PRD）里已经写好了，也不得誊抄**（处置方式见第 4 步"方案剥离"）
- 不做业务成效度量（本流程面向开发交付）
- 不在需求文档里内嵌术语表（用项目级 CONTEXT.md）
- 未经用户批准就把 status 置为 approved
