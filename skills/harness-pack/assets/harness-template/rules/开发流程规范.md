# 开发流程规范

> 状态：草案（待人工确认）

## 1. 需求分析阶段
- 使用 `skills/需求分析/SKILL.md`：解析需求 → 业务/技术影响分析 → 冲突检测 → 输出分析文档。
- 产出经用户确认后才进入设计。

## 2. 技术方案设计
- 涉及新实体/接口/表结构时，先更新 `wiki/` 对应文件（或提出更新补丁），再动工。
- 方案要点：改哪些文件、怎么测、有什么风险。

## 3. 编码实现阶段
- 使用 `skills/编码实现/SKILL.md`，按 Model → Repository → Service → MQ → Controller（后端）/ API → 类型 → 组件（前端）顺序推进。
- **分支管理**：{待填，如 main 保护、功能分支命名 feat/xxx、提 PR 合入}
- **提交规范**：按 `rules/工程结构.md` 第五节 Conventional Commits。

## 4. 代码评审阶段
- 提交前必过 `skills/代码审查/SKILL.md`（红线检查 + 性能与规范 + 坏味道）。
- 重大变更追加 `skills/专家评审/SKILL.md`（DDD 符合度、并发一致性、扩展性、技术债）。

## 5. 测试阶段
- 使用 `skills/单元测试编写/SKILL.md` 补测试。
- CI 使用 `skills/单元测试CI/SKILL.md`：覆盖率门槛 {待填，如整体≥80%、核心模块≥90%、变更文件≥70%}，不达标拒绝合入。
- **合入前反补检查（兜底）**：PR 描述必须勾选「已执行 harness-sync 反补（或本次无需反补）」；评审者对照 `changes/` 检查是否有对应记录——无记录且未声明“无需反补”的，打回。这是防保鲜循环静默断裂的最低成本门禁。

## 6. 部署上线
- 使用 `skills/部署验证/SKILL.md`：健康检查 → API 冒烟 → 依赖验证 → 监控确认。

## 7. 收尾（强制）
- 任务完成后执行 `harness-sync` 反补：新约定、新术语、协议/结构变更回流到本规范体系，并记录到 `changes/`。
