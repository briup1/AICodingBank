# 开发流程规范

> 状态：草案（待人工确认）
> 定位：任务生命周期状态机。每个阶段写清五要素——**准入条件 | 必做动作 | 产出物落点 | 退出条件 | 卡点**（卡点是必须停下、交棒给人类或外部系统的位置）。
> 验证基线：{branch@commit + 时间}
> 出处纪律：每条流程要素必须有出处——用户决策（greenfield 立法）或仓库证据（legacy 归纳：分支历史、CI 配置、tag 记录）；两者皆无的"想当然流程"禁止写入。组织无法本地读取的规定（分支保护、PR 必填项）由用户在生成时供给并标注来源。

## 1. 风险分级路由

| 等级 | 典型影响 | 最小流程 |
|------|----------|----------|
| 低 | 文档、注释、局部无行为变更 | 读取相关规则 → 修改 → 最小验证 |
| 中 | 单模块行为、接口实现、常规缺陷 | 影响分析 → 测试/复现 → 实现 → 审查 → 验证 |
| 高 | 安全、权限、数据模型、跨模块契约、发布或不可逆操作 | 需求确认 → 方案与回滚评审 → 实现 → 独立审查 → 完整验证 → 明确发布授权 |

风险示例只作路由参考；以实际影响面、可逆性和项目约束为准。等级决定走主路径的哪些阶段、跳过哪些阶段——它是门禁触发器，不是装饰。

## 2. 任务主路径

### 2.1 需求分析

- **准入**：{收到任务/缺陷报告}
- **动作**：读 wiki 相关知识（领域术语/业务模型/接口协议）→ 按 `rules/工程结构.md` 定位受影响模块 → 明确验收标准、影响面、不做什么；执行器 `skills/需求分析/SKILL.md`
- **产出物**：{summary.md 或项目实际采用的需求载体，写明落点}
- **退出**：验收标准可判定、影响模块清单确定
- **卡点**：{按项目填写；需求本身含糊时找谁确认}

### 2.2 方案设计

- **准入**：风险分级为中/高
- **动作**：先查已有扩展点与实现模式；依赖方向按工程结构已确认的依赖图，不用固定技术栈顺序；输出方案（含回滚思路）
- **产出物**：{方案文档落点}
- **退出**：{方案获批的判定者与形式}
- **卡点**：**方案未经批准不得进入编码**（高风险必卡）

### 2.3 编码实现

- **准入**：低风险直接准入；中/高风险须先过 2.2
- **动作**：遵循 `rules/编码规范.md`；落点按 `rules/工程结构.md`；执行器 `skills/编码实现/SKILL.md`；按逻辑单元提交（Git 规约见第 3 节）
- **产出物**：代码 + 对应测试
- **退出**：本节最小验证命令全部通过
- **卡点**：无

### 2.4 评审与 CI

- **动作**：提交 PR/MR → 触发 CI（流水线或命令：{按项目填写}）；执行器 `skills/代码审查/SKILL.md`，门禁 `skills/单元测试CI/SKILL.md`
- **退出**：CI 绿 + {评审人数/角色要求}
- **卡点**：**评审通过前不得合并**；高风险变更经 `skills/专家评审/SKILL.md`；AI 推完 PR 即停手

## 4. 异常路径与卡点

- **评审打回**：回到 2.3 按评审意见最小修改，重走 2.4；不重开分支。
- **CI 失败**：本地复现失败命令 → 修复 → 重推；禁止用 {--no-verify 等按项目列举} 手段绕过门禁。
- **发布后异常**：按 2.6 记录的回滚步骤执行；无回滚能力的项目如实写"回滚 = 回退提交并重新发布"，禁止虚构回滚能力。
- **热修**：从 {发布基线分支} 切 hotfix 分支 → 最小修复 + 复现测试 → 完整走 2.4/2.5 → 先合入发布基线，再 {是否回灌开发分支，按项目}。
