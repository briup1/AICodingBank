# 工程结构规范

> 状态：草案（待人工确认）

## 一、总体架构原则

- **约定优于配置**：目录即规范，物理结构强制逻辑分层。
- **单向依赖**：上层可依赖下层，严禁反向依赖。
- **AI 友好**：任何模块的位置可预测，AI 不需要猜。

## 二、后端工程结构（{后端技术栈}）

```
{后端目录}/
├── config/          # 配置类
├── controller/      # 控制器层：路由、参数校验、响应构造
├── service/         # 服务层：业务逻辑、事务
│   └── impl/
├── repository/      # 数据访问层
├── model/           # 模型层
│   ├── entity/      # 数据库实体
│   ├── dto/         # 数据传输对象
│   └── vo/          # 视图对象
├── mq/              # 消息队列（如适用）
│   ├── producer/
│   └── consumer/
└── common/          # 通用模块：exception / enums / constant / util
```

**四层调用链**：`Controller → Service → Repository → Model`

| 层 | 职责 | 禁止事项 |
|----|------|----------|
| Controller | 请求路由、参数校验、响应构造 | 禁止直接操作 Repository / Model |
| Service | 业务逻辑、事务管理 | 禁止反向依赖 Controller |
| Repository | 数据访问、SQL/查询映射 | 禁止包含业务逻辑 |
| Model | 数据结构定义 | 禁止依赖任何上层 |

## 三、前端工程结构（{前端技术栈}）

```
{前端目录}/src/
├── assets/        # 静态资源
├── components/    # 公共组件
├── composables/   # 组合式函数/可复用逻辑
├── layouts/       # 布局组件
├── router/        # 路由配置
├── stores/        # 状态管理
├── styles/        # 全局样式
├── types/         # 类型定义
├── utils/         # 工具函数
└── views/         # 页面视图（按路由模块划分）
```

## 四、领域驱动设计（DDD）建议

- 按业务域划分模块/包边界，跨域调用走明确的接口，不直接读别域的表。
- 领域术语统一见 `wiki/领域术语.md`，命名以术语表为准。

## 五、代码提交规范（Conventional Commits）

```
<type>(<scope>): <subject>

type: feat | fix | docs | style | refactor | test | chore | perf
```
- 一次提交只做一件事；提交信息用中文描述清楚"为什么"。
