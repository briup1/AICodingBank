# 接口协议规范

> 状态：草案（待人工确认）

## 1. REST API 设计规范
- 资源命名：小写、复数、层级表达归属（如 `/api/orders/{id}/items`）。
- 动词用 HTTP 方法表达：GET 查 / POST 增 / PUT 全改 / PATCH 部分改 / DELETE 删。
- 版本策略：{待填，如 /api/v1 前缀}。

## 2. 统一响应结构
```json
{ "code": 0, "message": "success", "data": {} }
```
- 成功 `code = 0`；失败为业务错误码（见第 3 节）。

### 2.1 成功响应
- data 为对象或分页结构（见第 5 节）；无数据时 data 为 null 或 {}。

### 2.2 错误响应
```json
{ "code": 10001, "message": "用户友好的错误描述", "data": null }
```
- message 面向用户可读；排查细节进日志，不进响应。

## 3. 错误码规范
| 区间 | 含义 |
|------|------|
| 0 | 成功 |
| {待填，如 1xxxx} | 参数/客户端错误 |
| {待填，如 2xxxx} | 业务规则错误 |
| {待填，如 5xxxx} | 系统/依赖错误 |

- 错误码登记表随接口一起维护在本文档第 6 节。

## 4. 接口安全
- 鉴权方式：{待填}；所有写操作必须鉴权。
- 入参校验：服务端为准，不信任前端校验。
- 敏感字段（密码、token、手机号等）不出现在日志和响应中。

## 5. 分页与排序
- 请求：`page`（从 1 起）、`size`（上限 {待填}）、`sort`（白名单字段）。
- 响应：`{ list: [], total: n, page: p, size: s }`。
