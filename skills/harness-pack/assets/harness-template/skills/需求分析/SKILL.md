# 需求分析 Playbook

> 状态：草案（待人工确认）

## 目标

在编码前沿真实调用链确定修改落点、契约、状态、不变量和验证方式，而不是只列受影响目录。

## Step 1：需求与验收

- 明确用户/调用方、触发条件、可观察结果、失败判定和不做什么。
- 缺陷定义稳定复现；新行为定义至少一条端到端验收路径。
- 列出假设和待确认项，不把推测写成项目事实。

**完成标准**：每条验收都能对应到可观察输出或可执行检查。

## Step 2：从能力地图定位入口

读取 `wiki/业务模型.md`，找到对应能力、用户入口、调用方和提供方。能力未登记时从真实入口反向追踪，并把缺失列为 Harness 同步项。

**完成标准**：能指出请求或动作从哪里产生，最终由谁完成。

## Step 3：沿工程结构追踪修改链

读取 `rules/工程结构.md` 的运行时链路和变更落点地图，逐跳检查调用方、核心逻辑、提供方、外部系统和返回路径；查找既有 helper、store、handler、adapter、注册表或插件点。

**完成标准**：列出每个受影响模块、具体落点和不受影响模块，说明复用点。

## Step 4：核对契约与状态

- 从 `wiki/接口协议*` 找到每个受影响接口/消息的请求、响应、错误、安全、副作用和兼容语义。
- 从 `wiki/数据模型.md` 核对结构、权威所有者、生命周期、隔离、并发和失败恢复。
- 检查性能、安全、权限、迁移和运维影响；不适用项写 N/A 及理由。

**完成标准**：契约字段和状态变化均有来源；未知项已提问或标 proposed。

## Step 5：风险路由与验证

按 `rules/开发流程规范.md` 选择最小充分流程，并从工程结构、编码规范和现有测试中给出验证矩阵。写入、迁移、部署、重启、回滚或权限变更必须明确授权和恢复步骤。

## 输出

- 目标、验收标准和不做什么；
- `入口 → 调用方 → 契约 → 提供方 → 状态/外部系统 → 返回` 链路；
- 按模块列出的修改点、复用点和不受影响项；
- 接口与状态变化前后对比；
- 性能、安全、数据和运维影响；
- 测试与验证矩阵；
- 假设、待确认项、风险和 Harness 同步项。
