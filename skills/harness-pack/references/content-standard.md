# Harness 内容完整性标准

Harness 是面向开发任务的工程手册。证据保证内容可信，但正文首先要让开发者和 Agent 能定位代码、遵循项目写法、理解契约和完成验证。

## 一、文档职责

| 位置 | 必须回答的问题 |
|------|----------------|
| 根入口 | 当前任务应读取什么、哪些红线始终生效 |
| `rules/工程结构.md` | 代码在哪里、如何分层、依赖方向是什么 |
| `rules/编码规范.md` | 在各模块中新增或修改代码具体应怎么写 |
| `rules/开发流程规范.md` | 不同风险和变更类型如何分析、实现、验证和交付 |
| `wiki/业务模型.md` | 系统提供什么能力，每项能力由哪些模块、接口、状态和测试实现 |
| `wiki/接口协议.md` 或其子目录 | 每个实际接口、事件或消息的完整调用契约 |
| `wiki/数据模型.md` | 数据和状态由谁拥有、存在哪里、如何变化和隔离 |
| `wiki/领域术语.md` | 产品、代码、协议和外部系统中的关键名称如何对应与消歧 |
| `skills/` | 完成一类任务时可直接执行的步骤、停止条件和完成标准 |
| `agents/` | 各角色的权限边界与委派关系；工序只在 `skills/`，角色文件是薄壳，不复制步骤 |
| `changes/` | Harness 本身何时、为什么、依据什么发生变化 |

根入口保持薄；Rules、Wiki 和 Skills 必须在各自任务范围内自足。已有专项文档仍可作为权威来源，但 Harness 应提供完成当前开发任务所需的摘要、导航和派生视图，不能退化成链接列表。

## 二、权威来源与派生视图

- **权威来源**决定冲突时以谁为准，例如正式 API 文档、schema、项目指令或生成类型。
- **派生视图**按开发任务重新组织权威信息，例如接口调用方、实现位置、测试和状态影响的联合视图。
- 派生视图标注来源、验证基线和同步责任；这不是建立第二个裁决源。
- 一条规范只在一个地方定义，其他文档引用规则 ID；实现事实可以在不同任务视图中摘要，但必须指回同一权威来源。

## 三、内容类型

| 类型 | 用途 | 对新增代码的约束力 |
|------|------|--------------------|
| 已确认规范 | 项目指令、自动门禁或用户明确批准的目标约束 | 强制 |
| 默认实践 | 从当前范围内稳定实现和扩展点归纳的推荐写法 | 默认遵循；偏离时说明理由，不作为既有门禁 |
| 事实 | 指定版本和范围内可观察的实现 | 用于理解现状，不直接阻断 |
| 技术债 | 已确认规范的存量违反 | 只阻断新增或扩大 |
| 提议 | 尚未批准的目标设计 | 不参与门禁 |

Legacy 可以从稳定实现归纳“默认实践”，但必须写明适用范围、代表性证据、反例和偏离条件；不能把它冒充强制规范。Greenfield 中的默认实践必须经用户选择，AI 推荐仍是提议。

## 四、探查完整性

先判断对象属于哪一种集合：

### 有限契约：全量枚举

对当前版本中可静态识别的下列集合逐项核对，不得抽样：

- HTTP/GraphQL/RPC/CLI/库公开入口；
- 项目实际消费或处理的消息方法、事件、通知和反向请求；
- 状态机、枚举、错误类型和公开配置键；
- 生产模块、运行入口和跨模块注册点；
- 数据 schema、迁移和对外序列化结构。

记录发现方式、总数、已文档化数和排除项。生成代码或大型第三方协议只需完整覆盖“项目实际消费/暴露的子集”，并指向权威全集。

### 开放惯例：按范围抽样

命名、错误处理、组件组织、测试写法等开放集合按语言、模块和职责分层抽样，记录检查数、命中数、反例和未覆盖范围。代表性样本用于归纳默认实践，不用于声称全仓一致。

## 五、正文深度

### 工程结构

最小可用集（先保住地图可用；本节之外的内容不默认生成，确有需要时经 harness-sync 增量补充）：

1. **实测目录结构**：按工作区全量覆盖生产目录，每个目录注释基于证据写实际职责与边界；写不出边界的如实标注混杂/杂物间，名义与实际不符照实注释；
2. **分层与识别信号**：从 import 关系归纳实际分层及判断锚点；项目没有稳定分层就如实说明，不硬套 N 层架构；
3. **依赖方向**：实测方向结论带内容类型与证据；反向依赖实例归入事实或债务，不把未证实的方向写成“严禁”规则。

不预设任何技术栈的分层命名；不描述目标架构，不指导重构。

### 编码规范

按项目实际使用的技术栈组件成节（中间件/框架/库，项目有什么写什么，不预设技术栈），每节三个小类目：

- **用法**：不变量、禁止项（含禁止平行机制）、默认写法骨架，规则写成可判定动作并配 ✅/❌ 示例；
- **错误与并发**：异常、重试、幂等、事务、权限和资源清理，按组件特性取舍；
- **测试**：测试写法、fixture/mock 惯例与位置，以及 lint/CI 能自动兜住的规则。

横切的项目级约定（traceId、统一错误结构等）单列薄节。所有规则过“删除测试”：删掉后 AI 默认会违反才留下，显而易见的通用内容不写。新增代码的落点归 `rules/工程结构.md`，本文不重复。配置事实和风格统计放末尾依据，不占据正文主体。

### 接口协议

通用约定（响应结构、错误码、鉴权、分页、关联 ID）全项目只写一次，端点条目不复述。每个接口、方法、事件或命令以紧凑条目记录：

- 用途、method/path/name、方向、调用方、实现位置、状态（current/proposed/deprecated）；
- 鉴权与身份边界（N/A 写明理由）；
- 请求与响应字段以**字段表**记录（位置/字段/类型/必填/约束与说明），约束含范围与默认值；**凡代码中以 Literal/Enum 定义的类型，必须展开为枚举全集**——枚举是最不能靠调用方猜的参数；
- 错误与状态码（引用通用表 + 特有项）；
- 幂等、副作用、顺序、并发和兼容语义（N/A 写明）；
- 契约、实现和测试来源（路径:行号，经回读核验）。

每域给一个最小合法示例（虚构非敏感值）；字段不能确认标 proposed，不编造。完整性闭合：发现数 = 文档化数 + 排除数。接口很多时按类别拆文件，README 只做目录，不替代逐项契约。API-ID 是跨文档稳定主键：首版按 method+path 字典序分配，再版不重排，新增取最大序数 +1，删除不复用——数据模型、业务模型按 ID 交叉引用。

### 数据与状态

每个重要对象或状态记录：结构、所有者、存储位置、创建/读取/更新/删除路径、生命周期、隔离、并发与一致性、失败恢复和来源；字段级补索引与唯一约束、软删除过滤语义、单位与快照/引用标注。没有数据库时仍需记录内存、文件、浏览器、远端真相源和投影状态。状态与枚举全集的权威只在本文档，其他文档只链接不复述。

### 能力与流程

每项核心能力连接用户入口、前端/调用方、后端/提供方、外部系统、接口、状态和验证，并给一句话关键逻辑/模式短语。核心流程用线性文本时序（触发→入口→处理→状态→结果），写出主路径、状态变化和错误路径，不能只列模块名称。

## 六、任务型验收

生成后至少选取项目实际存在的三类任务做静态推演；不足三类时覆盖全部：

1. 一个跨模块功能变更；
2. 一个接口或协议变更；
3. 一个状态、并发、权限或错误修复。

每次推演必须只借助 Harness 定位出：修改模块、调用链、契约、不变量、测试和验证命令。找不到任一项即判 Harness 不完整，返回补充探查。

成文后先执行**引用复核**：逐条重读文档中所有 `路径:行号` 引用，重跑所有债务/违规 grep；发现漂移立即修正或重新探查，不带已知漂移进入自检。

另执行以下计数检查：

- 有限契约发现数 = 文档化数 + 明确排除数；
- 生产目录/模块发现数 = 工程结构覆盖数；
- 核心能力均能映射到代码、契约、状态和验证；
- 文档中的路径、接口、规则 ID 和测试引用均存在或明确标 proposed。

## 七、成文纪律

- **引用回读**：每个 `路径:行号` 写入前重新打开该位置核对，不得从探索记忆誊写引用；例外、豁免、反例等**负向声明**（如"仅 X 处例外""存量残留 N 处"）与正向引用同标准回读并重新 grep 计数。
- **强断言枚举**：规则或事实断言含"唯一/集中/禁止/只能/保留/默认"等字眼时（**无论是否带行号引用**），必须 grep 相关符号全集并计数；发现的违规如实记为债务或反例，搜不到才写"未发现"。数字断言（"共 N 个 / N 项 / N 处"）与定性断言同标准：解析依赖清单或 grep 实际计数回核，且同段内的枚举名单与总数必须一致。
- **枚举出处**：凡标注"枚举："的取值集合，必须给出 Literal/Enum 定义的 `路径:行号`；代码无此定义的，改写为"约定取值（代码未约束）"，不得用与代码枚举相同的加粗格式表达归纳推断——格式权威不得超过证据权威。
- **反例搜索**：每条规则生成时主动搜索反例——包括通用最佳实践，先怀疑它在本项目是否成立，找到支持证据才写入；反例存在时降级为事实/提议或注明偏离条件。
