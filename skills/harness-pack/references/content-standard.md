# Harness 内容完整性标准

Harness 是面向开发任务的工程手册。证据保证内容可信，但正文首先要让开发者和 Agent 能定位代码、遵循项目写法、理解契约和完成验证。

## 一、文档职责

| 位置 | 必须回答的问题 |
|------|----------------|
| 根入口 | 当前任务应读取什么、哪些红线始终生效 |
| `rules/工程结构.md` | 代码在哪里、模块如何依赖、一次变更应落到哪里 |
| `rules/编码规范.md` | 在各模块中新增或修改代码具体应怎么写 |
| `rules/开发流程规范.md` | 不同风险和变更类型如何分析、实现、验证和交付 |
| `wiki/业务模型.md` | 系统提供什么能力，每项能力由哪些模块、接口、状态和测试实现 |
| `wiki/接口协议.md` 或其子目录 | 每个实际接口、事件或消息的完整调用契约 |
| `wiki/数据模型.md` | 数据和状态由谁拥有、存在哪里、如何变化和隔离 |
| `wiki/领域术语.md` | 产品、代码、协议和外部系统中的关键名称如何对应与消歧 |
| `skills/` | 完成一类任务时可直接执行的步骤、停止条件和完成标准 |
| `changes/` | Harness 本身何时、为什么、依据什么发生变化 |

根入口保持薄；Rules、Wiki 和 Skills 必须在各自任务范围内自足。已有专项文档仍可作为权威来源，但 Harness 应提供完成当前开发任务所需的摘要、导航和派生视图，不能退化成链接列表。

## 二、权威来源与派生视图

- **权威来源**决定冲突时以谁为准，例如正式 API 文档、schema、项目指令或生成类型。
- **派生视图**按开发任务重新组织权威信息，例如接口调用方、实现位置、测试和状态影响的联合视图。
- 派生视图标注来源、验证基线和同步责任；这不是建立第二个裁决源。
- 一条规范只在一个地方定义，其他文档引用规则 ID；实现事实可以在不同任务视图中摘要，但必须指回同一权威来源。

## 三、内容类型

| 类型 | 用途 | 对新增代码的约束力 |
|------|------|--------------------|
| 已确认规范 | 项目指令、自动门禁或用户明确批准的目标约束 | 强制 |
| 默认实践 | 从当前范围内稳定实现和扩展点归纳的推荐写法 | 默认遵循；偏离时说明理由，不作为既有门禁 |
| 事实 | 指定版本和范围内可观察的实现 | 用于理解现状，不直接阻断 |
| 技术债 | 已确认规范的存量违反 | 只阻断新增或扩大 |
| 提议 | 尚未批准的目标设计 | 不参与门禁 |

Legacy 可以从稳定实现归纳“默认实践”，但必须写明适用范围、代表性证据、反例和偏离条件；不能把它冒充强制规范。Greenfield 中的默认实践必须经用户选择，AI 推荐仍是提议。

## 四、探查完整性

先判断对象属于哪一种集合：

### 有限契约：全量枚举

对当前版本中可静态识别的下列集合逐项核对，不得抽样：

- HTTP/GraphQL/RPC/CLI/库公开入口；
- 项目实际消费或处理的消息方法、事件、通知和反向请求；
- 状态机、枚举、错误类型和公开配置键；
- 生产模块、运行入口和跨模块注册点；
- 数据 schema、迁移和对外序列化结构。

记录发现方式、总数、已文档化数和排除项。生成代码或大型第三方协议只需完整覆盖“项目实际消费/暴露的子集”，并指向权威全集。

### 开放惯例：按范围抽样

命名、错误处理、组件组织、测试写法等开放集合按语言、模块和职责分层抽样，记录检查数、命中数、反例和未覆盖范围。代表性样本用于归纳默认实践，不用于声称全仓一致。

## 五、正文深度

### 工程结构

至少包含：

1. 仓库与运行单元总览；
2. 每个生产模块的职责、入口、允许依赖和禁止承载的职责；
3. 实际构建依赖图和运行时调用链；
4. 前端、后端、CLI、worker 等实际子系统的内部导航；
5. 核心跨模块流程；
6. “需求类型 → 修改落点 → 契约 → 验证”的变更地图；
7. 现有扩展点、例外和架构解释。

### 编码规范

按实际语言和模块组织，每节优先写：

- 代码放在哪里；
- 默认实现方式；
- 必须保持的不变量；
- 禁止引入的平行机制；
- 错误、并发、权限和资源清理方式；
- 对应测试和自动检查。

配置事实和风格统计放在规范依据或附录，不得占据正文主体。

### 接口协议

每个接口、方法、事件或命令至少记录：

- 用途、调用方和实现位置；
- method/path/name、版本和方向；
- 鉴权、权限、Origin 或身份边界；
- path/query/header/body 或 payload 字段：类型、必填性、约束和语义；
- 成功响应或结果；
- 错误、状态码、关闭码或失败语义；
- 副作用、幂等、顺序、并发和兼容语义；
- 最小合法示例；
- 契约、实现和测试来源。

接口很多时按 HTTP、客户端请求、服务端请求、通知、事件等类别拆文件；README 只做目录，不替代逐项契约。

### 数据与状态

每个重要对象或状态记录：结构、所有者、存储位置、创建/读取/更新/删除路径、生命周期、隔离、并发与一致性、失败恢复和来源。没有数据库时仍需记录内存、文件、浏览器、远端真相源和投影状态。

### 能力与流程

每项核心能力连接用户入口、前端/调用方、后端/提供方、外部系统、接口、状态和验证。核心流程写出主路径、状态变化和错误路径，不能只列模块名称。

## 六、任务型验收

生成后至少选取项目实际存在的三类任务做静态推演；不足三类时覆盖全部：

1. 一个跨模块功能变更；
2. 一个接口或协议变更；
3. 一个状态、并发、权限或错误修复。

每次推演必须只借助 Harness 定位出：修改模块、调用链、契约、不变量、测试和验证命令。找不到任一项即判 Harness 不完整，返回补充探查。

另执行以下计数检查：

- 有限契约发现数 = 文档化数 + 明确排除数；
- 生产模块发现数 = 工程结构覆盖数；
- 核心能力均能映射到代码、契约、状态和验证；
- 文档中的路径、接口、规则 ID 和测试引用均存在或明确标 proposed。
