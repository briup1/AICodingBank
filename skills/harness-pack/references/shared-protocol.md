# 共享协议：harness-pack 三个 Skill 共用

## 输出位置与模板角色

- 生成物写入目标项目根目录的 `docs/harness/`；只生成项目适用的文件。
- `assets/harness-template/` 是可删减的内容菜单，不是架构答案。目录可按项目规模合并或拆分；不得为了填满模板发明层次、技术、流程或业务事实。
- 根入口只保留任务路由与高优先级约束；Rules、Wiki 和 Skills 必须达到 [content-standard.md](content-standard.md) 的任务自足标准。
- 已有 `AGENTS.md`、`CONTEXT.md`、架构/API 文档和 schema 优先作为权威来源；Harness 可生成面向开发任务的派生视图，并标注来源、验证基线和同步责任，不能只留下链接。

## 信息类型与证据记录

每个可执行规则、架构结论或关键事实必须区分以下类型：

| 类型 | 含义 | 是否可阻断变更 |
|------|------|----------------|
| 已确认规范 | 项目指令、自动门禁或用户明确批准的目标约束 | 是，但只约束标明范围及生效后的新增变更 |
| 默认实践 | 从指定范围内的稳定实现和既有扩展点归纳的推荐写法 | 否；新增代码默认遵循，偏离时说明理由 |
| 事实 | 在指定版本和范围内观察到的实现 | 否；只描述现状 |
| 技术债 | 已确认规范的存量违反基线 | 只阻断新增或扩大，不阻断无关变更 |
| 提议 | 尚未批准的 AI 建议或待决策事项 | 否 |

记录格式至少包含：稳定 ID、陈述、类型、作用范围、支持证据、反证/例外、置信度、验证方式、验证提交和时间。Legacy 中的高频实践可在标明证据、反例、范围和偏离条件后归纳为默认实践，但不能升级为强制规范；高频违反只能成为债务候选。

## 决策项处理

- 先判断事项是否适用于当前项目；不适用时删除对应章节，或记录 `N/A + 理由`，不得强迫用户决定缓存、消息、数据库、REST、覆盖率等不存在的能力。
- 能从代码、配置、测试和正式项目文档核实的内容记为事实，并保留证据与反证。
- 代码无法证明的目标约束只有在确实影响当前项目时才询问用户；不得提供模板默认值冒充项目决策。
- 用户拒答时记为提议/待决策，不得进入门禁。安全、权限、数据破坏、发布和回滚类关键决策未解决时禁止启用相关流程；其他待决策不阻塞无关工作。

## 运行前置与能力声明

生成到 `docs/harness/skills/` 的 Markdown 默认只是**人工 playbook**：它不会因出现“触发条件”而自动运行，也不自动获得审批、部署、数据写入或回滚权限。

只有同时存在并验证了对应 Router、Hook 或 CI/CD 配置，且记录其路径、触发事件、执行命令、验证提交和时间后，才能标为“已自动化”。缺少本 pack Skill 或 owner 调度者时，规范仍可只读使用，由人工按 playbook 操作。

## 技术栈与架构适配

`references/stack-variants.md` 只提供探查问题。生成草案时以目标项目的真实目录、import/调用关系、运行入口、扩展点和自动约束为准，不因语言或框架预设分层、响应包、事务位置、实现顺序或架构标签。

标准架构名称是可选解释。每个候选名称必须附支持证据、反证、作用范围和置信度；证据不足时使用“项目自有架构”“混合架构”或“当前无法命名”。

## 生成后自检

### 所有模式

1. **事实与规范分离**：每项内容类型明确；提议未进入门禁，存量债务只阻断扩大。
2. **证据复核**：事实和规范附具体来源、作用范围、反证、置信度与验证版本；禁止“全仓都遵守”等无分母断言。
3. **引用完整性**：引用文件存在；每项规则只有一个规范来源；派生视图指回权威来源且不与其冲突。
4. **能力声明核验**：自动触发或强制门禁有 Router、Hook 或 CI/CD 证据；否则写成人工步骤。部署验证满足默认只读和副作用授权门。
5. **模板残留检查**：扫描全部模板 token、示例标记和“同上结构”，而不只检查某一种占位符。
6. **关键决策门**：安全、权限、数据破坏、发布和回滚相关待决策已解决，或相关流程保持禁用。

### Legacy 追加检查

- 按 [content-standard.md](content-standard.md) 区分有限契约与开放惯例：前者全量枚举实际暴露/消费子集，后者按范围抽样并记录检查数、命中数、反例和未覆盖范围。
- Rules、Wiki 和 Skills 通过内容深度与任务型静态推演；只有链接或证据账本而无法指导任务时判定失败。
- 运行测试、lint、CI 等自动化只根据仓库静态配置认定；未获授权不执行项目命令。

### Greenfield 追加检查

- 检查用户决策的完整性、内部一致性和可验证验收标准。
- 没有代码时不得声称完成实体、接口、表、枚举或运行时验证。

## 双确认流程

1. **结构确认**：呈现文件清单、复用/删除说明、架构证据表、规则类型清单、未决事项和自检结果。
2. **内容确认**：逐文件走查已确认规范、事实来源、playbook 操作与风险边界。
3. 草案必须标明状态；确认前不得修改目标项目现有入口文件或业务代码。

## 根入口融合规则

- 草案入口暂存于 `docs/harness/CLAUDE.md`；启用后根据目标宿主生成最薄入口，不强制只能使用 `CLAUDE.md`。
- 已有 `AGENTS.md`、`CLAUDE.md` 或其他入口时优先插入指向唯一事实源的短引用，不复制完整规则。
- Harness 托管内容必须使用稳定 begin/end marker；找不到、重复或冲突时停止并交用户裁决，不得猜测修改范围。

## 启用动作

1. 移除草案标识前执行全部自检；关键待决策未解决时只启用无关部分。
2. 按根入口融合规则应用最薄索引，并保留原项目内容。
3. 在 `docs/harness/changes/` 记录初始化范围、规则 ID、事实来源、base/head 提交和验证结果。
