# 共享协议：harness-pack 三个 Skill 共用

## 输出位置

- 生成物统一写入**目标项目根目录的 `docs/harness/`**：
  ```
  <项目根>/
  ├── docs/harness/
  │   ├── CLAUDE.md（草案期暂存，启用后融合进项目根）
  │   ├── agents/owner.md
  │   ├── rules/             # 工程结构 / 编码规范 / 开发流程规范
  │   ├── skills/            # 需求分析 / 编码实现 / 代码审查 / 专家评审 / 单元测试编写 / 单元测试CI / 部署验证
  │   ├── wiki/              # 业务模型 / 接口协议 / 数据模型 / 领域术语
  │   └── changes/           # 变更追踪
  ```
- 模板来源：本 Pack 的 `assets/harness-template/`，**结构与细粒度照抄，内容必须按项目实际替换**（模板中的 `{待填}`、示例红线均不可原样保留）。

## 决策项清单（模板 `{待填}` 的来源映射）

模板中的 `{待填}` 分三类处理，bootstrap 逐项销项，禁止夹在两规则之间编造：

| 类别 | 含义 | 处理方式 |
|------|------|----------|
| 探查可得 | 读代码/配置能得出（框架版本、目录、formatter、lint 规则） | 直接填入 |
| 必须提问 | 代码反推不出的项目决策：覆盖率门槛（三档）、错误码区间、鉴权方式、API 版本策略、表名前缀、回滚策略、核心链路清单、核心模块清单、分支模型、业务异常类名、缓存序列化方式、单函数行数上限 | 向用户提问，逐项销项 |
| 可给缺省 | 常见默认值（如先写库后删缓存、Conventional Commits） | 直接填缺省值并标注 ❓，确认时可改 |

- legacy：探查（Step 2~3）覆盖"探查可得"项；Step 3 收尾时按本清单把"必须提问"项一次性向用户收集，再进 Step 4。
- greenfield：Step 2 分层提问必须覆盖本清单全部"必须提问"项。
- 用户拒答的"必须提问"项：在对应文件写 `> 待决策：{项}（❓ 开发前必须补齐）`，**不甩给 harness-sync**（sync 只捕获开发中实际发生的事实，无法替人做前置决策）。
- 销项完成后才允许生成草案；生成时不得残留 `{待填}` 字面量。

## 运行前置（生成物的环境依赖）

生成物中的 `agents/owner.md`、`rules/开发流程规范.md` 引用了本 pack 的技能（harness-sync 等）和一个 owner 调度角色。在目标项目使用规范体系前确认：

1. 执行环境的 Agent 已安装 harness-pack 三个 skill（否则保鲜循环不生效，规范仍可只读使用）；
2. 存在一个承担 owner 角色的调度者（人或 Agent）。

缺位降级：由人工按 `changes/README.md` 手工执行 sync 流程并记录，规范体系本身不受影响。

## 技术栈适配（技能步骤）

模板技能中的分层名/步骤名是 Java/Spring 视角默认值。生成草案时按 **`../../references/stack-variants.md`** 选用目标栈对应变体（Java / Python-FastAPI / TS）替换，只写一套进项目，方法论顺序不变。

## 生成后自检（进入双确认前强制执行）

草案生成后、呈现给用户之前逐项自检，未过先修，自检结果附在结构确认报告中（通过项一句话带过，未过项说明修了什么）：

1. **关键事实反查**：wiki 中的状态机/枚举取值必须与代码实际定义核对（grep 枚举/常量/状态定义，逐个值比对）；术语表实体、表名、接口路径抽查至少 5 处真实存在。
2. **红线证据逐条复核**：每条红线的证据表述（尤其"全部遵守""全表"类）必须实际验证到具体位置，禁止以偏概全；证据失实先修再确认。
3. **引用完整性**：rules/skills 互相引用的文件真实存在、名字对得上；宪法文件索引与实际文件一一对应。
4. **占位符清点**：无 `{待填}` 残留；❓ 待决策项汇总成清单随结构确认一并呈现。

## 红线标注体系（三分类）

每条红线必须标注来源，生成时分类、确认时逐条过：

| 标注 | 含义 | 处理方式 |
|------|------|----------|
| ✅ | 项目现状已遵守的惯例 | 直接写成规则 |
| ⚠️ | 项目现状违反的点 | 写成规则 + 标注为技术债，不粉饰 |
| ❓ | AI 新提议、项目里不存在 | 必须用户点头才能写入 |

## 双确认流程（人工确认后才算数）

1. **第一确认（结构层）**：生成完成后，先向用户呈现：文件清单 + 技术栈表 + 红线清单（含三分类标注）+ 探查中发现的问题摘要。用户确认结构后进入第二确认。
2. **第二确认（内容层）**：逐文件走查要点（rules 的硬性规定、wiki 的实体/接口/表、skills 的触发条件），用户可逐文件要求修改。
3. **确认前约束**：草案可以写入 `docs/harness/`，但必须带"草案"状态标识；**未确认前不得修改目标项目现有的 CLAUDE.md / AGENTS.md / 任何业务代码**。

### 宪法文件的位置与融合规则（重要）

宪法 `CLAUDE.md` **生成在项目根目录，不放 docs/harness/**：

- 项目根**没有** CLAUDE.md：启用时直接以宪法稿创建。
- 项目根**已有** CLAUDE.md：**融合，不覆盖**——保留原有全部内容，宪法区（技术栈表 + 红线区 + 文件索引）置顶插入；与原有条款冲突的，列出冲突清单在确认阶段由用户裁决，不得自行删改原文。
- 草案期宪法稿暂存于 `docs/harness/CLAUDE.md`（带草案头），**确认通过前不动项目根**；启用时应用融合并删除暂存稿，宪法只此一份，避免双份漂移。
- 规范体系内所有引用"CLAUDE.md"处均指**项目根** CLAUDE.md。

## 启用动作（用户最终点头后执行）

1. 移除草案状态标识，红线标注保留（✅/⚠️/❓ 是长期信息）。
2. **宪法落位**：把 `docs/harness/CLAUDE.md` 草案稿按上述融合规则应用进项目根 CLAUDE.md（项目无根 CLAUDE.md 则直接创建；融合后删除暂存稿，宪法只留项目根一份）。
3. 在 `docs/harness/changes/` 下建立首个变更记录：`0001-YYYYMMDD-初始化-harness.md`（日期为启用当天，格式见 changes/README.md）。
