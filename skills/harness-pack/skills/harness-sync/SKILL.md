# Harness 反补（规范回流）

## 概述

规范体系靠一次生成一定会腐烂；本 skill 是保鲜循环：**开发中实际发生的事实 → 增量补丁 → 人确认 → 应用 + 记录**。

适用前提：项目已有 `docs/harness/` 且宪法已落位项目根 CLAUDE.md（由 harness-bootstrap-legacy 或 harness-bootstrap-greenfield 生成并启用）。

## 执行流程

### Step 1：收集本次变更事实
先定基准再收集 diff（基准不清会污染全部补丁）：
- **默认基准**：当前分支起点（merge-base）；或上一次 `changes/` 变更记录之后的提交范围。
- 用户可指定其他基准；有未提交改动时一并列入并注明“工作区”。

收集内容：
- 本次开发的 diff（代码 + 文档 + 配置）
- 开发对话中用户明确拍板的决策（如“这里就用构造器注入”、“这个状态叫 X”）
- 新增/变更的接口、表结构、枚举状态

### Step 2：逐项对照现有 harness 找差异
按六类检查，只找**增量**：

| 类别 | 检查点 | 典型补丁目标 |
|------|--------|-------------|
| 新约定 | 代码里反复出现、rules 没写的模式 | rules/编码规范.md |
| 新领域知识 | 新实体/状态/术语/业务流程 | wiki/业务模型.md、wiki/领域术语.md |
| 协议/结构变更 | 新接口、响应结构变化、新表 | wiki/接口协议.md、wiki/数据模型.md |
| **规则被突破** | 代码违反了现有红线 | **必须停下来问用户**（见下方原则 2） |
| 新红线候选 | 开发中发现值得升级为红线的高优约束 | 项目根 CLAUDE.md 红线区（需用户点头，❓ 标注，changes 留痕） |
| 标注更新 | 技术债清偿（⚠️→✅）、新提议转正（❓→✅）、规则退役 | 对应红线/规则的标注与正文同步修正，changes 留痕 |

### Step 3：生成增量补丁建议
每处补丁一条，格式：

```markdown
- 文件：wiki/领域术语.md
- 位置：## 1. 业务术语 末尾追加
- 变更：无 → 增加"拼团：xxx"
- 理由：本次订单模块开发中用户确认的概念
- 类别：✅ 已在代码实践（补丁统一用三分类：✅ 代码已在实践 | ⚠️ 涉及现状违反/技术债 | ❓ 新提议需用户点头）
```

### Step 4：人工确认
整批呈现补丁清单，用户逐条批准/修改/拒绝。**拒绝的丢弃，不偷塞。**

### Step 5：应用并记录
- 把批准的补丁写入对应文件（保持原有格式与细粒度）。
- 在 `docs/harness/changes/` 追加变更记录：`NNNN-YYYYMMDD-<主题>.md`（编号递增），内容：日期、触发任务、补丁清单、用户裁决（批准/拒绝及原因）。

## 原则与边界

1. **只提增量补丁，不重写全文**；发现整章过时，单独列出并说明理由，由用户决定整章重写。
2. **规则被实际突破时，不改规则也不改代码**，把冲突原样呈现：「规则说 X，代码做了 Y」，让用户裁决方向；裁决结果连同补丁一起记录。
3. **红线增删走第五类（新红线候选）**，必须用户点头并写入 changes/；规则退役同样留痕。
4. **标注要及时更新**：债务还清、新提议转正时，把 ⚠️/❓ 改为 ✅，禁止规范携带过期标注。
5. 不修改任何业务代码；wiki/rules 补不了的脏数据问题只记录不修理。
6. 项目还没有 `docs/harness/` 时，提示先走 bootstrap，不代劳。
