# Harness 增量同步

先读取 [shared-protocol.md](../../references/shared-protocol.md) 和 [content-standard.md](../../references/content-standard.md)。同步不仅保持证据一致，还要防止工程手册退化成链接索引或过期概览。

## 适用条件

仅在本次工作产生以下至少一项增量时使用：

- 新的稳定项目事实；
- 用户明确批准的工程决策；
- 已实现的接口、数据、状态或模块边界变化；
- 规则新增、退役或技术债基线变化。

没有规范增量时输出“无需同步”并结束，不创建空 changes 记录。项目尚无 `docs/harness/` 时提示使用 bootstrap。

## Step 1：确定可复现基准

1. 只读检查 Git 状态，记录当前分支、`base_ref`、`head_ref` 和未提交文件清单。
2. 基准优先级：用户明确指定的提交 > 最近一条有效 changes 记录的 `head_ref` > 当前分支与已确认目标分支的 merge-base。
3. 基准不唯一、提交不存在或目标分支不明确时停止询问，不猜测“上一次变更”。
4. 工作区非空时记录 tracked diff 的 SHA-256 和未跟踪文件路径；只读取与本次任务有关的内容，不把无关改动纳入补丁。

## Step 2：提取增量并分类

| 类型 | 条件 | 处理方式 |
|------|------|----------|
| 已确认规范 | 有项目指令、自动门禁或用户明确批准 | 分配稳定规则 ID，写入唯一规范来源 |
| 默认实践 | 指定范围内稳定实现或既有扩展点 | 更新对应模块的具体开发指导，附证据、反例和偏离条件 |
| 事实 | 在指定版本和范围内可观察 | 更新权威来源或派生视图，附证据、反证、范围和置信度 |
| 技术债 | 已确认规范的存量违反 | 更新基线；只阻断新增或扩大 |
| 提议 | 尚未批准 | 只列建议，不应用、不参与门禁 |

- 代码中反复出现的写法可归纳为默认实践，但不能自动成为强制规范。
- 规则被突破时原样呈现“规则 X / 实现 Y / 影响范围”，由用户决定修代码、调整规则或登记债务；本 Skill 不改业务代码。
- 未实现设计保持 proposed，只有代码、配置、迁移或测试证据齐全后才能标 current。

## Step 3：定位权威来源与受影响视图

- 优先更新项目已有 AGENTS、CONTEXT、架构/API 文档、schema 或配置中的权威定义。
- 每项规则只在一个文件定义，其他入口通过稳定 ID 引用；同时更新受影响的工程结构、编码指导、能力、接口和状态派生视图，避免局部正确、手册整体过期。
- 有限契约变化时重新计算“发现数/文档化数/排除数”，逐项更新请求、响应、错误、安全、副作用、调用方、实现和测试。
- 修改根入口时仅操作 `harness-pack:begin/end` 边界内内容；标记缺失、重复或嵌套错误时停止。

## Step 4：生成待确认补丁

每项包含：

```markdown
- 目标文件与位置：
- 规则/条目 ID：
- 类型：已确认规范 / 默认实践 / 事实 / 技术债 / 提议
- 变更前 / 变更后：
- 作用范围：
- 支持证据：
- 反证或例外：
- 置信度与验证方式：
- 理由：
```

整批呈现给用户逐条批准、修改或拒绝；拒绝项丢弃。

## Step 5：应用、验证与记录

1. 保存所有待改文件的前置内容哈希；应用批准的文档补丁和 changes 记录。
2. 校验引用、规则 ID 唯一性、状态、模板残留、托管边界和 Markdown 格式；再按 content-standard 重跑受影响任务推演与有限契约计数。
3. 校验通过后记录：`base_ref`、`head_ref`、dirty diff hash、变更文件、批准/拒绝项、验证命令与结果、残余风险。
4. 校验失败时只撤销本次同步写入；若文件已被并发修改则停止并报告，不使用 `git reset`、`checkout` 或覆盖用户改动。

## 边界

- 不修改业务代码，不执行部署、迁移、写库、回滚或重启。
- 不重写无关章节；确需大范围重构时另列方案并重新确认。
- 不把提议转为规范，不把债务伪装为已遵守，不因模板要求创建不存在的文档。
