# 新项目 Harness 正向生成

## 概述

与逆向生成的本质区别：**新项目没有代码可观察，每一层内容都来自"提问→用户决策"**。红线只能来自用户点头，AI 的职责是提供参照选项，不是替用户决定。

先读共享参考（相对本文件：`../../references/shared-protocol.md`）：输出位置、红线三分类、双确认、启用动作。

## 执行流程

### Step 1：需求解析与目标检查
读原始需求（文档/口述/票据），输出一页纸理解：业务目标、用户角色、核心流程、边界假设。**先与用户确认理解无误再往下。**
**护栏**：若 `<项目根>/docs/harness/` 已存在，停下问用户：覆盖重来 / 在现有基础上合并 / 改走 harness-sync 增量更新——不得静默覆盖（会毁掉 changes/ 历史和 sync 沉淀）。

### Step 2：分层提问（核心步骤）
按以下顺序逐层提问，每层给出参照模板里的选项 + 推荐及理由，让用户选或改：

| 层 | 要问什么 | 输出物 |
|----|----------|--------|
| 技术栈 | 语言/框架/存储/中间件，及其选型理由 | CLAUDE.md 技术栈表 |
| 架构分层 | 目录结构、分层方式、依赖方向（禁止反向依赖） | rules/工程结构.md |
| 红线候选 | 按技术栈**只出示相关的**示例红线（金额精度/缓存键前缀/消息幂等/异常封装/依赖注入/事务回滚/前端语法/API 响应结构——Java/Spring 视角，不适用项直接跳过不出示），逐条问“要不要、改成什么” | CLAUDE.md 红线区 |
| 编码规范 | 命名、空值、日志、测试覆盖率门槛等 | rules/编码规范.md |
| 领域 | 核心实体、领域划分、状态机、术语表 | wiki/ 四个文件 |
| 流程 | 分支模型、提交规范、评审/测试/部署环节 | rules/开发流程规范.md |

原则：**一次问一层**，用户答完再进下一层；用户说“你定”时才由 AI 给默认值并明确标注 ❓ 新提议。提问范围必须覆盖 shared-protocol **决策项清单**中的全部“必须提问”项（覆盖率门槛、错误码区间、鉴权方式等），逐项销项。

### Step 3：生成草案
以 `../../assets/harness-template/` 为骨架，把确认的决策填进去，写入 `<项目根>/docs/harness/`。不留 `{待填}` 字面量——用户拒答的"必须提问"项统一写为 `> 待决策：{项}（❓ 开发前必须补齐）`（由 owner 在后续会话显式决策，sync 不背这个锅）。
技能文件中的分层名/步骤名按技术栈适配（参照 `../../references/stack-variants.md`，Java / Python-FastAPI / TS 选一套），删除栈不适用的小节。草案文件头部标注：`> 状态：草案（待人工确认）`。
注意：宪法 CLAUDE.md 的草案稿写入 `docs/harness/CLAUDE.md` 暂存，**确认通过前不动项目根**；启用时才融合进项目根（见 shared-protocol「宪法文件的位置与融合规则」）。

### Step 4：生成后自检
按 shared-protocol 的「生成后自检」清单逐项执行（关键事实反查、红线证据复核、引用完整性、占位符清点），未过项先修，自检结果附进结构确认报告。

### Step 5：双确认
按 shared-protocol：先呈结构（文件清单+技术栈+红线清单+自检结果），再逐文件走查。重点核对：红线是否为 Step 2 用户亲口确认的版本。

### Step 6：启用
按 shared-protocol：宪法融合落位到项目根 CLAUDE.md（已有则融合不覆盖）、去草案标识、写 changes/0001 变更记录。

## 边界

- 只生成 `docs/harness/` 规范体系；**不生成业务代码、不搭脚手架**（用户另下指令再说）。
- 需求信息不足时问，不猜；用户拒绝回答的项按 shared-protocol 决策项清单规则标 ❓ 待决策（**开发前必须补齐**，不甩给 harness-sync）。
- 项目实际已有代码（哪怕一点点），说明这是"老项目伪装成新项目"，改走 harness-bootstrap-legacy。
- 模板（`../../assets/`）或共享 references（`../../references/`）**缺失或不可读时，立即停下报告用户**，禁止即兴编造生成物结构。
