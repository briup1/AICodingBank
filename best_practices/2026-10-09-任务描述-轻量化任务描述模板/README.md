# 任务描述：目标/现场/规则/约束/验收/执行六段模板

## 主题与预期效果

给 AI 派任务时，背景堆太多它抓不住重点，说得太模糊它只能猜。这份模板用六段固定结构压缩一条任务：任务目标、当前现场、业务规则、项目约束、验收标准、执行要求，让 AI“严格按模板理解再执行”。

链路：

```text
任务目标（一句话）
  → 当前现场（涉及文件/函数 + 现状）
  → 业务规则（正常流程/异常处理/业务约束）
  → 项目约束（技术栈/目录规范/依赖限制）
  → 验收标准（可勾选的通过条件 + 回归检查点）
  → 执行要求（先列步骤等确认、分模块输出、不确定先问）
```

预期效果：AI 在动手前必须先把六个格子填满，填不满的地方就是需要回来问人的地方。

## 适用场景

- 有真实代码现场的任务：改 bug、加小功能、接口调整。
- 跨会话交接或给一个不熟悉上下文的执行者派活。
- 希望先得到“改动文件 + 步骤 + 风险点”确认、再放行编码的场景（执行要求第 1 条）。

不适用：探索型任务（还不知道要改什么）；与 [任务编排记录](../2026-06-16-任务编排-目标驱动的多角色任务提示词/README.md) 的分工是：那条管“谁来干”，这条管“任务本身怎么写清楚”，可以叠加使用。

## 原文意图

[原文 prompt.md](prompt.md) 中值得注意的三处：

- “当前现场”要求列出关键文件/函数/模块与现状（报错日志、接口返回、数据库状态）——把“你去找找看”变成“从这些坐标开始”。
- “验收标准”要求写成可验证的 checkbox，并显式包含“现有功能不受影响”的回归检查点。
- “执行要求”第 4 条：“如果有不确定的业务规则，先问，不要猜”——把猜测成本前置成提问成本。

## 建议用法（尚未实测）

1. 当成任务开场白的第一段直接填；填不出的段说明信息缺口，先补齐再发包。
2. 小改动可以合并段落，“验收标准”与“执行要求”建议保留不变。
3. “分模块逐步输出”和“先分析等确认”适合高风险改动；低风险小改可放宽为一步一确认。
4. “依赖限制”三问（能否加包、能否加接口、能否改表结构）建议默认写死答案，防止执行者自作主张。

## 注意事项

- 模板假设的是单执行者顺序流程；多角色并发编排不在本文覆盖范围内。
- “等我确认后再生成代码”会拉长交互轮次，不是所有任务都值得。
- 原文没有执行记录，效果是方法分析，不是实测结论。
