# 任务编排：目标驱动 + 固定团队角色 + 可追溯改动

## 主题与预期效果

把一条开发任务交给 AI 时，只说“完成这个功能”会导致三件事失控：做什么范围靠猜、做得好不好靠感觉、改了什么说不清。这份提示词尝试把任务描述成五块：目标、要求、团队、资源指针、成功标准，并让 AI 以“项目负责人”身份组织一个固定团队来交付。

链路：

```text
任务（目标/要求/资源/成功标准）
  → 项目负责人：想清楚再行动、拆解、协调
  → coder：实现功能或修已知问题
  → tester（独立上下文）：测试并报告问题
  → reviewer（独立上下文）：审核质量与功能实现
  → 按成功标准验收，每处改动可追溯回需求
```

预期效果：任务结果按“成功标准”验收，而不是按“看起来做完了”验收；测试和审核有独立上下文，避免实现者自证正确。

## 适用场景

- 需求已经清楚、可以用文字写清目标和成功标准的开发任务。
- 改动会触碰多处代码，需要控制范围（“只做必要修改”）的场景。
- 希望测试与审核不由实现方自己完成的任务。

不适用：目标还模糊、需要先讨论方案的任务；纯查询或一次性小改动，直接做即可。

## 原文意图

[原文 prompt.md](prompt.md) 的四条“要求”各自针对一类失控：想清楚再行动（防乱改）、简单优先（防过度设计）、外科手术式改动（防顺手重构，每处改动都要能追溯回需求）、项目负责人机制（防无人对最终结果负责，团队外角色通过 subagent 委派）。

团队固定三角色：coder 负责实现；tester 独立上下文测试并报告问题；reviewer 独立上下文审核质量与功能实现。资源区留给需求地址和任务列表；成功标准留给每单任务自己写。

## 建议用法（尚未实测）

1. 先写成功标准，再写任务描述——写不出可验收的标准，说明任务还没想清楚。
2. 资源区放需求文档位置和任务清单指针，不要把需求全文抄进来。
3. 简单任务可以只留 coder 一个角色；测试和审核有价值的前提是任务值得独立验证。
4. 这套结构和当前工作台的岗位制同源：`roles/` 下的项目经理协调、开发实现、测试独立验证、审核独立评审，就是这支团队的正式化版本，见 [岗位名册](../../roles/README.md)。
5. 原文“## 测试任务”一节为空，测试任务部分没有写完，使用时需要自己补。

## 注意事项

- “项目负责人”是分工写法，不改变实际执行者是单个 AI 会话的事实；独立上下文需要真实隔离（subagent 或另行指派）才成立。
- “每处改动可追溯回需求”需要真检查，不能只在提示词里声明。
- 原文没有执行记录，效果（更少返工、更可控范围）是方法分析，不是实测结论。
