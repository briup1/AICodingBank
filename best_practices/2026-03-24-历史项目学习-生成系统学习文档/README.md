# 项目学习：先建立简要路线图，再按主题深入研究

## 问题与适用条件

面对陌生项目，直接要求“全面分析”容易得到一篇篇幅很长、主次不清的报告；一开始就钻进局部代码，又可能不知道这个局部在整体中的位置。本方法希望解决的是：先知道值得学什么、按什么顺序学，再对必要主题深入，形成可单独查阅的研究文档。

适合以理解和学习为目标、需要逐步掌握项目的场景。若只需修一个已定位的小问题，不应自动升级为整个项目学习。上述风险和效果是方法分析，不是已有运行结果。

## 原始提示词与预期效果

[两条提示词原文](prompt.md)保留不变，分别承担两步：

| 原始要求 | 想达到的效果 | 前后依赖 |
| --- | --- | --- |
| 阅读分析本项目，给一份用于研究本项目的简要路线图 | 先得到学习全貌、重点和顺序，而不是立即铺开详细报告 | 依据项目事实形成路线；“简要”约束首轮输出，不代表可以省略依据 |
| 将以上内容按主题分别输出到对应详细调研文档中 | 把概要展开成主题明确、能单独阅读和持续更新的文档 | “以上内容”应指前一步路线图，主题需与路线对应，不能重新随意分组 |

核心链路：项目事实 → 简要学习路线 → 选择/确认主题 → 分主题深入 → 文档互相引用。

## 建议用法（尚未实测）

以下是对原提示词的明确化建议，不是历史上已经执行过的步骤。

### 第一步：先得到能指路的概要

提供项目位置、学习目的和重点后，可以这样要求：

```text
请基于本项目的入口文档与必要代码，给我一份简要学习路线图。
每个主题说明：要回答什么问题、为何值得先学、从哪些真实文件开始、与前后主题有什么关系。
先给概要；证据不足时说明缺口，不先生成全量详细文档，也不修改业务代码。
```

期望的概要形态，例如：请求从哪里进入 → 怎样流转到核心业务 → 数据如何保存 → 结果怎样返回。具体主题以项目事实和学习目标为准，不把这个例子硬套到所有项目。

### 第二步：把路线展开成可查阅的主题文档

确定范围和输出位置后，可以这样衔接：

```text
沿用刚才的学习路线，按已确定的主题分别研究并保存文档。
每篇回答该主题的问题，讲清主链路、关键节点、一个最小例子和真实源码定位；未知项明确标注。
概要作为导航，详细内容只在对应主题维护，跨主题用链接，不重复整段正文。
只展开约定范围，不为了补齐目录扫描无关模块。
```

项目专属调研正文留在对应项目的现有文档位置；本记录只保存可复用方法，不复制那些调研成果。写入目录遵守目标项目规则。

## 注意事项与可预见的误用

这些是使用建议，不是已经发生过的踩坑记录：

- “简要路线图”不是文件清单：应解释先后顺序与学习问题，否则读者仍然不知道如何开始。
- 主题以要回答的问题划分，不要求一个源文件一篇文档。
- 第二步需要引用第一步的路线及约定范围，否则可能丢失重点，变成泛化报告。
- 先查真实依据再写结论；文件名、接口和链路不能靠模型猜测。
- 概要和详文分别负责导航与细节，不维护两份相同正文。

## 下次使用与来源修订

先明确“我为什么学习这个项目”，再用概要控制深入范围；学习目标或项目结构变化后重新核对路线，不无条件照搬旧文档。
